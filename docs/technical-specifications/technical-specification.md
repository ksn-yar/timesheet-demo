## 1. Введение и цели системы

### 1.1 Назначение

**corpo-timesheet** — локальная корпоративная система учёта рабочего времени. Назначение системы состоит в том, чтобы обеспечить прозрачную и структурированную фиксацию фактических трудозатрат сотрудников в разрезе клиентов, проектов и задач.

Система не является task-tracker'ом: задачи создаются как справочные объекты для привязки трудозатрат, а не как инструмент планирования. Система не выставляет счета клиентам и не управляет расписанием и загрузкой сотрудников — она предоставляет данные, на основе которых это может быть сделано во внешних инструментах.

### 1.2 Бизнес-цели

| # | Цель | Ценность |
|---|------|----------|
| БЦ-1 | Обеспечить достоверный учёт рабочего времени сотрудников в привязке к конкретным задачам | Основа для расчёта стоимости работ и контроля трудозатрат |
| БЦ-2 | Предоставить руководителям инструмент для анализа и выгрузки отчётов о трудозатратах | Управленческая аналитика, обоснование счетов клиентам |
| БЦ-3 | Поддержать иерархическую структуру Client — Project — Task | Структурирование работ и корректная тарификация |
| БЦ-4 | Обеспечить автоматический импорт данных из внешних систем | Снижение ручного ввода и ошибок, интеграция с существующими инструментами |
| БЦ-5 | Контролировать доступ к данным в соответствии с ролями пользователей | Конфиденциальность и разграничение ответственности |

### 1.3 Архитектурная декомпозиция

Система состоит из пяти изолированных Bounded Context, каждый из которых несёт ответственность за чётко очерченную область данных и правил:

```
┌─────────────────────────────────────────────────────────────────┐
│                        CORPO-TIMESHEET                          │
│                                                                 │
│  [Project Management]  ──────────────────────────────────────┐  │
│  Client, Project, CR, Task                                   │  │
│                                                              ▼  │
│  [Work Catalog]  ────────────►  [Timesheet]  ────► [Reporting]  │
│  Rate, Role, Work              Ticket (ядро)        Report       │
│                                      ▲                          │
│  [Identity]  ───────────────────────┘                          │
│  User, Group                                                    │
└─────────────────────────────────────────────────────────────────┘
```

Направления зависимостей между контекстами:

- **Project Management** → Timesheet (Task — обязательная ссылка для Ticket)
- **Work Catalog** → Timesheet (Rate фиксируется при создании Ticket; Work указывается в Ticket)
- **Identity** → Timesheet (Employee — обязательный атрибут Ticket)
- **Timesheet** → Reporting (все Report строятся на основе Ticket)

## 2. Роли пользователей и матрица доступа

### 2.1 Описание ролей

**Admin (Администратор)** — управляет конфигурацией всей системы. Единственная роль, имеющая право создавать и редактировать справочники и структурные объекты, настраивать и запускать импорт, а также добавлять Ticket за любого сотрудника.

**Manager (Менеджер)** — контролирует ход работ и анализирует трудозатраты команды. Не вносит данные — работает исключительно с результатами. Имеет доступ к тикетам всех сотрудников и к функциям формирования и выгрузки отчётов.

**Employee (Сотрудник)** — вносит фактические трудозатраты в систему. Работает только со своими данными: добавляет и редактирует собственные Manual Ticket, просматривает справочники для выбора при вводе.

### 2.2 Матрица прав доступа

| Действие | Admin | Manager | Employee |
|----------|:-----:|:-------:|:--------:|
| Создание и редактирование Client, Project, CR, Task | + | — | — |
| Создание и редактирование Rate, Role, Work | + | — | — |
| Создание и редактирование User и Group | + | — | — |
| Настройка и запуск импорта (Import Policy) | + | — | — |
| Добавление Ticket за себя | + | — | + |
| Добавление Ticket за другого сотрудника | + | — | — |
| Редактирование своих Manual Ticket | + | — | + |
| Редактирование Manual Ticket любого сотрудника | + | — | — |
| Просмотр своих Ticket | + | — | + |
| Просмотр Ticket любого сотрудника | + | + | — |
| Формирование Report | + | + | — |
| Просмотр Report List | + | + | — |
| Выгрузка Report в файл | + | + | — |
| Просмотр справочников (Work List, Task List) | + | + | + |
| Просмотр User List | + | + | — |

## 3. Доменная модель

### 3.1 Project Management

#### Client (Клиент)

Организация или физическое лицо, для которого выполняются работы. Верхний уровень иерархии.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование клиента |
| description | string | опционально | Дополнительное описание |

**Ограничения:** `name` не может быть пустым. Client не может быть удалён, если к нему привязан хотя бы один активный Project.

---

#### Project (Проект)

Совокупность работ, выполняемых для Client в рамках договора. Принадлежит ровно одному Client.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| clientId | UUID | обязательно | Ссылка на Client |
| name | string | обязательно | Наименование проекта |
| status | enum | обязательно | Статус: `Active`, `Closed` |
| description | string | опционально | Дополнительное описание |

**Ограничения:** Project не может быть удалён, если к нему привязаны Task или CR.

---

#### CR (Change Request)

Запрос на изменение скоупа Project. Не является самостоятельным Project — всегда привязан к конкретному Project.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| projectId | UUID | обязательно | Ссылка на родительский Project |
| name | string | обязательно | Наименование CR |
| description | string | опционально | Описание изменения |

**Ограничения:** CR не может быть перенесён в другой Project после создания.

---

#### Task (Задача)

Единица работы внутри Project или CR. Конечная точка иерархии, к которой привязываются Ticket.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| projectId | UUID | условно | Ссылка на Project (заполняется, если Task принадлежит Project) |
| crId | UUID | условно | Ссылка на CR (заполняется, если Task принадлежит CR) |
| name | string | обязательно | Наименование задачи |
| description | string | опционально | Описание задачи |
| estimate | decimal | опционально | Эстимейт трудозатрат в часах |

**Ограничения:** ровно одно из полей `projectId` / `crId` должно быть заполнено. Task не может быть удалена, если к ней привязаны Ticket.

---

### 3.2 Work Catalog

#### Rate (Ставка)

Тарифная ставка в единицу времени. Фиксируется в Ticket на момент его создания и не пересчитывается ретроспективно.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| amount | decimal | обязательно | Сумма ставки (> 0) |
| currency | string | обязательно | Валюта (например: USD, EUR, RUB) |
| effectiveFrom | date | обязательно | Дата вступления ставки в силу |
| roleId | UUID | опционально | Ссылка на Role |
| workId | UUID | опционально | Ссылка на Work |

**Ограничения:** `amount` должен быть положительным числом. `effectiveFrom` не может быть изменён после того, как Rate была применена к хотя бы одному Ticket.

---

#### Role (Функциональная роль)

Специализация исполнителя (например: Developer, QA, PM). Влияет на Rate при расчёте стоимости работ.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование (уникальное) |
| description | string | опционально | Описание роли |

**Ограничения:** `name` должен быть уникальным. Role не может быть удалена, если к ней привязаны Rate или пользователи.

---

#### Work (Вид работ)

Классификатор вида выполняемой деятельности (например: Development, Consulting, Testing). Используется при вводе Ticket и группировке в отчётах.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование (уникальное) |
| description | string | опционально | Описание вида работ |

**Ограничения:** `name` должен быть уникальным. Work не может быть удалена, если она используется в существующих Ticket.

---

### 3.3 Identity

#### User (Пользователь)

Физическое лицо, имеющее доступ к системе.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Полное имя |
| email | string | обязательно | Email — уникальный логин для входа в систему |
| systemRole | enum | обязательно | Системная роль: `Admin`, `Manager`, `Employee` |
| groupId | UUID | опционально | Ссылка на Group |
| roleId | UUID | опционально | Ссылка на функциональную Role из Work Catalog |
| isActive | boolean | обязательно | Признак активности учётной записи |

**Ограничения:** `email` должен быть уникальным. User не может быть удалён физически, если к нему привязаны Ticket; допускается только деактивация (`isActive = false`).

---

#### Group (Группа)

Организационная единица, объединяющая User. Используется для разграничения доступа и группировки данных в отчётах.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование (уникальное) |
| description | string | опционально | Описание группы |

**Ограничения:** `name` должен быть уникальным. Group не может быть удалена, если в ней есть активные User.

---

### 3.4 Timesheet

#### Ticket (Тикет)

Основная сущность системы. Запись о времени, затраченном Employee на конкретную Task.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| employeeId | UUID | обязательно | Ссылка на User (в роли Employee) |
| taskId | UUID | обязательно | Ссылка на Task |
| workId | UUID | обязательно | Ссылка на Work |
| date | date | обязательно | Дата, за которую зафиксированы трудозатраты |
| hours | decimal | обязательно | Количество часов (> 0) |
| comment | string | опционально | Комментарий к тикету |
| rateSnapshot | decimal | обязательно | Снимок значения Rate на момент создания (не изменяется) |
| type | enum | обязательно | Тип: `Manual`, `Imported` |
| importSource | string | условно | Идентификатор источника (только для Imported Ticket) |
| isEditable | boolean | обязательно | Разрешено ли ручное редактирование |

**Ограничения:** `hours` должно быть положительным числом. `rateSnapshot` фиксируется один раз при создании и не пересчитывается. Для Imported Ticket `isEditable = false` по умолчанию (переопределяется Import Policy).

---

#### Import Policy (Политика импорта)

Набор правил трансформации данных внешней системы в Ticket. Реализует паттерн Anti-Corruption Layer на границе с внешней системой.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование политики |
| sourceSystem | string | обязательно | Идентификатор внешней системы-источника |
| mappingRules | JSON | обязательно | Правила трансформации полей |
| allowEdit | boolean | обязательно | Разрешает ли политика ручное редактирование Imported Ticket |
| isActive | boolean | обязательно | Признак активности политики |

**Ограничения:** для одного `sourceSystem` может быть активна (`isActive = true`) только одна Import Policy одновременно.

---

### 3.5 Reporting

#### Report (Отчёт)

Агрегированное представление Ticket за заданный период и набор параметров. Сохраняется как неизменяемый снимок данных.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование отчёта |
| createdBy | UUID | обязательно | Ссылка на User, создавшего отчёт |
| createdAt | datetime | обязательно | Дата и время формирования |
| periodFrom | date | обязательно | Начало периода выборки |
| periodTo | date | обязательно | Конец периода выборки |
| filters | JSON | опционально | Применённые фильтры (Employee, Group, Project, CR, Task, Work) |
| groupBy | string[] | обязательно | Измерения группировки |
| data | JSON | обязательно | Агрегированные данные (snapshot) |

**Ограничения:** `periodFrom` не может быть позже `periodTo`. Report не может быть изменён после создания.

---

#### Report Export (Выгрузка отчёта)

Value Object — артефакт операции экспорта, не самостоятельный агрегат.

| Атрибут | Тип | Описание |
|---------|-----|---------|
| reportIds | UUID[] | Идентификаторы Report, включённых в выгрузку |
| format | enum | Формат файла: `CSV`, `XLSX`, `PDF` |
| generatedAt | datetime | Дата и время генерации |
| fileRef | string | Ссылка на сгенерированный файл |

---

### 3.6 Read Models (Проекции)

| Read Model | Контекст | Описание | Фильтрация |
|------------|----------|---------|------------|
| Client List | Project Management | Список всех Client | Поиск по наименованию |
| Project List | Project Management | Список Project по Client | По Client, по статусу |
| Task List | Project Management | Список Task | По Project, по CR |

| Exported Reports List | Reporting | Список файлов выгрузок | По формату, дате генерации |

## 4. Функциональные требования по доменам

### 4.1 Project Management

**ФТ-PM-01.** Система должна позволять Admin создавать записи о клиентах с указанием наименования и опционального описания.

**ФТ-PM-02.** Система должна позволять Admin создавать проекты с привязкой к существующему Client, наименованием, статусом (`Active` / `Closed`) и опциональным описанием.

**ФТ-PM-03.** Система должна позволять Admin создавать Change Request с привязкой к существующему Project. Привязка CR к Project должна быть неизменной после создания.

**ФТ-PM-04.** Система должна позволять Admin создавать Task внутри Project или CR с наименованием, опциональным описанием и опциональным эстимейтом трудозатрат в часах.

**ФТ-PM-05.** Система должна предоставлять всем ролям доступ к Client List, Project List и Task List с возможностью фильтрации:
- Client List — поиск по наименованию;
- Project List — фильтр по Client и/или статусу;
- Task List — фильтр по Project и/или CR.

**ФТ-PM-06.** Система должна запрещать удаление Client при наличии хотя бы одного привязанного активного Project; Project — при наличии Task или CR; Task — при наличии привязанных Ticket.

---

### 4.2 Work Catalog

**ФТ-WC-01.** Система должна позволять Admin создавать Work (виды работ) с уникальным наименованием и опциональным описанием.

**ФТ-WC-02.** Система должна позволять Admin создавать Role (функциональные роли) с уникальным наименованием и опциональным описанием.

**ФТ-WC-03.** Система должна позволять Admin создавать Rate с указанием суммы (> 0), валюты, даты вступления в силу и опциональных ссылок на Role и/или Work.

**ФТ-WC-04.** Система должна запрещать изменение `effectiveFrom` у Rate, если к ней уже привязан хотя бы один Ticket.

**ФТ-WC-05.** Система должна запрещать удаление Work, если она использована в существующих Ticket; запрещать удаление Role, если к ней привязаны Rate или пользователи.

**ФТ-WC-06.** Система должна предоставлять всем ролям доступ к Work List.

---

### 4.3 Identity

**ФТ-ID-01.** Система должна позволять Admin создавать учётные записи User с уникальным email, именем, системной ролью (`Admin`, `Manager`, `Employee`) и опциональными ссылками на Group и функциональную Role.

**ФТ-ID-02.** Система должна позволять Admin создавать Group с уникальным наименованием.

**ФТ-ID-03.** Система должна позволять Admin назначать User в Group и изменять принадлежность к Group.

**ФТ-ID-04.** Система должна позволять Admin деактивировать User (устанавливать `isActive = false`), сохраняя при этом все исторические данные (Ticket, отчёты) пользователя.

**ФТ-ID-05.** Система должна запрещать физическое удаление User, если к нему привязаны Ticket. Допускается только деактивация.

**ФТ-ID-06.** Система должна предоставлять Admin и Manager доступ к User List с фильтрацией по Group, функциональной Role и статусу активности.

---

### 4.4 Timesheet

**ФТ-TS-01.** Система должна позволять Employee добавлять Manual Ticket с указанием Task, Work, даты, количества часов (> 0) и опционального комментария. При создании Ticket система фиксирует текущее значение Rate как `rateSnapshot`.

**ФТ-TS-02.** Система должна запрещать Employee добавлять Ticket за другого сотрудника. Добавление Ticket за любого сотрудника доступно только Admin.

**ФТ-TS-03.** Система должна позволять Employee редактировать собственные Manual Ticket (дата, часы, Work, комментарий). Admin может редактировать любой Manual Ticket. `rateSnapshot` не пересчитывается при редактировании.

**ФТ-TS-04.** Система должна запрещать ручное редактирование Imported Ticket, если параметр `allowEdit` соответствующей Import Policy установлен в `false`.

**ФТ-TS-05.** Система должна предоставлять:
- Employee — Ticket List только со своими записями, с фильтрацией по Project, Task, Work и периоду;
- Manager и Admin — Ticket List по любому сотруднику, с расширенной фильтрацией по Employee, Project, CR, Task, Work и периоду.

**ФТ-TS-06.** Система должна позволять Admin создавать и редактировать Import Policy с указанием наименования, идентификатора внешней системы, правил маппинга полей, флага `allowEdit` и статуса активности.

**ФТ-TS-07.** Система должна позволять Admin запускать импорт Ticket по активной Import Policy для заданного временного диапазона. В ходе импорта система должна:
- трансформировать данные внешней системы по правилам `mappingRules`;
- сопоставлять внешние записи с внутренними сущностями (Employee, Task, Work);
- не создавать дубликаты: запись считается дубликатом по паре (`importSource` + внешний идентификатор записи);
- логировать записи, которые не удалось сопоставить, не прерывая импорт остальных записей.

---

### 4.5 Reporting

**ФТ-RP-01.** Система должна позволять Manager и Admin формировать Report с указанием периода (дата от/до), опциональных фильтров (Employee, Group, Project, CR, Task, Work) и измерений группировки (Employee, Group, Project, CR, Task, Work). `periodFrom` не может быть позже `periodTo`.

**ФТ-RP-02.** Сформированный Report должен сохраняться как неизменяемый снимок данных. Последующие изменения в Ticket не должны влиять на ранее сохранённые Report.

**ФТ-RP-03.** Система должна предоставлять Manager и Admin доступ к Report List с мета-информацией (наименование, период, автор, дата создания) и возможностью фильтрации по автору, периоду и наименованию.

**ФТ-RP-04.** Система должна позволять Manager и Admin выгружать один или несколько Report в файл формата CSV, XLSX или PDF.

**ФТ-RP-05.** Система должна хранить ссылки на сгенерированные файлы и предоставлять доступ к ним через Exported Reports List.

## 5. Сценарии использования (Use Cases)

### 5.1 Project Management

---

**UC-PM-01: Создать Client**

**Актор:** Admin
**Предусловия:** Admin аутентифицирован в системе.
**Триггер:** Admin инициирует создание нового клиента.

**Основной сценарий:**
1. Admin вводит наименование и опциональное описание Client.
2. Система проверяет, что наименование не пустое.
3. Система создаёт Client и публикует событие `ClientCreated`.
4. Client отображается в Client List.

**Альтернативные сценарии:**
- 2a. Наименование пустое → система отклоняет запрос с сообщением об ошибке валидации; Client не создаётся.

**Постусловия:** новый Client доступен для выбора при создании Project.

---

**UC-PM-02: Создать Project**

**Актор:** Admin
**Предусловия:** существует хотя бы один Client.
**Триггер:** Admin инициирует создание нового проекта.

**Основной сценарий:**
1. Admin выбирает Client из Client List.
2. Admin вводит наименование, статус (`Active` / `Closed`) и опциональное описание Project.
3. Система создаёт Project, привязанный к выбранному Client, и публикует событие `ProjectCreated`.
4. Project отображается в Project List для данного Client.

- 1a. Client не выбран → система не позволяет завершить создание.
- 2a. Наименование пустое → система отклоняет запрос с сообщением об ошибке валидации.

**Постусловия:** новый Project доступен для создания CR и Task.

---

**UC-PM-03: Создать CR**

**Актор:** Admin
**Предусловия:** существует хотя бы один Project.
**Триггер:** Admin инициирует создание Change Request.

**Основной сценарий:**
1. Admin выбирает Project из Project List.
2. Admin вводит наименование и опциональное описание CR.
3. Система создаёт CR, привязанный к выбранному Project, и публикует событие `CRCreated`.

**Альтернативные сценарии:**

**Постусловия:** новый CR доступен для создания Task и привязки Ticket.

---

**UC-PM-04: Создать Task**

**Актор:** Admin
**Предусловия:** существует хотя бы один Project или CR.
**Триггер:** Admin инициирует создание задачи.

**Основной сценарий:**
1. Admin выбирает Project или CR в качестве родительского объекта.
2. Admin вводит наименование, опциональное описание и опциональный эстимейт трудозатрат.
3. Система создаёт Task, привязанную к выбранному Project или CR, и публикует событие `TaskCreated`.
4. Task отображается в Task List.

**Альтернативные сценарии:**
- 1a. Родительский объект не выбран → система не позволяет завершить создание.
- 3a. Admin пытается удалить Task, к которой привязаны Ticket → система отклоняет удаление.

**Постусловия:** новая Task доступна для привязки Ticket.

**UC-PM-05: Просмотр Client List / Project List / Task List**

**Актор:** Admin, Manager, Employee

3. Система возвращает отфильтрованный список объектов.

**Постусловия:** актор видит актуальные данные и может выбрать нужную запись.

### 5.4 Timesheet

---

**UC-TS-01: Добавить Manual Ticket**

**Актор:** Employee, Admin (за любого Employee)
**Предусловия:** актор аутентифицирован. Существуют Task и Work.
**Триггер:** Employee фиксирует трудозатраты.

**Основной сценарий:**
1. Employee открывает форму добавления Ticket.
2. Employee выбирает Task из Task List, Work из Work List, указывает дату, количество часов, опциональный комментарий.
3. Система проверяет: `hours > 0`; Employee добавляет Ticket только за себя (если не Admin); Task существует.
4. Система фиксирует текущее значение Rate как `rateSnapshot`.
5. Система создаёт Manual Ticket (`type = Manual`, `isEditable = true`) и публикует событие `TicketsAdded`.
6. Ticket отображается в Ticket List.

**Альтернативные сценарии:**
- 3a. `hours ≤ 0` → система отклоняет создание.
- 3b. Employee пытается добавить Ticket за другого сотрудника → система отклоняет операцию.
- 3c. Task не существует → система отклоняет создание.

**Постусловия:** трудозатраты зафиксированы и доступны для формирования Report.

---

**UC-TS-02: Редактировать Manual Ticket**

**Актор:** Employee (автор), Admin
**Предусловия:** Ticket существует, `type = Manual`.

**Основной сценарий:**
1. Актор выбирает Ticket из Ticket List.
2. Актор изменяет допустимые поля: дата, часы, Work, комментарий.
3. Система проверяет права: Employee может редактировать только собственный Ticket.
4. Система обновляет Ticket. `rateSnapshot` не пересчитывается.

**Альтернативные сценарии:**
- 3a. Employee пытается редактировать Ticket другого сотрудника → система отклоняет.
- 1a. Ticket имеет `type = Imported` и `isEditable = false` → система отклоняет редактирование.

**Постусловия:** Manual Ticket обновлён с сохранением исходного `rateSnapshot`.

---

**UC-TS-03: Просмотр Ticket List**

**Актор:** Employee, Manager, Admin
**Предусловия:** актор аутентифицирован.

**Основной сценарий:**
1. Актор открывает Ticket List.
2. Актор применяет фильтры согласно своим правам:
   - Employee видит только свои Ticket; доступны фильтры по Project, Task, Work, периоду.
   - Manager и Admin видят Ticket всех сотрудников; доступны фильтры по Employee, Project, CR, Task, Work, периоду.
3. Система возвращает отфильтрованный список Ticket.

**Постусловия:** актор видит записи о трудозатратах в соответствии со своими правами.

---

**UC-TS-04: Настроить Import Policy**

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin задаёт наименование, `sourceSystem` (идентификатор внешней системы), `mappingRules` (правила трансформации полей), `allowEdit`.
2. Admin активирует политику (`isActive = true`).
3. Система проверяет: для данного `sourceSystem` нет другой активной политики.
4. Система сохраняет Import Policy.

**Альтернативные сценарии:**
- 3a. Для данного `sourceSystem` уже существует активная Import Policy → система отклоняет активацию новой.

**Постусловия:** система готова к импорту Ticket из указанной внешней системы.

---

**UC-TS-05: Запустить импорт Ticket**

**Актор:** Admin
**Предусловия:** существует активная Import Policy для внешней системы.

**Основной сценарий:**
1. Admin выбирает Import Policy и указывает временной диапазон для импорта.
2. Система через Anti-Corruption Layer (Import Policy) получает данные из внешней системы.
3. Система трансформирует записи по `mappingRules`, сопоставляет их с внутренними сущностями (Employee, Task, Work).
4. Система создаёт Imported Ticket для каждой успешно трансформированной записи. Дубликаты (по паре `importSource` + внешний идентификатор) не создаются.
5. Записи, которые не удалось сопоставить, логируются; импорт остальных записей продолжается.
6. Система публикует событие `TicketsImported` с количеством импортированных записей.

**Постусловия:** данные из внешней системы доступны в Ticket List.

## 6. API-требования

В данном разделе описывается *что должны делать* API системы (требования к поведению и контракту), без привязки к технологии реализации.

### 6.1 Общие требования ко всем API

- Все API-операции должны требовать аутентификации. Неаутентифицированные запросы отклоняются.
- Каждая API-операция должна проверять права вызывающего пользователя и отклонять запрос с соответствующей ошибкой при нарушении прав доступа.
- Ответы об ошибках должны содержать машиночитаемый код ошибки и человекочитаемое описание.
- Все идентификаторы сущностей должны быть UUID.
- Операции с коллекциями должны поддерживать пагинацию.
- Валидация входных данных должна выполняться на уровне API до передачи в доменный слой.

### 6.2 Project Management API

| Операция | Описание | Права |
|----------|---------|-------|
| Создать Client | Принимает `name`, `description`. Возвращает созданный Client с `id`. Отклоняет пустое `name`. | Admin |
| Получить Client List | Возвращает список Client с поддержкой поиска по `name`. | Admin, Manager, Employee |
| Создать Project | Принимает `clientId`, `name`, `status`, `description`. Проверяет существование Client. | Admin |
| Получить Project List | Поддерживает фильтрацию по `clientId`, `status`. | Admin, Manager, Employee |
| Создать CR | Принимает `projectId`, `name`, `description`. Проверяет существование Project. | Admin |
| Создать Task | Принимает `projectId` или `crId`, `name`, `description`, `estimate`. Ровно одно из `projectId`/`crId` должно быть заполнено. | Admin |
| Получить Task List | Поддерживает фильтрацию по `projectId`, `crId`. | Admin, Manager, Employee |
| Удалить Client | Отклоняет удаление при наличии активных Project. | Admin |
| Удалить Project | Отклоняет удаление при наличии Task или CR. | Admin |
| Удалить Task | Отклоняет удаление при наличии привязанных Ticket. | Admin |

### 6.3 Work Catalog API

| Операция | Описание | Права |
|----------|---------|-------|
| Создать Work | Принимает `name`, `description`. Проверяет уникальность `name`. | Admin |
| Получить Work List | Возвращает полный список Work. | Admin, Manager, Employee |
| Создать Role | Принимает `name`, `description`. Проверяет уникальность `name`. | Admin |
| Получить Role List | Возвращает список Role. | Admin |
| Создать Rate | Принимает `amount` (> 0), `currency`, `effectiveFrom`, опциональные `roleId`, `workId`. | Admin |
| Получить Rate List | Возвращает список Rate с возможностью фильтрации по `roleId`, `workId`. | Admin |
| Изменить Rate | Запрещает изменение `effectiveFrom`, если Rate применена к Ticket. | Admin |
| Удалить Work | Отклоняет удаление, если Work используется в Ticket. | Admin |
| Удалить Role | Отклоняет удаление, если Role привязана к Rate или пользователям. | Admin |

### 6.4 Identity API

| Операция | Описание | Права |
|----------|---------|-------|
| Создать User | Принимает `name`, `email`, `systemRole`, опциональные `groupId`, `roleId`. Проверяет уникальность `email`. | Admin |
| Получить User List | Поддерживает фильтрацию по `groupId`, `roleId`, `isActive`. | Admin, Manager |
| Создать Group | Принимает `name`, `description`. Проверяет уникальность `name`. | Admin |
| Получить Group List | Возвращает список Group. | Admin, Manager |
| Назначить User в Group | Принимает `userId`, `groupId`. Обновляет принадлежность User к Group. | Admin |
| Деактивировать User | Устанавливает `isActive = false`. Не удаляет исторические данные. | Admin |
| Удалить User | Отклоняет удаление при наличии привязанных Ticket; предлагает деактивацию. | Admin |

### 6.5 Timesheet API

| Операция | Описание | Права |
|----------|---------|-------|
| Создать Manual Ticket | Принимает `employeeId`, `taskId`, `workId`, `date`, `hours` (> 0), `comment`. Фиксирует `rateSnapshot`. Employee может указать только себя в качестве `employeeId`. | Employee, Admin |
| Получить Ticket List | Поддерживает фильтрацию по `employeeId`, `projectId`, `crId`, `taskId`, `workId`, `dateFrom`, `dateTo`. Employee получает только свои Ticket. | Employee, Manager, Admin |
| Обновить Manual Ticket | Принимает `date`, `hours`, `workId`, `comment`. Проверяет права на редактирование. `rateSnapshot` не изменяется. Отклоняет, если `type = Imported` и `isEditable = false`. | Employee (свой), Admin |
| Создать Import Policy | Принимает `name`, `sourceSystem`, `mappingRules`, `allowEdit`. Проверяет отсутствие другой активной политики для того же `sourceSystem`. | Admin |
| Получить Import Policy List | Возвращает список всех Import Policy. | Admin |
| Обновить Import Policy | Позволяет изменить `mappingRules`, `allowEdit`, `isActive`. | Admin |
| Запустить импорт | Принимает `importPolicyId`, `dateFrom`, `dateTo`. Возвращает сводку: количество импортированных, количество дубликатов, количество ошибок. | Admin |

### 6.6 Reporting API

| Операция | Описание | Права |
|----------|---------|-------|
| Создать Report | Принимает `name`, `periodFrom`, `periodTo`, `filters`, `groupBy`. Проверяет `periodFrom ≤ periodTo`. Возвращает сформированный Report. | Manager, Admin |
| Получить Report List | Поддерживает фильтрацию по `createdBy`, `periodFrom`, `periodTo`, поиск по `name`. | Manager, Admin |
| Получить Report | Возвращает полные данные конкретного Report по `id`. | Manager, Admin |
| Экспортировать Report | Принимает список `reportIds`, `format` (CSV, XLSX, PDF). Генерирует файл и возвращает ссылку на него. | Manager, Admin |
| Получить Exported Reports List | Возвращает список ранее сгенерированных файлов с `format`, `generatedAt`, `fileRef`. | Manager, Admin |

## 7. Нефункциональные требования

### 7.1 Производительность

**НФТ-П-01.** Время отклика API для операций чтения (получение списков, просмотр данных) при нормальной нагрузке не должно превышать 1 секунды.

**НФТ-П-02.** Время отклика API для операций записи (создание, обновление одной сущности) при нормальной нагрузке не должно превышать 2 секунд.

**НФТ-П-03.** Формирование Report для периода до 12 месяцев при количестве Ticket до 100 000 должно завершаться не более чем за 30 секунд.

**НФТ-П-04.** Генерация файла Report Export (CSV, XLSX, PDF) для отчёта с данными до 50 000 строк должна завершаться не более чем за 60 секунд.

**НФТ-П-05.** Список-запросы (Ticket List, Report List и другие) должны поддерживать пагинацию и не загружать в память более 1 000 записей за один запрос.

### 7.2 Безопасность

**НФТ-Б-01.** Все API-операции должны выполняться только от имени аутентифицированного пользователя. Неаутентифицированные запросы должны возвращать ошибку без каких-либо данных о системе.

**НФТ-Б-02.** Разграничение прав доступа должно быть реализовано на уровне каждой операции в соответствии с матрицей прав из раздела 2. Попытка выполнить операцию без необходимых прав должна возвращать ошибку авторизации.

**НФТ-Б-03.** Employee не должен иметь возможности получить данные Ticket, принадлежащих другим сотрудникам, даже при прямом обращении по идентификатору.

**НФТ-Б-04.** Пароли пользователей не должны храниться в открытом виде. Должно применяться надёжное хэширование с солью.

**НФТ-Б-05.** Все входные данные должны проходить валидацию и санитизацию до обработки бизнес-логикой, чтобы исключить инъекции и XSS.

**НФТ-Б-06.** Доступ к функциям администрирования (управление пользователями, справочниками, Import Policy) должен логироваться с указанием пользователя, действия, времени и результата.

### 7.3 Надёжность и согласованность данных

**НФТ-Н-01.** Система должна обеспечивать атомарность операций создания и обновления сущностей: операция либо применяется полностью, либо откатывается без частичных изменений.

**НФТ-Н-02.** Инварианты доменной модели (раздел 8) должны соблюдаться при любых обстоятельствах. Нарушение инварианта недопустимо и должно приводить к отклонению операции с явным сообщением об ошибке.

**НФТ-Н-03.** Значение `rateSnapshot` в Ticket должно быть неизменным после создания — никакие последующие операции не должны его модифицировать.

**НФТ-Н-04.** Данные сформированного Report (`data`) должны быть неизменными после сохранения — изменение Ticket не должно влиять на ранее сохранённые Report.

**НФТ-Н-05.** Операция импорта должна быть идемпотентной: повторный запуск импорта с теми же данными не должен создавать дублирующие Ticket.

### 7.4 Удобство использования

**НФТ-У-01.** Сообщения об ошибках валидации должны содержать явное указание на поле и причину ошибки на понятном для пользователя языке.

**НФТ-У-02.** API-ответы должны содержать достаточно информации для построения пользовательского интерфейса без дополнительных запросов: списки должны возвращать наименования связанных сущностей (а не только идентификаторы).

**НФТ-У-03.** Все операции фильтрации списков должны корректно обрабатывать пустые результаты — возвращать пустую коллекцию, а не ошибку.

**НФТ-У-04.** При деактивации User система должна явно информировать, что исторические данные будут сохранены.

### 7.5 Расширяемость

**НФТ-Р-01.** Каждый Bounded Context должен иметь чётко определённую публичную границу (API/контракт). Внутренняя модель контекста не должна быть напрямую доступна другим контекстам.

**НФТ-Р-02.** Механизм Import Policy (маппинг полей через `mappingRules`) должен быть расширяемым: добавление новой внешней системы-источника не должно требовать изменения ядра Timesheet-контекста.

**НФТ-Р-03.** Параметры группировки и фильтрации в Reporting должны быть расширяемыми — добавление нового измерения группировки не должно требовать переработки архитектуры Reporting-контекста.

## 8. Бизнес-правила и инварианты

Инварианты — правила, которые система обязана соблюдать при любых обстоятельствах. Нарушение инварианта недопустимо и должно приводить к отклонению операции.

### 8.1 Инварианты иерархии объектов

| # | Инвариант |
|---|-----------|
| ИН-01 | Ticket всегда привязан к Task. |
| ИН-02 | Task всегда принадлежит либо Project, либо CR — не может существовать без родителя. |
| ИН-03 | CR всегда принадлежит ровно одному Project. CR не может быть перенесён в другой Project после создания. |
| ИН-04 | Project всегда принадлежит ровно одному Client. |
| ИН-05 | Client не может быть удалён, если к нему привязан хотя бы один активный Project. |
| ИН-06 | Project не может быть удалён, если к нему привязаны Task или CR. |
| ИН-07 | Task не может быть удалена, если к ней привязаны Ticket. |

### 8.2 Инварианты тарификации

| # | Инвариант |
|---|-----------|
| ИН-08 | Rate фиксируется в момент создания Ticket (`rateSnapshot`) и не пересчитывается ретроспективно ни при редактировании Ticket, ни при изменении Rate. |
| ИН-09 | Дата вступления в силу (`effectiveFrom`) у Rate не может быть изменена после того, как Rate была применена хотя бы к одному Ticket. |
| ИН-10 | Сумма Rate (`amount`) должна быть строго положительным числом (> 0). |
| ИН-11 | Наименование Role должно быть уникальным. Role не может быть удалена, если к ней привязаны Rate или пользователи в IdentityContext. |
| ИН-12 | Наименование Work должно быть уникальным. Work не может быть удалена, если она использована в существующих Ticket. |

### 8.3 Инварианты доступа к данным

| # | Инвариант |
|---|-----------|
| ИН-13 | Employee может добавлять Ticket только за себя. Добавление Ticket за другого сотрудника доступно только Admin. |
| ИН-14 | Employee может редактировать только собственные Manual Ticket. Admin может редактировать любой Manual Ticket. |
| ИН-15 | Imported Ticket нельзя редактировать вручную, если Import Policy не установила `allowEdit = true`. |
| ИН-16 | User не может быть удалён физически, если к нему привязаны Ticket. Допускается только деактивация (`isActive = false`). |
| ИН-17 | Email пользователя должен быть уникальным в системе. |

### 8.4 Инварианты импорта

| # | Инвариант |
|---|-----------|
| ИН-18 | Для одного `sourceSystem` может быть активна только одна Import Policy одновременно. |
| ИН-19 | Изменение Import Policy не пересчитывает ранее импортированные Ticket. |
| ИН-20 | Дубликаты при импорте определяются по паре (`importSource` + внешний идентификатор записи) и не создаются повторно. |

### 8.5 Инварианты отчётности

| # | Инвариант |
|---|-----------|
| ИН-21 | Данные Report (`data`) фиксируются как snapshot на момент формирования и не обновляются автоматически при изменении Ticket. |
| ИН-22 | Report не может быть изменён после создания. |
| ИН-23 | `periodFrom` отчёта не может быть позже `periodTo`. |

### 8.6 Правила для идентификаторов групп

| # | Правило |
|---|---------|
| БП-01 | Наименование Group должно быть уникальным. |
| БП-02 | Group не может быть удалена, если в ней состоят активные User. |

## 9. Глоссарий

Полный единый глоссарий терминов ведётся в документе `<project-dir>/docs/UbiquitousLanguage.md`. Все термины в коде, документации и коммуникациях используются строго в соответствии с этим глоссарием, без синонимов и произвольных замен.

### Ключевые термины

| Термин | Определение |
|--------|-------------|
| **Client** | Организация или лицо, для которого выполняются работы. Верхний уровень иерархии. |
| **Project** | Совокупность работ для Client в рамках договора. Принадлежит одному Client. |
| **CR (Change Request)** | Запрос на изменение скоупа Project. Всегда привязан к Project. |
| **Task** | Единица работы внутри Project или CR. Конечная точка иерархии для привязки Ticket. |
| **Rate** | Тарифная ставка в единицу времени. Фиксируется в Ticket на момент его создания. |
| **Role** | Функциональная роль исполнителя (Developer, QA, PM и т.д.). Влияет на тарификацию. |
| **Work** | Классификатор вида деятельности (Development, Consulting и т.д.). Используется в Ticket и отчётах. |
| **User** | Физическое лицо с доступом к системе. |
| **Group** | Организационная единица, объединяющая User. |
| **Admin** | Системная роль User с правами на управление конфигурацией. Не отдельный агрегат. |
| **Employee** | Контекстная роль User в TimesheetContext — вносит трудозатраты через Ticket. |
| **Manager** | Системная роль User — контролирует и анализирует работы, формирует отчёты. |
| **Ticket** | Запись о затраченном времени Employee на конкретную Task. Основная сущность системы. |
| **Manual Ticket** | Ticket, добавленный вручную через форму. |
| **Imported Ticket** | Ticket, созданный автоматически по правилам Import Policy из внешней системы. |
| **Import Policy** | Набор правил трансформации данных внешней системы в Ticket (Anti-Corruption Layer). |
| **rateSnapshot** | Значение Rate, зафиксированное в Ticket в момент его создания. Не изменяется. |
| **Report** | Агрегированный неизменяемый снимок данных о трудозатратах за период. |
| **Report Export** | Файл (CSV, XLSX, PDF), сгенерированный из Report. Value Object, не агрегат. |
| **Bounded Context** | Изолированная область доменной модели с чёткими границами и собственным языком. |

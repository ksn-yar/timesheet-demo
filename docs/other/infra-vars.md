# Варианты Docker-инфраструктуры для разработки corpo-timesheet

**Дата:** 2026-03-11
**Статус:** Черновик

---

## Контекст

Система corpo-timesheet — корпоративное приложение учёта рабочего времени на PHP 8.4 (предполагается Symfony). Архитектура разделена на 5 Bounded Context, использует доменные события, требует импорта данных из внешних систем (асинхронная обработка), генерации отчётов в CSV/XLSX/PDF (тяжёлые фоновые задачи), а также отправки уведомлений по email.

Требования к инфраструктуре разработки:
- База данных (реляционная, UUID как PK, JSON-поля для mappingRules/filters/data)
- Кеш (списки, read-модели, сессии)
- Бэкенд на PHP 8.4
- Веб-сервер nginx
- MailHog для перехвата писем
- Брокер очередей (импорт тикетов, генерация отчётов/экспортов, доменные события)

---

## Вариант 1: PostgreSQL + Redis + RabbitMQ (рекомендуемый)

### Концепция

Классическая связка для Symfony-проектов с выделенным брокером сообщений. PostgreSQL покрывает все потребности в хранении данных (включая нативную поддержку JSON и UUID). RabbitMQ обеспечивает надёжную доставку сообщений с подтверждениями, routing и dead-letter очередями — критично для импорта тикетов, где ошибки не должны блокировать остальные записи.

### Сервисы

| Сервис | Образ | Порт (host) | Назначение |
|--------|-------|-------------|------------|
| **app** | `php:8.4-fpm` (custom Dockerfile) | 9000 | PHP-FPM, бэкенд-приложение. Расширения: pdo_pgsql, intl, opcache, amqp, redis, zip, gd |
| **nginx** | `nginx:1.27-alpine` | 8080 | Веб-сервер, проксирует запросы к php-fpm |
| **db** | `postgres:17-alpine` | 5432 | Основная БД. Volumes для персистентности данных |
| **redis** | `redis:7.4-alpine` | 6379 | Кеширование read-моделей, сессии, блокировки |
| **rabbitmq** | `rabbitmq:4.0-management-alpine` | 5672 / 15672 | Брокер очередей + management UI |
| **mailhog** | `mailhog/mailhog:v1.0.1` | 1025 / 8025 | SMTP-ловушка + веб-интерфейс просмотра писем |
| **worker** | тот же образ, что и app | - | Symfony Messenger consumer (команда `messenger:consume`) |

### Достоинства

- **Надёжность очередей.** RabbitMQ предоставляет подтверждения доставки (ack/nack), dead-letter exchange для обработки ошибок импорта, TTL для сообщений. Это напрямую закрывает требование ФТ-TS-07: записи, которые не удалось импортировать, логируются, а остальные продолжают обрабатываться.
- **Нативная поддержка JSON и UUID в PostgreSQL.** Поля `mappingRules`, `filters`, `data` (Report snapshot) хранятся в `jsonb` с возможностью индексации. UUID — встроенный тип `uuid`, а не строка.
- **Management UI для RabbitMQ.** В разработке видно состояние очередей, количество сообщений, ошибки — удобно при отладке импорта и генерации отчётов.
- **Зрелая интеграция с Symfony.** Symfony Messenger имеет первоклассную поддержку AMQP-транспорта.
- **Redis как универсальный кеш.** Подходит и для кеширования read-моделей (Client List, Work List), и для сессий, и для rate-limiting.

### Недостатки

- **Потребление памяти.** RabbitMQ требует ~200-300 МБ RAM даже в idle-состоянии. Суммарно стек потребляет 800-1200 МБ.
- **Сложность конфигурации RabbitMQ.** Необходимо настраивать exchanges, queues, bindings, dead-letter policy. Для проекта с 5 контекстами и доменными событиями конфигурация будет нетривиальной.
- **6-7 контейнеров.** Больше сервисов для мониторинга и обслуживания, хотя для разработки это приемлемо.

### Когда использовать

Рекомендуемый вариант для данного проекта. Выбирайте этот стек, если:
- Планируется полноценная реализация асинхронного импорта тикетов с обработкой ошибок и повторами.
- Доменные события между Bounded Context будут передаваться через брокер (а не синхронно).
- Генерация отчётов (Report) и экспорт файлов (CSV/XLSX/PDF) выполняются в фоне.
- Команда готова к настройке RabbitMQ или имеет опыт с ним.

## Вариант 2: PostgreSQL + Redis + Symfony Messenger Doctrine Transport

### Концепция

Облегчённый вариант без выделенного брокера сообщений. Очереди реализуются через таблицу в PostgreSQL, используя Doctrine Transport для Symfony Messenger. Это убирает из стека один инфраструктурный сервис (RabbitMQ) и упрощает DevOps, при этом сохраняя возможность асинхронной обработки.

### Сервисы

| Сервис | Образ | Порт (host) | Назначение |
|--------|-------|-------------|------------|
| **app** | `php:8.4-fpm` (custom Dockerfile) | 9000 | PHP-FPM, бэкенд-приложение. Расширения: pdo_pgsql, intl, opcache, redis, zip, gd |
| **nginx** | `nginx:1.27-alpine` | 8080 | Веб-сервер |
| **db** | `postgres:17-alpine` | 5432 | Основная БД + таблица `messenger_messages` для очередей |
| **redis** | `redis:7.4-alpine` | 6379 | Кеш, сессии |
| **mailhog** | `mailhog/mailhog:v1.0.1` | 1025 / 8025 | Перехват писем |
| **worker** | тот же образ, что и app | - | Symfony Messenger consumer |

### Достоинства

- **Меньше сервисов.** 5-6 контейнеров вместо 6-7. Нет отдельного брокера — меньше поверхность отказа при разработке.
- **Проще старт.** Не нужно настраивать exchanges, bindings, dead-letter policy. Doctrine Transport работает «из коробки» — достаточно одной миграции для создания таблицы.
- **Единая точка хранения.** Данные приложения и очереди в одной БД — проще бэкапить, проще отлаживать (можно делать SELECT из таблицы очереди).
- **Экономия памяти.** На 200-300 МБ меньше по сравнению с вариантом с RabbitMQ. Суммарно 500-800 МБ.
- **Легко мигрировать на RabbitMQ позже.** Symfony Messenger абстрагирует транспорт — переключение на AMQP сводится к изменению DSN в конфигурации.

### Недостатки

- **Polling вместо push.** Doctrine Transport опрашивает таблицу через `SELECT ... FOR UPDATE SKIP LOCKED`. Это создаёт постоянную нагрузку на БД и добавляет задержку доставки (по умолчанию 1 секунда).
- **Нет routing.** Нет exchanges и routing keys — все сообщения попадают в одну или несколько «плоских» очередей. Для маршрутизации доменных событий по контекстам придётся использовать stamps и envelope-механизмы Symfony.
- **Нет dead-letter из коробки.** Для обработки ошибок импорта (ФТ-TS-07) нужно реализовать retry-стратегию средствами Symfony Messenger (`failed` transport), а не инфраструктурно.
- **Масштабирование ограничено.** При росте объёма сообщений таблица `messenger_messages` становится «горячей точкой» в БД. Не подходит для high-throughput сценариев (но для corpo-timesheet с ~50-100 пользователями этого достаточно).

### Когда использовать

Выбирайте этот стек, если:
- Приоритет — быстрый старт разработки с минимальной инфраструктурной сложностью.
- Асинхронные задачи немногочисленны и не требуют сложной маршрутизации.
- Команда маленькая (1-2 разработчика) и нет ресурса на настройку RabbitMQ.
- Планируется миграция на полноценный брокер позже, когда система вырастет.

## Вариант 3: MySQL + Memcached + RabbitMQ

### Концепция

Альтернативный стек на базе MySQL вместо PostgreSQL и Memcached вместо Redis. Вариант для команд, у которых основная экспертиза в MySQL-экосистеме. RabbitMQ сохранён как брокер, поскольку требования к обработке ошибок импорта (ФТ-TS-07) делают выделенный брокер обоснованным.

### Сервисы

| Сервис | Образ | Порт (host) | Назначение |
|--------|-------|-------------|------------|
| **app** | `php:8.4-fpm` (custom Dockerfile) | 9000 | PHP-FPM. Расширения: pdo_mysql, intl, opcache, amqp, memcached, zip, gd |
| **nginx** | `nginx:1.27-alpine` | 8080 | Веб-сервер |
| **db** | `mysql:8.4` | 3306 | Основная БД |
| **memcached** | `memcached:1.6-alpine` | 11211 | Кеширование read-моделей и списков |
| **rabbitmq** | `rabbitmq:4.0-management-alpine` | 5672 / 15672 | Брокер очередей |
| **mailhog** | `mailhog/mailhog:v1.0.1` | 1025 / 8025 | Перехват писем |
| **worker** | тот же образ, что и app | - | Symfony Messenger consumer |

### Достоинства

- **Знакомый стек.** Если команда имеет глубокую экспертизу в MySQL, кривая обучения минимальна.
- **Простота Memcached.** Memcached проще Redis: один тип данных (key-value), нет персистентности, нет сложной конфигурации. Для кеширования read-моделей (списков Client, Project, Work) этого достаточно.
- **MySQL 8.4 поддерживает JSON.** Тип `JSON` с функциями `JSON_EXTRACT`, `JSON_CONTAINS` закрывает потребности в хранении `mappingRules`, `filters`, `data`.

### Недостатки

- **UUID в MySQL менее удобен.** MySQL не имеет нативного типа UUID. Хранение в `BINARY(16)` эффективно по памяти, но неудобно при отладке. `CHAR(36)` удобнее, но занимает больше места и медленнее при индексации.
- **Нет jsonb-индексов.** В PostgreSQL можно создавать GIN-индексы по `jsonb` для эффективного поиска внутри JSON-полей (фильтры отчётов, правила маппинга). В MySQL — только виртуальные колонки + обычные индексы, что требует больше ручной работы.
- **Memcached не поддерживает структуры данных.** В отличие от Redis, нет sorted sets, lists, hashes. Нельзя использовать для сессий (нет TTL на уровне сервера в том же смысле), rate-limiting, распределённых блокировок. Для сессий придётся использовать отдельный механизм (файлы или БД).
- **Memcached не персистентен.** Перезапуск контейнера = потеря всего кеша. В разработке это некритично, но отличается от поведения Redis с RDB/AOF.
- **Два тяжёлых сервиса.** MySQL + RabbitMQ потребляют суммарно больше RAM, чем PostgreSQL + RabbitMQ (MySQL 8.4 с настройками по умолчанию резервирует ~400 МБ под InnoDB buffer pool).

### Когда использовать

Выбирайте этот стек, если:
- Команда имеет устоявшуюся экспертизу в MySQL и не готова к переходу на PostgreSQL.
- Кеширование ограничивается простыми key-value паттернами (списки в JSON по ключу), без сложных структур.
- Инфраструктура продакшена уже построена на MySQL (например, AWS RDS MySQL), и хочется сохранить паритет окружений.

## Рекомендация

Для corpo-timesheet рекомендуется **Вариант 1** по следующим причинам:

1. **JSON-heavy модель данных.** Report.data, ImportPolicy.mappingRules, Report.filters — всё это jsonb с потенциальной необходимостью индексации и фильтрации. PostgreSQL здесь объективно сильнее MySQL.
2. **UUID как первичный ключ.** PostgreSQL имеет нативный тип `uuid` и функцию `gen_random_uuid()`. Не нужны обходные решения.
3. **Асинхронный импорт с обработкой ошибок.** Требование ФТ-TS-07 явно описывает сценарий, где часть записей падает, а остальные продолжают обрабатываться. Dead-letter exchange в RabbitMQ — штатный инструмент для этого.
4. **Redis — универсальный кеш.** Закрывает и read-модели, и сессии, и распределённые блокировки (при необходимости).

Если приоритет — минимизация времени до первого рабочего прототипа, начинайте с **Варианта 2** и переключайтесь на **Вариант 1** при появлении потребности в сложной маршрутизации сообщений или dead-letter обработке.

## 1. Цель домена

Домен **Reporting** отвечает за формирование управленческой аналитики на основе данных о трудозатратах. Это downstream-контекст: он потребляет данные из всех остальных доменов (Timesheet, Project Management, Work Catalog, Identity) и не изменяет их.

**Ключевые обязанности:**
- Формирование Report как неизменяемого снимка агрегированных данных о трудозатратах за выбранный период.
- Хранение ранее сформированных Report.
- Предоставление Report List с возможностью фильтрации.
- Экспорт одного или нескольких Report в файлы форматов CSV, XLSX, PDF.
- Хранение ссылок на сгенерированные файлы и предоставление доступа к ним.

**Чем домен не занимается:**
- Не изменяет данные в других доменах.
- Не является инструментом планирования или управления задачами.
- Не выставляет счёта клиентам.
- Не обновляет ранее сохранённые Report при изменении Ticket.

## 2. Сущности и Value Objects

### 2.1 Report (Aggregate Root)

Агрегированное представление Ticket за заданный период и набор параметров. Сохраняется как неизменяемый снимок данных.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование отчёта |
| createdBy | UUID | обязательно | Ссылка на User, создавшего отчёт (из IdentityContext) |
| createdAt | datetime | обязательно | Дата и время формирования |
| periodFrom | date | обязательно | Начало периода выборки |
| periodTo | date | обязательно | Конец периода выборки |
| filters | JSON | опционально | Применённые фильтры (Employee, Group, Project, CR, Task, Work) |
| groupBy | string[] | обязательно | Измерения группировки (Employee, Group, Project, CR, Task, Work — одно или несколько) |
| data | JSON | обязательно | Агрегированные данные (snapshot Ticket на момент формирования) |

**Ограничения:**
- `periodFrom` не может быть позже `periodTo`.
- Report не может быть изменён после создания (все атрибуты, включая `data`, неизменны).

---

### 2.2 Report Export (Value Object)

Артефакт операции экспорта. Не является самостоятельным агрегатом — создаётся как результат операции экспорта Report.

| Атрибут | Тип | Описание |
|---------|-----|---------|
| reportIds | UUID[] | Идентификаторы Report, включённых в выгрузку |
| format | enum | Формат файла: `CSV`, `XLSX`, `PDF` |
| generatedAt | datetime | Дата и время генерации файла |
| fileRef | string | Ссылка на сгенерированный файл (для скачивания) |

**Допустимые значения `format`:** `CSV`, `XLSX`, `PDF`.

## 3. Use Cases

### UC-RP-01: Сформировать Report

**Актор:** Manager, Admin
**Предусловия:** актор аутентифицирован. Существуют Ticket за запрашиваемый период (отсутствие Ticket не является ошибкой — Report будет сформирован с пустыми данными).
**Триггер:** актор запрашивает управленческую аналитику по трудозатратам.

**Основной сценарий:**
1. Актор задаёт параметры:
   - наименование Report;
   - период: `periodFrom`, `periodTo`;
   - опциональные фильтры: Employee, Group, Project, CR, Task, Work;
   - измерения группировки (`groupBy`): одно или несколько из Employee, Group, Project, CR, Task, Work.
2. Система проверяет: `periodFrom ≤ periodTo`.
3. Система запрашивает Ticket из TimesheetContext с учётом заданных фильтров и периода.
4. Система агрегирует данные по заданным измерениям группировки (суммирует `hours`, `rateSnapshot * hours` и т.д.).
5. Система сохраняет Report как неизменяемый snapshot и публикует событие `ReportAdded`.
6. Report отображается в Report List.

**Альтернативные сценарии:**
- 2a. `periodFrom > periodTo` → система отклоняет формирование с сообщением об ошибке.

**Постусловия:** Report сохранён. Последующие изменения в Ticket не влияют на данный Report.

---

### UC-RP-02: Выгрузить Report в файл

**Актор:** Manager, Admin
**Предусловия:** в Report List существует хотя бы один Report. Актор аутентифицирован.

**Основной сценарий:**
1. Актор выбирает один или несколько Report из Report List.
2. Актор указывает формат выгрузки: `CSV`, `XLSX` или `PDF`.
3. Система генерирует файл Report Export из данных выбранных Report.
4. Система публикует событие `ReportsExported`.
5. Ссылка на файл добавляется в Exported Reports List.
6. Актор скачивает файл по ссылке.

**Постусловия:** файл выгрузки доступен для скачивания и отображается в Exported Reports List.

---

### UC-RP-03: Просмотр Report List

**Актор:** Manager, Admin
**Предусловия:** актор аутентифицирован.

**Основной сценарий:**
1. Актор открывает Report List.
2. Актор опционально фильтрует список по: автору (`createdBy`), периоду (`periodFrom`/`periodTo`), наименованию.
3. Система возвращает список Report с мета-информацией: наименование, период, автор, дата создания.

**Постусловия:** актор видит актуальный список отчётов и может инициировать выгрузку.

---

### UC-RP-04: Просмотр Exported Reports List

**Актор:** Manager, Admin
**Предусловия:** актор аутентифицирован.

**Основной сценарий:**
1. Актор открывает список выгрузок (Exported Reports List).
2. Система возвращает список Report Export с: форматом файла, датой генерации, ссылкой на файл.
3. Актор скачивает нужный файл по ссылке.

**Постусловия:** актор получает доступ к ранее сгенерированным файлам.

## 4. Бизнес-правила и инварианты

### Инварианты отчётности

| # | Инвариант |
|---|-----------|
| ИН-21 | Данные Report (`data`) фиксируются как snapshot на момент формирования и не обновляются автоматически при изменении Ticket. |
| ИН-22 | Report не может быть изменён после создания. Атрибуты `data`, `filters`, `groupBy`, `periodFrom`, `periodTo` неизменны. |
| ИН-23 | `periodFrom` отчёта не может быть позже `periodTo`. |

**Дополнительные правила:**
- `groupBy` должен содержать хотя бы одно измерение группировки.
- `name` Report не может быть пустым.
- При выборе нескольких Report для выгрузки в один файл допускается любая их комбинация.

## 5. API-интерфейсы

Все операции требуют аутентификации. Все идентификаторы — UUID. Все операции с коллекциями поддерживают пагинацию.

### Report

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать Report | `name`, `periodFrom`, `periodTo`, `filters` (опционально), `groupBy` | Сформированный и сохранённый Report с `id` и `data` | Manager, Admin |
| Получить Report List | Фильтры: `createdBy`, `periodFrom`, `periodTo`, поиск по `name` (опционально) | Список Report с мета-информацией (без `data`) | Manager, Admin |
| Получить Report | `id` | Полные данные Report, включая `data` | Manager, Admin |
| Экспортировать Report | `reportIds[]` (один или несколько), `format` (CSV/XLSX/PDF) | Ссылка на сгенерированный файл (`fileRef`) | Manager, Admin |
| Получить Exported Reports List | Без обязательных фильтров, опциональный фильтр по `format`, `generatedAt` | Список Report Export с `format`, `generatedAt`, `fileRef` | Manager, Admin |

**Требования к операции Создать Report:**
- Проверяет `periodFrom ≤ periodTo`.
- Запрашивает Ticket из Timesheet API с учётом `filters` и периода.
- Агрегирует данные по `groupBy`.
- Сохраняет `data` как неизменяемый snapshot.

**Требования к операции Экспортировать Report:**
- Принимает список `reportIds` — минимум один.
- Генерирует файл в указанном формате (`CSV`, `XLSX`, `PDF`).
- Сохраняет ссылку на файл в Exported Reports List.
- При большом объёме данных (до 50 000 строк) операция должна завершаться не более чем за 60 секунд.

## 6. Read Models

| Read Model | Описание | Фильтрация |
|------------|---------|------------|
| Report List | Список сохранённых Report (без `data`) | По `createdBy`, по периоду, поиск по `name` |
| Exported Reports List | Список сгенерированных файлов выгрузок | По `format`, по `generatedAt` |

**Требование к Report List:** при отображении списка поле `data` не возвращается (только мета-информация). Полные данные Report возвращаются только при прямом запросе по `id`.

**Требование к ответам:** списки должны возвращать наименования связанных сущностей (имя автора, а не только `createdBy`) для построения UI без дополнительных запросов.

## 7. Публикуемые события

| Событие | Триггер | Содержимое |
|---------|---------|------------|
| `ReportAdded` | Сформирован и сохранён Report | `reportId`, `createdBy`, `periodFrom`, `periodTo` |
| `ReportsExported` | Сгенерирован файл выгрузки | `reportIds[]`, `format`, `fileRef`, `generatedAt` |

## 8. Зависимости от других доменов

### Входящие зависимости (этот домен зависит от...)

Reporting является downstream-контекстом и зависит от всех остальных доменов:

| Домен-поставщик | Что используется | Характер зависимости |
|-----------------|-----------------|---------------------|
| **Timesheet** | Ticket (основной источник данных для Report) | Reporting запрашивает Ticket List с фильтрами через Timesheet API |
| **Project Management** | Project, CR, Task (измерения группировки и фильтрации) | Reporting использует иерархию проектов как измерения |
| **Work Catalog** | Work (измерение группировки и фильтрации) | Reporting использует Work как измерение |
| **Identity** | User, Group (измерения группировки, фильтрации и идентификация автора Report) | Reporting использует User/Group как измерения и для отображения имени автора |

### Исходящие зависимости (другие домены зависят от нас)

Reporting не является upstream-контекстом ни для одного другого домена системы.

**Принцип изоляции:** Reporting не изменяет данные в других доменах. Все данные в Report — это snapshot, скопированный на момент формирования. После сохранения Report не обращается к другим доменам за пересчётом.

## 9. Нефункциональные требования

| # | Требование |
|---|-----------|
| НФТ-П-01 | Время отклика API для операций чтения (Report List, Exported Reports List) не должно превышать 1 секунды при нормальной нагрузке. |
| НФТ-П-03 | Формирование Report для периода до 12 месяцев при количестве Ticket до 100 000 должно завершаться не более чем за 30 секунд. |
| НФТ-П-04 | Генерация файла Report Export (CSV, XLSX, PDF) для отчёта с данными до 50 000 строк должна завершаться не более чем за 60 секунд. |
| НФТ-П-05 | Report List поддерживает пагинацию и не загружает в память более 1 000 записей за один запрос. |
| НФТ-Б-01 | Все операции выполняются только от имени аутентифицированного пользователя. |
| НФТ-Б-02 | Разграничение прав реализовано на уровне каждой операции: только Manager и Admin имеют доступ к Reporting. |
| НФТ-Б-05 | Все входные данные проходят валидацию и санитизацию до передачи в доменный слой. |
| НФТ-Н-01 | Атомарность операций: формирование Report применяется полностью или откатывается. |
| НФТ-Н-02 | Инварианты доменной модели соблюдаются при любых обстоятельствах. |
| НФТ-Н-04 | Данные Report (`data`) неизменны после сохранения — изменение Ticket не влияет на ранее сохранённые Report. |
| НФТ-Р-01 | Публичная граница (API/контракт) чётко определена. Внутренняя модель недоступна другим контекстам напрямую. |
| НФТ-Р-03 | Параметры группировки и фильтрации расширяемы: добавление нового измерения группировки не требует переработки архитектуры Reporting-контекста. |
| НФТ-У-01 | Сообщения об ошибках валидации содержат явное указание на поле и причину ошибки. |
| НФТ-У-02 | API-ответы содержат достаточно информации для построения UI без дополнительных запросов. |
| НФТ-У-03 | Пустые результаты фильтрации возвращаются как пустая коллекция, а не ошибка. |

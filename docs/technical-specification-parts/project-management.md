## 1. Цель домена

Домен **Project Management** отвечает за управление иерархической структурой: Client → Project → CR/Task. Это справочный upstream-контекст: он не хранит данные о трудозатратах, но предоставляет структурные объекты, к которым привязываются Ticket в TimesheetContext.

**Ключевые обязанности:**
- Хранение и управление справочником клиентов (Client).
- Хранение и управление проектами (Project) с привязкой к клиентам.
- Хранение и управление Change Request (CR) с привязкой к проектам.
- Хранение и управление задачами (Task) с привязкой к Project или CR.
- Предоставление этих данных всем ролям для выбора при вводе Ticket.

**Чем домен не занимается:**
- Не ведёт учёт трудозатрат.
- Не выставляет счета клиентам.
- Не управляет расписанием и загрузкой сотрудников.

## 2. Сущности и Value Objects

### 2.1 Client (Aggregate Root)

Организация или физическое лицо, для которого выполняются работы. Верхний уровень иерархии.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование клиента |
| description | string | опционально | Дополнительное описание |

**Ограничения:**
- `name` не может быть пустым.
- Client не может быть удалён, если к нему привязан хотя бы один активный Project.

---

### 2.2 Project (Aggregate Root)

Совокупность работ, выполняемых для Client в рамках договора. Принадлежит ровно одному Client.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| clientId | UUID | обязательно | Ссылка на Client |
| name | string | обязательно | Наименование проекта |
| status | enum | обязательно | Статус: `Active`, `Closed` |
| description | string | опционально | Дополнительное описание |

**Допустимые значения `status`:** `Active`, `Closed`.

**Ограничения:**
- Project не может быть удалён, если к нему привязаны Task или CR.

---

### 2.3 CR / Change Request (Aggregate Root)

Запрос на изменение скоупа Project. Не является самостоятельным Project — всегда привязан к конкретному Project.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| projectId | UUID | обязательно | Ссылка на родительский Project |
| name | string | обязательно | Наименование CR |
| description | string | опционально | Описание изменения |

**Ограничения:**
- CR не может быть перенесён в другой Project после создания.

---

### 2.4 Task (Aggregate Root)

Единица работы внутри Project или CR. Конечная точка иерархии, к которой привязываются Ticket.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| projectId | UUID | условно | Ссылка на Project (если Task принадлежит Project) |
| crId | UUID | условно | Ссылка на CR (если Task принадлежит CR) |
| name | string | обязательно | Наименование задачи |
| description | string | опционально | Описание задачи |
| estimate | decimal | опционально | Эстимейт трудозатрат в часах |

**Ограничения:**
- Ровно одно из полей `projectId` / `crId` должно быть заполнено. Task не может существовать без родителя.
- Task не может быть удалена, если к ней привязаны Ticket (проверка через обращение к TimesheetContext).

## 3. Use Cases

### UC-PM-01: Создать Client

**Актор:** Admin
**Предусловия:** Admin аутентифицирован в системе.
**Триггер:** Admin инициирует создание нового клиента.

**Основной сценарий:**
1. Admin вводит наименование и опциональное описание Client.
2. Система проверяет, что наименование не пустое.
3. Система создаёт Client и публикует событие `ClientCreated`.
4. Client отображается в Client List.

**Альтернативные сценарии:**
- 2a. Наименование пустое → система отклоняет запрос с сообщением об ошибке валидации; Client не создаётся.

**Постусловия:** новый Client доступен для выбора при создании Project.

---

### UC-PM-02: Создать Project

**Актор:** Admin
**Предусловия:** существует хотя бы один Client.
**Триггер:** Admin инициирует создание нового проекта.

**Основной сценарий:**
1. Admin выбирает Client из Client List.
2. Admin вводит наименование, статус (`Active` / `Closed`) и опциональное описание Project.
3. Система создаёт Project, привязанный к выбранному Client, и публикует событие `ProjectCreated`.
4. Project отображается в Project List для данного Client.

**Альтернативные сценарии:**
- 1a. Client не выбран → система не позволяет завершить создание.
- 2a. Наименование пустое → система отклоняет запрос с сообщением об ошибке валидации.

**Постусловия:** новый Project доступен для создания CR и Task.

---

### UC-PM-03: Создать CR

**Актор:** Admin
**Предусловия:** существует хотя бы один Project.
**Триггер:** Admin инициирует создание Change Request.

**Основной сценарий:**
1. Admin выбирает Project из Project List.
2. Admin вводит наименование и опциональное описание CR.
3. Система создаёт CR, привязанный к выбранному Project, и публикует событие `CRCreated`.

**Альтернативные сценарии:**
- 3a. Admin пытается впоследствии перенести CR в другой Project → система отклоняет операцию.

**Постусловия:** новый CR доступен для создания Task и привязки Ticket.

---

### UC-PM-04: Создать Task

**Актор:** Admin
**Предусловия:** существует хотя бы один Project или CR.
**Триггер:** Admin инициирует создание задачи.

**Основной сценарий:**
1. Admin выбирает Project или CR в качестве родительского объекта.
2. Admin вводит наименование, опциональное описание и опциональный эстимейт трудозатрат.
3. Система создаёт Task, привязанную к выбранному Project или CR, и публикует событие `TaskCreated`.
4. Task отображается в Task List.

**Альтернативные сценарии:**
- 1a. Родительский объект не выбран → система не позволяет завершить создание.
- 3a. Admin пытается удалить Task, к которой привязаны Ticket → система отклоняет удаление.

**Постусловия:** новая Task доступна для привязки Ticket.

---

### UC-PM-05: Просмотр Client List / Project List / Task List

**Актор:** Admin, Manager, Employee
**Предусловия:** актор аутентифицирован.

**Основной сценарий:**
1. Актор открывает нужный список.
2. Актор опционально применяет фильтры (по наименованию, Client, статусу, Project, CR).
3. Система возвращает отфильтрованный список объектов.

**Постусловия:** актор видит актуальные данные и может выбрать нужную запись.

---

### UC-PM-06: Удалить Client

**Актор:** Admin
**Предусловия:** Client существует.

**Основной сценарий:**
1. Admin инициирует удаление Client.
2. Система проверяет отсутствие привязанных активных Project.
3. Система удаляет Client.

**Альтернативные сценарии:**
- 2a. К Client привязан хотя бы один активный Project → система отклоняет удаление с явным сообщением.

---

### UC-PM-07: Удалить Project

**Актор:** Admin
**Предусловия:** Project существует.

**Основной сценарий:**
1. Admin инициирует удаление Project.
2. Система проверяет отсутствие привязанных Task и CR.
3. Система удаляет Project.

**Альтернативные сценарии:**
- 2a. К Project привязаны Task или CR → система отклоняет удаление.

---

### UC-PM-08: Удалить Task

**Актор:** Admin
**Предусловия:** Task существует.

**Основной сценарий:**
1. Admin инициирует удаление Task.
2. Система проверяет отсутствие привязанных Ticket (запрос к TimesheetContext).
3. Система удаляет Task.

**Альтернативные сценарии:**
- 2a. К Task привязаны Ticket → система отклоняет удаление.

## 4. Бизнес-правила и инварианты

| # | Инвариант |
|---|-----------|
| ИН-01 | Ticket всегда привязан к Task. Task не может быть удалена, пока к ней привязан хотя бы один Ticket. |
| ИН-02 | Task всегда принадлежит либо Project, либо CR — ровно одно из полей `projectId` / `crId` заполнено. |
| ИН-03 | CR всегда принадлежит ровно одному Project. CR не может быть перенесён в другой Project после создания. |
| ИН-04 | Project всегда принадлежит ровно одному Client. |
| ИН-05 | Client не может быть удалён, если к нему привязан хотя бы один активный Project. |
| ИН-06 | Project не может быть удалён, если к нему привязаны Task или CR. |
| ИН-07 | Task не может быть удалена, если к ней привязаны Ticket. |

**Дополнительные правила валидации:**
- `name` у Client, Project, CR, Task не может быть пустой строкой.
- `estimate` у Task, если указан, должен быть положительным числом.
- `status` у Project принимает только значения `Active` или `Closed`.

## 5. API-интерфейсы

Все операции требуют аутентификации. Все идентификаторы — UUID. Все операции с коллекциями поддерживают пагинацию.

### Client

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать Client | `name` (обязательно), `description` (опционально) | Созданный Client с `id` | Admin |
| Получить Client List | Фильтр: поиск по `name` (опционально) | Список Client с пагинацией | Admin, Manager, Employee |
| Удалить Client | `id` | Подтверждение или ошибка | Admin |

### Project

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать Project | `clientId`, `name`, `status`, `description` (опционально) | Созданный Project с `id` | Admin |
| Получить Project List | Фильтры: `clientId`, `status` (опционально) | Список Project с пагинацией | Admin, Manager, Employee |
| Удалить Project | `id` | Подтверждение или ошибка | Admin |

### CR

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать CR | `projectId`, `name`, `description` (опционально) | Созданный CR с `id` | Admin |

### Task

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать Task | `projectId` или `crId` (ровно одно), `name`, `description` (опционально), `estimate` (опционально) | Созданная Task с `id` | Admin |
| Получить Task List | Фильтры: `projectId`, `crId` (опционально) | Список Task с пагинацией | Admin, Manager, Employee |
| Удалить Task | `id` | Подтверждение или ошибка | Admin |

**Требования к ошибкам:**
- Ответ при ошибке содержит машиночитаемый код и человекочитаемое описание.
- Попытка выполнить операцию без необходимых прав возвращает ошибку авторизации.
- Нарушение бизнес-правила (например, удаление Client с активными Project) возвращает ошибку с указанием причины.

## 6. Read Models

| Read Model | Описание | Фильтрация |
|------------|---------|------------|
| Client List | Список всех Client | Поиск по наименованию |
| Project List | Список Project | По `clientId`, по `status` |
| Task List | Список Task | По `projectId`, по `crId` |

**Требование к ответам:** списки должны возвращать наименования связанных сущностей (а не только идентификаторы), достаточные для построения UI без дополнительных запросов.

**Требование к пустым результатам:** фильтры, не нашедшие записей, возвращают пустую коллекцию, а не ошибку.

## 7. Публикуемые события

| Событие | Триггер | Содержимое |
|---------|---------|------------|
| `ClientCreated` | Создание Client | `id`, `name` |
| `ProjectCreated` | Создание Project | `id`, `clientId`, `name`, `status` |
| `CRCreated` | Создание CR | `id`, `projectId`, `name` |
| `TaskCreated` | Создание Task | `id`, `projectId` или `crId`, `name` |

## 8. Зависимости от других доменов

### Входящие зависимости (этот домен зависит от...)

Project Management не имеет входящих зависимостей от других доменов системы.

### Исходящие зависимости (другие домены зависят от нас)

| Домен-потребитель | Что использует | Характер зависимости |
|-------------------|---------------|---------------------|
| **Timesheet** | Task (обязательная ссылка для Ticket: `taskId`) | Upstream: Timesheet читает Task из Project Management |
| **Reporting** | Project, CR, Task (группировка и фильтрация в отчётах) | Upstream: Reporting читает данные для агрегации |

**Важно:** внутренняя модель домена не должна быть напрямую доступна другим контекстам. Взаимодействие происходит через публичный API (контракт) домена.

## 9. Нефункциональные требования

| # | Требование |
|---|-----------|
| НФТ-П-01 | Время отклика API для операций чтения (Client List, Project List, Task List) не должно превышать 1 секунды при нормальной нагрузке. |
| НФТ-П-02 | Время отклика для операций записи (создание Client, Project, CR, Task) не должно превышать 2 секунд. |
| НФТ-П-05 | Список-запросы должны поддерживать пагинацию и не загружать в память более 1 000 записей за один запрос. |
| НФТ-Б-01 | Все операции выполняются только от имени аутентифицированного пользователя. |
| НФТ-Б-02 | Разграничение прав реализовано на уровне каждой операции согласно матрице доступа. |
| НФТ-Б-05 | Все входные данные проходят валидацию и санитизацию до передачи в доменный слой. |
| НФТ-Б-06 | Все административные операции (создание, удаление) логируются с указанием пользователя, действия, времени и результата. |
| НФТ-Н-01 | Атомарность операций: операция применяется полностью или откатывается без частичных изменений. |
| НФТ-Н-02 | Инварианты доменной модели соблюдаются при любых обстоятельствах. |
| НФТ-Р-01 | Публичная граница (API/контракт) чётко определена. Внутренняя модель недоступна другим контекстам напрямую. |
| НФТ-У-01 | Сообщения об ошибках валидации содержат явное указание на поле и причину ошибки. |
| НФТ-У-02 | API-ответы содержат наименования связанных сущностей, достаточные для UI без дополнительных запросов. |
| НФТ-У-03 | Пустые результаты фильтрации возвращаются как пустая коллекция, а не ошибка. |

## 1. Цель домена

Домен **Work Catalog** отвечает за управление тарифными ставками (Rate), функциональными ролями исполнителей (Role) и классификаторами вида работ (Work). Это upstream-контекст: он предоставляет справочные данные для тарификации Ticket в TimesheetContext.

**Ключевые обязанности:**
- Хранение и управление видами работ (Work) — классификатор деятельности.
- Хранение и управление функциональными ролями (Role) — специализация исполнителя.
- Хранение и управление тарифными ставками (Rate) — ставка в единицу времени, привязанная к Role и/или Work.
- Предоставление текущего значения Rate при создании Ticket (фиксация `rateSnapshot`).

**Чем домен не занимается:**
- Не хранит трудозатраты и не вычисляет итоговую стоимость работ.
- Не управляет назначением сотрудников на проекты.
- Не пересчитывает ранее зафиксированные `rateSnapshot` в Ticket.

## 2. Сущности и Value Objects

### 2.1 Work (Aggregate Root)

Классификатор вида выполняемой деятельности (например: Development, Consulting, Testing). Используется при вводе Ticket и группировке в отчётах.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование (уникальное в системе) |
| description | string | опционально | Описание вида работ |

**Ограничения:**
- `name` должен быть уникальным.
- Work не может быть удалена, если она используется в существующих Ticket.

---

### 2.2 Role (Aggregate Root)

Специализация исполнителя (например: Developer, QA, PM). Влияет на Rate при расчёте стоимости работ.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование (уникальное в системе) |
| description | string | опционально | Описание роли |

**Ограничения:**
- `name` должен быть уникальным.
- Role не может быть удалена, если к ней привязаны Rate или пользователи (User в IdentityContext).

---

### 2.3 Rate (Aggregate Root)

Тарифная ставка в единицу времени. Фиксируется в Ticket на момент его создания и не пересчитывается ретроспективно.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| amount | decimal | обязательно | Сумма ставки (строго > 0) |
| currency | string | обязательно | Валюта (например: USD, EUR, RUB) |
| effectiveFrom | date | обязательно | Дата вступления ставки в силу |
| roleId | UUID | опционально | Ссылка на Role |
| workId | UUID | опционально | Ссылка на Work |

**Ограничения:**
- `amount` должен быть строго положительным числом (> 0).
- `effectiveFrom` не может быть изменён после того, как Rate была применена хотя бы к одному Ticket.

## 3. Use Cases

### UC-WC-01: Создать Work

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin вводит уникальное наименование и опциональное описание Work.
2. Система проверяет уникальность наименования.
3. Система создаёт Work и публикует событие `WorkCreated`.

**Альтернативные сценарии:**
- 2a. Наименование не уникально → система отклоняет создание с сообщением о дубликате.

**Постусловия:** Work доступен в Work List и может быть указан при добавлении Ticket.

---

### UC-WC-02: Создать Role

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin вводит уникальное наименование и опциональное описание Role.
2. Система проверяет уникальность наименования.
3. Система создаёт Role и публикует событие `RoleCreated`.

**Альтернативные сценарии:**
- 2a. Наименование не уникально → система отклоняет создание с сообщением о дубликате.

**Постусловия:** Role доступна для назначения пользователям и привязки Rate.

---

### UC-WC-03: Создать Rate

**Актор:** Admin
**Предусловия:** Admin аутентифицирован. Существует хотя бы одна Role или Work (при необходимости привязки).

**Основной сценарий:**
1. Admin вводит сумму (> 0), валюту, дату вступления в силу (`effectiveFrom`).
2. Admin опционально выбирает Role и/или Work, к которым применяется ставка.
3. Система проверяет: `amount > 0`, `effectiveFrom` заполнен.
4. Система создаёт Rate и публикует событие `RateCreated`.

**Альтернативные сценарии:**
- 3a. `amount ≤ 0` → система отклоняет создание с сообщением об ошибке валидации.
- 3b. `effectiveFrom` не заполнен → система отклоняет создание.

**Постусловия:** Rate будет применяться к новым Ticket начиная с `effectiveFrom`.

---

### UC-WC-04: Изменить Rate

**Актор:** Admin
**Предусловия:** Rate существует.

**Основной сценарий:**
1. Admin выбирает Rate для изменения.
2. Admin вносит изменения в допустимые поля (например, `currency`, привязка к Role/Work).
3. Система сохраняет изменения.

**Альтернативные сценарии:**
- 2a. Admin пытается изменить `effectiveFrom` у Rate, применённой к хотя бы одному Ticket → система отклоняет изменение `effectiveFrom`.

**Постусловия:** Rate обновлена. `rateSnapshot` у существующих Ticket не пересчитывается.

---

### UC-WC-05: Удалить Work

**Актор:** Admin
**Предусловия:** Work существует.

**Основной сценарий:**
1. Admin инициирует удаление Work.
2. Система проверяет, что Work не используется в существующих Ticket.
3. Система удаляет Work.

**Альтернативные сценарии:**
- 2a. Work используется в хотя бы одном Ticket → система отклоняет удаление.

---

### UC-WC-06: Удалить Role

**Актор:** Admin
**Предусловия:** Role существует.

**Основной сценарий:**
1. Admin инициирует удаление Role.
2. Система проверяет отсутствие привязанных Rate и пользователей.
3. Система удаляет Role.

**Альтернативные сценарии:**
- 2a. К Role привязаны Rate или пользователи → система отклоняет удаление.

---

### UC-WC-07: Просмотр Work List

**Актор:** Admin, Manager, Employee
**Предусловия:** актор аутентифицирован.

**Основной сценарий:**
1. Актор открывает Work List.
2. Система возвращает полный список Work.

**Постусловия:** актор может выбрать Work при вводе Ticket или просмотреть доступные виды работ.

## 4. Бизнес-правила и инварианты

| # | Инвариант |
|---|-----------|
| ИН-08 | Rate фиксируется в момент создания Ticket (`rateSnapshot`) и не пересчитывается ретроспективно ни при редактировании Ticket, ни при изменении Rate. |
| ИН-09 | Дата вступления в силу (`effectiveFrom`) у Rate не может быть изменена после того, как Rate была применена хотя бы к одному Ticket. |
| ИН-10 | Сумма Rate (`amount`) должна быть строго положительным числом (> 0). |
| ИН-11 | Наименование Role должно быть уникальным. Role не может быть удалена, если к ней привязаны Rate или пользователи в IdentityContext. |
| ИН-12 | Наименование Work должно быть уникальным. Work не может быть удалена, если она использована в существующих Ticket. |

**Дополнительные правила валидации:**
- `name` у Work и Role не может быть пустой строкой.
- `currency` у Rate должна быть непустой строкой.

## 5. API-интерфейсы

Все операции требуют аутентификации. Все идентификаторы — UUID. Все операции с коллекциями поддерживают пагинацию.

### Work

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать Work | `name` (обязательно, уникально), `description` (опционально) | Созданный Work с `id` | Admin |
| Получить Work List | Без обязательных фильтров | Полный список Work | Admin, Manager, Employee |
| Удалить Work | `id` | Подтверждение или ошибка | Admin |

### Role

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать Role | `name` (обязательно, уникально), `description` (опционально) | Созданная Role с `id` | Admin |
| Получить Role List | Без обязательных фильтров | Список Role | Admin |
| Удалить Role | `id` | Подтверждение или ошибка | Admin |

### Rate

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать Rate | `amount` (> 0), `currency`, `effectiveFrom`, `roleId` (опционально), `workId` (опционально) | Созданная Rate с `id` | Admin |
| Получить Rate List | Фильтры: `roleId`, `workId` (опционально) | Список Rate | Admin |
| Изменить Rate | Допустимые поля (кроме `effectiveFrom`, если Rate применена к Ticket) | Обновлённая Rate | Admin |
| Удалить Rate | `id` | Подтверждение или ошибка | Admin |

**Требования к ошибкам:**
- Попытка изменить `effectiveFrom` у применённой Rate возвращает ошибку с явным указанием причины.
- Попытка удалить Work/Role, используемую в Ticket/Rate/User, возвращает ошибку с явным указанием причины.

## 6. Read Models

| Read Model | Описание | Фильтрация |
|------------|---------|------------|
| Work List | Полный список Work | Без обязательных фильтров |
| Role List | Список функциональных ролей | Без обязательных фильтров |
| Rate List | Список тарифных ставок | По `roleId`, по `workId` |

**Требование к ответам:** списки должны возвращать достаточно данных для построения UI без дополнительных запросов (наименования связанных Role/Work в Rate, а не только их идентификаторы).

## 7. Публикуемые события

| Событие | Триггер | Содержимое |
|---------|---------|------------|
| `WorkCreated` | Создание Work | `id`, `name` |
| `RoleCreated` | Создание Role | `id`, `name` |
| `RateCreated` | Создание Rate | `id`, `amount`, `currency`, `effectiveFrom`, `roleId`, `workId` |

## 8. Зависимости от других доменов

### Входящие зависимости (этот домен зависит от...)

Work Catalog не имеет входящих зависимостей от других доменов системы.

### Исходящие зависимости (другие домены зависят от нас)

| Домен-потребитель | Что использует | Характер зависимости |
|-------------------|---------------|---------------------|
| **Timesheet** | Rate (фиксация `rateSnapshot` при создании Ticket), Work (обязательный атрибут Ticket) | Upstream: Timesheet запрашивает актуальную Rate при создании Ticket |
| **Identity** | Role (опциональная ссылка `roleId` у User) | Upstream: Identity использует Role для профиля пользователя |
| **Reporting** | Work (группировка и фильтрация в Report) | Upstream: Reporting использует Work как измерение |

**Важно:** при проверке возможности удаления Role домен должен запрашивать IdentityContext для проверки наличия пользователей с данной Role; при проверке возможности удаления Work — TimesheetContext для проверки наличия Ticket с данным Work.

## 9. Нефункциональные требования

| # | Требование |
|---|-----------|
| НФТ-П-01 | Время отклика API для операций чтения (Work List, Role List, Rate List) не должно превышать 1 секунды. |
| НФТ-П-02 | Время отклика для операций записи не должно превышать 2 секунд. |
| НФТ-П-05 | Список-запросы поддерживают пагинацию и не загружают в память более 1 000 записей за один запрос. |
| НФТ-Б-01 | Все операции выполняются только от имени аутентифицированного пользователя. |
| НФТ-Б-02 | Разграничение прав реализовано на уровне каждой операции согласно матрице доступа. |
| НФТ-Б-05 | Все входные данные проходят валидацию и санитизацию до передачи в доменный слой. |
| НФТ-Б-06 | Административные операции логируются. |
| НФТ-Н-01 | Атомарность операций: операция применяется полностью или откатывается. |
| НФТ-Н-02 | Инварианты доменной модели соблюдаются при любых обстоятельствах. |
| НФТ-Н-03 | Значение `rateSnapshot` в Ticket неизменно после создания — никакие изменения Rate не влияют на него. |
| НФТ-Р-01 | Публичная граница (API/контракт) чётко определена. Внутренняя модель недоступна другим контекстам напрямую. |
| НФТ-У-01 | Сообщения об ошибках валидации содержат явное указание на поле и причину ошибки. |
| НФТ-У-03 | Пустые результаты фильтрации возвращаются как пустая коллекция, а не ошибка. |

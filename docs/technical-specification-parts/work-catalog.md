## 1. Цель домена

Домен **Work Catalog** отвечает за управление тарифными ставками (Rate), функциональными ролями исполнителей (Role) и классификаторами вида работ (Work). Это upstream-контекст: он предоставляет справочные данные для тарификации Ticket в TimesheetContext.

**Ключевые обязанности:**
- Хранение и управление видами работ (Work) — классификатор деятельности.
- Хранение и управление функциональными ролями (Role) — специализация исполнителя.
- Хранение и управление тарифными ставками (Rate) — ставка в единицу времени, привязанная к Role и/или Work.
- Предоставление текущего значения Rate при создании Ticket (фиксация `rateSnapshot`).

**Чем домен не занимается:**
- Не хранит трудозатраты и не вычисляет итоговую стоимость работ.
- Не управляет назначением сотрудников на проекты.
- Не пересчитывает ранее зафиксированные `rateSnapshot` в Ticket.

## 2. Сущности и Value Objects

### 2.1 Work (Aggregate Root)

Классификатор вида выполняемой деятельности (например: Development, Consulting, Testing). Используется при вводе Ticket и группировке в отчётах.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование (уникальное в системе) |
| description | string | опционально | Описание вида работ |

**Дополнительные атрибуты (служебные):**

| Атрибут | Тип | Описание |
|---------|-----|---------|
| deletedAt | datetime\|null | Дата и время мягкого удаления; `null` — запись активна |

**Ограничения:**
- `name` должен быть уникальным среди активных (не удалённых) записей. Если Work была удалена (soft-delete), её имя может быть повторно использовано при создании новой Work.
- Work не может быть помечена удалённой, если она используется в существующих Ticket.
- Удаление Work выполняется через Soft-delete: запись не удаляется физически из базы данных, поле `deletedAt` устанавливается в текущий момент времени.
- Soft-deleted Work не отображается в Work List и недоступна для выбора при добавлении Ticket.

---

### 2.2 Role (Aggregate Root)

Специализация исполнителя (например: Developer, QA, PM). Влияет на Rate при расчёте стоимости работ.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование (уникальное в системе) |
| description | string | опционально | Описание роли |

**Дополнительные атрибуты (служебные):**

| Атрибут | Тип | Описание |
|---------|-----|---------|
| deletedAt | datetime\|null | Дата и время мягкого удаления; `null` — запись активна |

**Ограничения:**
- `name` должен быть уникальным среди активных (не удалённых) записей. Если Role была удалена (soft-delete), её имя может быть повторно использовано при создании новой Role.
- Role не может быть помечена удалённой, если к ней привязаны активные Rate или пользователи (User в IdentityContext).
- Удаление Role выполняется через Soft-delete: запись не удаляется физически из базы данных, поле `deletedAt` устанавливается в текущий момент времени.
- Soft-deleted Role не отображается в Role List и недоступна для выбора при создании Rate или назначении пользователям.

---

### 2.3 Rate (Aggregate Root)

Тарифная ставка в единицу времени. Фиксируется в Ticket на момент его создания и не пересчитывается ретроспективно.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| amount | string | обязательно | Сумма ставки (строго > 0); передаётся как строка для точности; хранится как `decimal(12,2)` в БД |
| currency | string | обязательно | Валюта (например: USD, EUR, RUB); непустая строка длиной ровно 3 символа (совместимо с ISO 4217) |
| effectiveFrom | date | обязательно | Дата вступления ставки в силу |
| roleId | UUID | опционально | Ссылка на Role (должна быть заполнена, если `workId` не указан) |
| workId | UUID | опционально | Ссылка на Work (должна быть заполнена, если `roleId` не указан) |

**Дополнительные атрибуты (служебные):**

| Атрибут | Тип | Описание |
|---------|-----|---------|
| deletedAt | datetime\|null | Дата и время мягкого удаления; `null` — запись активна |

**Ограничения:**
- `amount` должен быть строго положительным числом (> 0).
- Rate должна быть привязана хотя бы к одному из полей: `roleId` или `workId`. Создание Rate без привязки ни к Role, ни к Work не допускается.
- `effectiveFrom` не может быть изменён после того, как Rate была применена хотя бы к одному Ticket.
- Удаление Rate выполняется через Soft-delete: запись не удаляется физически из базы данных, поле `deletedAt` устанавливается в текущий момент времени. Зафиксированные `rateSnapshot` в Ticket сохраняются без изменений.
- Soft-deleted Rate не отображается в Rate List и не применяется к новым Ticket.

## 3. Use Cases

### UC-WC-01: Создать Work

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin вводит уникальное наименование и опциональное описание Work.
2. Система проверяет уникальность наименования.
3. Система создаёт Work и публикует событие `WorkCreated`.

**Альтернативные сценарии:**
- 2a. Наименование не уникально → система отклоняет создание с сообщением о дубликате.

**Постусловия:** Work доступен в Work List и может быть указан при добавлении Ticket.

---

### UC-WC-02: Создать Role

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin вводит уникальное наименование и опциональное описание Role.
2. Система проверяет уникальность наименования.
3. Система создаёт Role и публикует событие `RoleCreated`.

**Альтернативные сценарии:**
- 2a. Наименование не уникально → система отклоняет создание с сообщением о дубликате.

**Постусловия:** Role доступна для назначения пользователям и привязки Rate.

---

### UC-WC-03: Создать Rate

**Актор:** Admin
**Предусловия:** Admin аутентифицирован. Существует хотя бы одна активная Role или активная Work.

**Основной сценарий:**
1. Admin вводит сумму (> 0), валюту (3 символа), дату вступления в силу (`effectiveFrom`).
2. Admin выбирает Role и/или Work, к которым применяется ставка (хотя бы одно из двух обязательно).
3. Система проверяет: `amount > 0`, `effectiveFrom` заполнен, указан хотя бы один из `roleId` или `workId`.
4. Система создаёт Rate и публикует событие `RateCreated`.

**Альтернативные сценарии:**
- 3a. `amount ≤ 0` → система отклоняет создание с сообщением об ошибке валидации.
- 3b. `effectiveFrom` не заполнен → система отклоняет создание.
- 3c. Ни `roleId`, ни `workId` не указаны → система отклоняет создание с сообщением о необходимости указать привязку.

**Постусловия:** Rate будет применяться к новым Ticket начиная с `effectiveFrom`.

---

### UC-WC-04: Изменить Rate

**Актор:** Admin
**Предусловия:** Rate существует.

**Основной сценарий:**
1. Admin выбирает Rate для изменения.
2. Admin вносит изменения в допустимые поля: `amount`, `currency`, `effectiveFrom`, `roleId`, `workId`.
3. Система проверяет, что после обновления хотя бы один из `roleId` или `workId` остаётся заполненным.
4. Система сохраняет изменения и публикует событие `RateUpdated`.

**Альтернативные сценарии:**
- 3a. Admin пытается изменить `effectiveFrom` у Rate, применённой к хотя бы одному Ticket, и новое значение отличается от текущего → система отклоняет изменение с ошибкой `RateEffectiveFromImmutableException`. Если передаётся то же самое значение `effectiveFrom`, что уже хранится у Rate, запрос считается допустимым (значение фактически не изменилось).
- 3b. После обновления ни `roleId`, ни `workId` не будут заполнены → система отклоняет изменение с сообщением о необходимости указать привязку.

**Постусловия:** Rate обновлена. `rateSnapshot` у существующих Ticket не пересчитывается.

---

### UC-WC-05: Удалить Work (Soft-delete)

**Актор:** Admin
**Предусловия:** Work существует и не помечена удалённой.

**Основной сценарий:**
1. Admin инициирует удаление Work.
2. Система проверяет, что Work не используется в существующих Ticket.
3. Система помечает Work удалённой: устанавливает `deletedAt` = текущее время. Данные физически не удаляются.
4. Soft-deleted Work исчезает из Work List.

**Альтернативные сценарии:**
- 2a. Work используется в хотя бы одном Ticket → система отклоняет удаление с явным сообщением.

---

### UC-WC-06: Удалить Role (Soft-delete)

**Актор:** Admin
**Предусловия:** Role существует и не помечена удалённой.

**Основной сценарий:**
1. Admin инициирует удаление Role.
2. Система проверяет отсутствие привязанных активных Rate и пользователей (запрос к IdentityContext).
3. Система помечает Role удалённой: устанавливает `deletedAt` = текущее время. Данные физически не удаляются.
4. Soft-deleted Role исчезает из Role List.

**Альтернативные сценарии:**
- 2a. К Role привязаны активные Rate или пользователи → система отклоняет удаление с явным сообщением. Каскадный soft-delete не предусмотрен: Admin должен сначала удалить все привязанные активные Rate, а затем удалить Role.

---

### UC-WC-07: Удалить Rate (Soft-delete)

**Актор:** Admin
**Предусловия:** Rate существует и не помечена удалённой.

**Основной сценарий:**
1. Admin инициирует удаление Rate.
2. Система помечает Rate удалённой: устанавливает `deletedAt` = текущее время. Данные физически не удаляются.
3. Soft-deleted Rate исчезает из Rate List и перестаёт применяться к новым Ticket.
4. Ранее зафиксированные `rateSnapshot` в Ticket остаются без изменений.

## 4. Бизнес-правила и инварианты

| # | Инвариант |
|---|-----------|
| ИН-08 | Rate фиксируется в момент создания Ticket (`rateSnapshot`) и не пересчитывается ретроспективно ни при редактировании Ticket, ни при изменении Rate. |
| ИН-09 | Дата вступления в силу (`effectiveFrom`) у Rate не может быть изменена после того, как Rate была применена хотя бы к одному Ticket. |
| ИН-10 | Сумма Rate (`amount`) должна быть строго положительным числом (> 0). Rate должна быть привязана хотя бы к одному из полей: `roleId` или `workId`. Rate без привязки ни к Role, ни к Work не допускается. |
| ИН-11 | Наименование Role должно быть уникальным среди активных (не удалённых) записей. Role не может быть помечена удалённой (Soft-delete), если к ней привязаны активные Rate или пользователи в IdentityContext. Физического удаления записи Role из базы данных не происходит. |
| ИН-12 | Наименование Work должно быть уникальным среди активных (не удалённых) записей. Work не может быть помечена удалённой (Soft-delete), если она использована в существующих Ticket. Физического удаления записи Work из базы данных не происходит. |

**Дополнительные правила валидации:**
- `name` у Work и Role не может быть пустой строкой.
- `currency` у Rate должна быть непустой строкой длиной ровно 3 символа (совместимо с ISO 4217). Валидация формата выполняется на уровне Request DTO.
- `amount` у Rate передаётся через API как строка, представляющая десятичное число. Валидация формата строки выполняется на уровне Request DTO.

## 5. API-интерфейсы

Все операции требуют аутентификации. Все идентификаторы — UUID. Все операции с коллекциями поддерживают пагинацию.

### Work

| Операция | Метод и путь | Входные данные | Выходные данные | Права |
|----------|-------------|----------------|----------------|-------|
| Создать Work | POST `/work-catalog/works` | `name` (обязательно, уникально среди активных), `description` (опционально) | Созданный Work с `id` | Admin |
| Получить Work List | GET `/work-catalog/works` | Без обязательных фильтров | Полный список Work | Admin, Manager, Employee |
| Получить Work по ID | GET `/work-catalog/works/{id}` | `id` | Work или ошибка 404 | Admin, Manager, Employee |
| Обновить Work | PUT `/work-catalog/works/{id}` | `name` (уникально среди активных), `description` (опционально) | Обновлённый Work | Admin |
| Удалить Work (Soft-delete) | DELETE `/work-catalog/works/{id}` | `id` | Подтверждение или ошибка | Admin |

### Role

| Операция | Метод и путь | Входные данные | Выходные данные | Права |
|----------|-------------|----------------|----------------|-------|
| Создать Role | POST `/work-catalog/roles` | `name` (обязательно, уникально среди активных), `description` (опционально) | Созданная Role с `id` | Admin |
| Получить Role List | GET `/work-catalog/roles` | Без обязательных фильтров | Список Role | Admin, Manager, Employee |
| Получить Role по ID | GET `/work-catalog/roles/{id}` | `id` | Role или ошибка 404 | Admin, Manager, Employee |
| Обновить Role | PUT `/work-catalog/roles/{id}` | `name` (уникально среди активных), `description` (опционально) | Обновлённая Role | Admin |
| Удалить Role (Soft-delete) | DELETE `/work-catalog/roles/{id}` | `id` | Подтверждение или ошибка | Admin |

### Rate

| Операция | Метод и путь | Входные данные | Выходные данные | Права |
|----------|-------------|----------------|----------------|-------|
| Создать Rate | POST `/work-catalog/rates` | `amount` (строка, > 0), `currency` (3 символа), `effectiveFrom`, `roleId` (опционально), `workId` (опционально) | Созданная Rate с `id` | Admin |
| Получить Rate List | GET `/work-catalog/rates` | Фильтры: `roleId`, `workId` (опционально) | Список Rate | Admin |
| Получить Rate по ID | GET `/work-catalog/rates/{id}` | `id` | Rate или ошибка 404 | Admin |
| Изменить Rate | PUT `/work-catalog/rates/{id}` | `amount`, `currency`, `effectiveFrom` (запрещено изменять, если Rate применена к Ticket, допустимо передать то же значение), `roleId` (опционально), `workId` (опционально) | Обновлённая Rate | Admin |
| Удалить Rate (Soft-delete) | DELETE `/work-catalog/rates/{id}` | `id` | Подтверждение или ошибка | Admin |

**Требования к ошибкам:**
- Попытка изменить `effectiveFrom` у применённой Rate возвращает ошибку с явным указанием причины.
- Попытка выполнить Soft-delete Work, используемой в Ticket, возвращает ошибку с явным указанием причины.
- Попытка выполнить Soft-delete Role, привязанной к активным Rate или пользователям, возвращает ошибку с явным указанием причины.

## 6. Read Models

| Read Model | Описание | Фильтрация | Права доступа |
|------------|---------|------------|---------------|
| Work List | Список активных (не удалённых) Work | Без обязательных фильтров | Admin, Manager, Employee |
| Work (по ID) | Одна активная Work по идентификатору | По `id` | Admin, Manager, Employee |
| Role List | Список активных (не удалённых) функциональных ролей | Без обязательных фильтров | Admin, Manager, Employee |
| Role (по ID) | Одна активная Role по идентификатору | По `id` | Admin, Manager, Employee |
| Rate List | Список активных (не удалённых) тарифных ставок | По `roleId`, по `workId` | Admin |
| Rate (по ID) | Одна активная Rate по идентификатору | По `id` | Admin |

**Требование к ответам:** списки должны возвращать достаточно данных для построения UI без дополнительных запросов (наименования связанных Role/Work в Rate, а не только их идентификаторы).

| Событие | Триггер | Содержимое |

## 8. Зависимости от других доменов

### Входящие зависимости (этот домен зависит от...)

Work Catalog не имеет входящих зависимостей от других доменов системы.

### Исходящие зависимости (другие домены зависят от нас)

| Домен-потребитель | Что использует | Характер зависимости |
|-------------------|---------------|---------------------|
| **Timesheet** | Rate (фиксация `rateSnapshot` при создании Ticket), Work (обязательный атрибут Ticket) | Upstream: Timesheet запрашивает актуальную Rate при создании Ticket |
| **Identity** | Role (опциональная ссылка `roleId` у User) | Upstream: Identity использует Role для профиля пользователя |
| **Reporting** | Work (группировка и фильтрация в Report) | Upstream: Reporting использует Work как измерение |

**Важно:** при проверке возможности удаления Role домен должен запрашивать IdentityContext для проверки наличия пользователей с данной Role; при проверке возможности удаления Work — TimesheetContext для проверки наличия Ticket с данным Work.

## 9. Нефункциональные требования

| # | Требование |
|---|-----------|
| НФТ-П-01 | Время отклика API для операций чтения (Work List, Role List, Rate List) не должно превышать 1 секунды. |
| НФТ-П-02 | Время отклика для операций записи не должно превышать 2 секунд. |
| НФТ-П-05 | Список-запросы поддерживают пагинацию и не загружают в память более 1 000 записей за один запрос. |
| НФТ-Б-01 | Все операции выполняются только от имени аутентифицированного пользователя. |
| НФТ-Б-02 | Разграничение прав реализовано на уровне каждой операции согласно матрице доступа. |
| НФТ-Б-05 | Все входные данные проходят валидацию и санитизацию до передачи в доменный слой. |
| НФТ-Б-06 | Административные операции логируются. |
| НФТ-Н-01 | Атомарность операций: операция применяется полностью или откатывается. |
| НФТ-Н-02 | Инварианты доменной модели соблюдаются при любых обстоятельствах. |
| НФТ-Н-03 | Значение `rateSnapshot` в Ticket неизменно после создания — никакие изменения Rate не влияют на него. |
| НФТ-Р-01 | Публичная граница (API/контракт) чётко определена. Внутренняя модель недоступна другим контекстам напрямую. |
| НФТ-У-01 | Сообщения об ошибках валидации содержат явное указание на поле и причину ошибки. |
| НФТ-У-03 | Пустые результаты фильтрации возвращаются как пустая коллекция, а не ошибка. |

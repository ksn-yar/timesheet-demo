## 1. Цель домена

Домен **Identity** отвечает за управление пользователями системы (User) и организационными единицами (Group). Это upstream-контекст: он предоставляет информацию о том, кто имеет доступ к системе и с какими правами.

**Ключевые обязанности:**
- Хранение и управление учётными записями пользователей (User).
- Хранение и управление организационными группами (Group).
- Назначение пользователей в группы.
- Управление системными ролями пользователей (Admin, Manager, Employee).
- Деактивация пользователей без потери исторических данных.
- Аутентификация пользователей при входе в систему.

**Чем домен не занимается:**
- Не хранит трудозатраты.
- Не управляет тарификацией (тарифные роли Role — из WorkCatalogContext).
- Не определяет структуру проектов.

## 2. Сущности и Value Objects

### 2.1 User (Aggregate Root)

Физическое лицо, имеющее доступ к системе.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Полное имя пользователя |
| email | string | обязательно | Email — уникальный логин для входа в систему |
| systemRole | enum | обязательно | Системная роль: `Admin`, `Manager`, `Employee` |
| groupId | UUID | опционально | Ссылка на Group |
| roleId | UUID | опционально | Ссылка на функциональную Role из WorkCatalogContext |
| isActive | boolean | обязательно | Признак активности учётной записи (по умолчанию `true` при создании) |

**Допустимые значения `systemRole`:** `Admin`, `Manager`, `Employee`.

**Ограничения:**
- `email` должен быть уникальным в системе.
- User не может быть удалён физически, если к нему привязаны Ticket. Допускается только деактивация (`isActive = false`).
- Пароль хранится в виде хэша с солью, никогда не в открытом виде.

---

### 2.2 Group (Aggregate Root)

Организационная единица, объединяющая User. Используется для разграничения доступа и группировки данных в отчётах.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование (уникальное в системе) |
| description | string | опционально | Описание группы |

**Ограничения:**
- `name` должен быть уникальным.
- Group не может быть удалена, если в ней состоят активные User.

## 3. Use Cases

### UC-ID-01: Создать User

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin вводит имя, уникальный email, системную роль (`Admin`, `Manager`, `Employee`).
2. Admin опционально выбирает Group и функциональную Role (из WorkCatalogContext).
3. Система проверяет уникальность email.
4. Система создаёт User (`isActive = true`) и публикует событие `UserCreated`.
5. User отображается в User List.

**Альтернативные сценарии:**
- 3a. Email уже существует в системе → система отклоняет создание с сообщением о дубликате.

**Постусловия:** User может войти в систему и выполнять действия согласно своей системной роли.

---

### UC-ID-02: Создать Group

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin вводит уникальное наименование и опциональное описание Group.
2. Система проверяет уникальность наименования.
3. Система создаёт Group и публикует событие `GroupCreated`.

**Альтернативные сценарии:**
- 2a. Наименование не уникально → система отклоняет создание с сообщением о дубликате.

**Постусловия:** Group доступна для назначения User и фильтрации в отчётах.

---

### UC-ID-03: Назначить User в Group

**Актор:** Admin
**Предусловия:** существуют User и Group.

**Основной сценарий:**
1. Admin выбирает User из User List.
2. Admin выбирает Group.
3. Система обновляет `groupId` у User и публикует событие `UserAssignedToGroup`.

**Постусловия:** Ticket данного User учитываются при групповой фильтрации в Reporting.

---

### UC-ID-04: Деактивировать User

**Актор:** Admin
**Предусловия:** User существует и имеет `isActive = true`.

**Основной сценарий:**
1. Admin выбирает User из User List.
2. Admin инициирует деактивацию.
3. Система информирует Admin, что исторические данные будут сохранены.
4. Система устанавливает `isActive = false` и публикует событие `UserDeactivated`.

**Альтернативные сценарии:**
- 2a. Admin пытается физически удалить User, к которому привязаны Ticket → система отклоняет удаление и предлагает деактивацию.

**Постусловия:** User теряет доступ к системе; исторические Ticket и данные в отчётах сохраняются в неизменном виде.

---

### UC-ID-05: Просмотр User List

**Актор:** Admin, Manager
**Предусловия:** актор аутентифицирован.

**Основной сценарий:**
1. Актор открывает User List.
2. Актор опционально применяет фильтры по Group, функциональной Role или статусу активности (`isActive`).
3. Система возвращает отфильтрованный список User.

**Постусловия:** актор видит актуальный список пользователей.

---

### UC-ID-06: Удалить User

**Актор:** Admin
**Предусловия:** User существует.

**Основной сценарий:**
1. Admin инициирует удаление User.
2. Система проверяет наличие привязанных Ticket.
3. Если Ticket нет — система удаляет User.

**Альтернативные сценарии:**
- 2a. К User привязаны Ticket → система отклоняет физическое удаление и предлагает деактивацию.

---

### UC-ID-07: Изменить принадлежность User к Group

**Актор:** Admin
**Предусловия:** User существует.

**Основной сценарий:**
1. Admin выбирает User.
2. Admin выбирает новую Group или снимает привязку.
3. Система обновляет `groupId` у User.

**Постусловия:** принадлежность User к Group изменена.

## 4. Бизнес-правила и инварианты

| # | Инвариант |
|---|-----------|
| ИН-13 | Employee может добавлять Ticket только за себя. (Контроль на стороне TimesheetContext, но IdentityContext обеспечивает корректность идентификации актора.) |
| ИН-16 | User не может быть удалён физически, если к нему привязаны Ticket. Допускается только деактивация (`isActive = false`). |
| ИН-17 | Email пользователя должен быть уникальным в системе. |

**Дополнительные бизнес-правила:**

| # | Правило |
|---|---------|
| БП-01 | Наименование Group должно быть уникальным. |
| БП-02 | Group не может быть удалена, если в ней состоят активные User. |

**Правила безопасности:**
- Пароли не хранятся в открытом виде. Применяется надёжное хэширование с солью.
- `isActive = false` — единственный способ ограничить доступ User, если к нему привязаны Ticket.
- Системная роль User определяет всю матрицу доступа в системе.

## 5. API-интерфейсы

Все операции требуют аутентификации. Все идентификаторы — UUID. Все операции с коллекциями поддерживают пагинацию.

### User

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать User | `name`, `email` (уникальный), `systemRole`, `groupId` (опционально), `roleId` (опционально) | Созданный User с `id` | Admin |
| Получить User List | Фильтры: `groupId`, `roleId`, `isActive` (опционально) | Список User с пагинацией | Admin, Manager |
| Деактивировать User | `userId` | Обновлённый User (`isActive = false`) | Admin |
| Назначить User в Group | `userId`, `groupId` | Обновлённый User | Admin |
| Удалить User | `userId` | Подтверждение или ошибка (если есть Ticket) | Admin |

### Group

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать Group | `name` (уникальное), `description` (опционально) | Созданная Group с `id` | Admin |
| Получить Group List | Без обязательных фильтров | Список Group | Admin, Manager |
| Удалить Group | `id` | Подтверждение или ошибка | Admin |

**Требования к ошибкам:**
- Попытка создать User с уже существующим email → ошибка с явным указанием поля.
- Попытка физически удалить User с Ticket → ошибка с предложением деактивации.
- Попытка удалить Group с активными User → ошибка с явным указанием причины.
- Попытка выполнить операцию без необходимых прав → ошибка авторизации.

## 6. Read Models

| Read Model | Описание | Фильтрация |
|------------|---------|------------|
| User List | Список пользователей с атрибутами | По `groupId`, по `roleId`, по `isActive` |
| Group List | Список организационных групп | Без обязательных фильтров |

**Требование к ответам:** User List должен возвращать наименования связанных Group и Role (а не только идентификаторы) для построения UI без дополнительных запросов.

## 7. Публикуемые события

| Событие | Триггер | Содержимое |
|---------|---------|------------|
| `UserCreated` | Создание User | `id`, `name`, `email`, `systemRole` |
| `GroupCreated` | Создание Group | `id`, `name` |
| `UserAssignedToGroup` | Назначение User в Group | `userId`, `groupId` |
| `UserDeactivated` | Деактивация User | `userId` |

## 8. Зависимости от других доменов

### Входящие зависимости (этот домен зависит от...)

| Домен-поставщик | Что используется | Характер зависимости |
|-----------------|-----------------|---------------------|
| **Work Catalog** | Role (опциональная ссылка `roleId` у User) | Downstream: Identity использует Role из WorkCatalog для профиля пользователя |

### Исходящие зависимости (другие домены зависят от нас)

| Домен-потребитель | Что использует | Характер зависимости |
|-------------------|---------------|---------------------|
| **Timesheet** | User (Employee — обязательный атрибут Ticket: `employeeId`) | Upstream: Timesheet идентифицирует исполнителя по User из Identity |
| **Reporting** | User, Group (фильтрация и группировка в Report) | Upstream: Reporting использует User и Group как измерения |

**Проверка при удалении User:** домен должен запрашивать TimesheetContext для проверки наличия Ticket с данным `employeeId`.

**Проверка при удалении Role:** WorkCatalogContext запрашивает IdentityContext для проверки, есть ли пользователи с данной `roleId`.

## 9. Нефункциональные требования

| # | Требование |
|---|-----------|
| НФТ-П-01 | Время отклика API для операций чтения (User List, Group List) не должно превышать 1 секунды. |
| НФТ-П-02 | Время отклика для операций записи не должно превышать 2 секунд. |
| НФТ-П-05 | Список-запросы поддерживают пагинацию и не загружают в память более 1 000 записей за один запрос. |
| НФТ-Б-01 | Все операции выполняются только от имени аутентифицированного пользователя. |
| НФТ-Б-02 | Разграничение прав реализовано на уровне каждой операции согласно матрице доступа. |
| НФТ-Б-03 | Employee не должен иметь возможности получить данные Ticket, принадлежащих другим сотрудникам (контроль совместно с TimesheetContext). |
| НФТ-Б-04 | Пароли пользователей не хранятся в открытом виде. Применяется надёжное хэширование с солью. |
| НФТ-Б-05 | Все входные данные проходят валидацию и санитизацию до передачи в доменный слой. |
| НФТ-Б-06 | Административные операции (создание/деактивация/удаление User, создание Group) логируются с указанием пользователя, действия, времени и результата. |
| НФТ-Н-01 | Атомарность операций: операция применяется полностью или откатывается. |
| НФТ-Н-02 | Инварианты доменной модели соблюдаются при любых обстоятельствах. |
| НФТ-Р-01 | Публичная граница (API/контракт) чётко определена. Внутренняя модель недоступна другим контекстам напрямую. |
| НФТ-У-01 | Сообщения об ошибках валидации содержат явное указание на поле и причину ошибки. |
| НФТ-У-02 | API-ответы содержат достаточно информации для UI без дополнительных запросов. |
| НФТ-У-03 | Пустые результаты фильтрации возвращаются как пустая коллекция, а не ошибка. |
| НФТ-У-04 | При деактивации User система явно информирует, что исторические данные будут сохранены. |

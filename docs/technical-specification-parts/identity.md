## 1. Цель домена

Домен **Identity** отвечает за управление пользователями системы (User) и организационными единицами (Group). Это upstream-контекст: он предоставляет информацию о том, кто имеет доступ к системе и с какими правами.

**Ключевые обязанности:**
- Хранение и управление учётными записями пользователей (User).
- Хранение и управление организационными группами (Group).
- Назначение пользователей в группы.
- Управление системными ролями пользователей (Admin, Manager, Employee).
- Деактивация пользователей без потери исторических данных.
- Аутентификация пользователей при входе в систему (сессионная аутентификация по логину и паролю).

**Чем домен не занимается:**
- Не хранит трудозатраты.
- Не управляет тарификацией (тарифные роли Role — из WorkCatalogContext).
- Не определяет структуру проектов.

## 2. Сущности и Value Objects

### 2.1 User (Aggregate Root)

Физическое лицо, имеющее доступ к системе.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Полное имя пользователя |
| email | string | обязательно | Email — уникальный логин для входа в систему |
| passwordHash | string | обязательно | Хэш пароля с солью; при создании User Admin задаёт пароль, который хэшируется через `PasswordHasherInterface`; в ответе API не возвращается |
| systemRole | enum | обязательно | Системная роль: `Admin`, `Manager`, `Employee` |
| groupId | UUID | опционально | Ссылка на Group |
| roleId | UUID | опционально | Ссылка на функциональную Role из WorkCatalogContext; хранится как UUID без валидации существования в WorkCatalog (валидация будет добавлена после реализации WorkCatalog через порт ACL) |
| isActive | boolean | обязательно | Признак активности учётной записи (по умолчанию `true` при создании) |

**Допустимые значения `systemRole`:** `Admin`, `Manager`, `Employee`.

**Дополнительные атрибуты (служебные):**

| Атрибут | Тип | Описание |
|---------|-----|---------|
| deletedAt | datetime\|null | Дата и время мягкого удаления; `null` — запись активна |

**Ограничения:**
- `email` должен быть уникальным в системе.
- `email` является логином и не может быть изменён после создания User.
- User не может быть удалён физически. Удаление выполняется через Soft-delete: поле `deletedAt` устанавливается в текущий момент времени. Если к User привязаны Ticket — Soft-delete недоступен; допускается только деактивация (`isActive = false`).
- Soft-deleted User не отображается в User List и не может войти в систему.
- Пароль хранится в виде хэша с солью, никогда не в открытом виде.
- `groupId` изменяется только через UC-ID-03 (ChangeUserGroup).

---

### 2.2 Group (Aggregate Root)

Организационная единица, объединяющая User. Используется для разграничения доступа и группировки данных в отчётах.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование (уникальное в системе) |
| description | string | опционально | Описание группы |

**Дополнительные атрибуты (служебные):**

| Атрибут | Тип | Описание |
|---------|-----|---------|
| deletedAt | datetime\|null | Дата и время мягкого удаления; `null` — запись активна |

**Ограничения:**
- `name` должен быть уникальным.
- Group не может быть помечена удалённой, если в ней состоят активные User.
- Удаление Group выполняется через Soft-delete: запись не удаляется физически из базы данных, поле `deletedAt` устанавливается в текущий момент времени.
- Soft-deleted Group не отображается в Group List и недоступна для назначения User.

## 3. Use Cases

### UC-ID-01: Создать User

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin вводит имя, уникальный email, пароль, системную роль (`Admin`, `Manager`, `Employee`).
2. Admin опционально выбирает Group и функциональную Role (из WorkCatalogContext).
3. Система проверяет уникальность email.
4. Система хэширует пароль через `PasswordHasherInterface`.
5. Система создаёт User (`isActive = true`) и публикует событие `UserCreated`.
6. User отображается в User List.

**Альтернативные сценарии:**
- 3a. Email уже существует в системе → система отклоняет создание с сообщением о дубликате.

**Постусловия:** User может войти в систему и выполнять действия согласно своей системной роли.

---

### UC-ID-02: Создать Group

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin вводит уникальное наименование и опциональное описание Group.
2. Система проверяет уникальность наименования.
3. Система создаёт Group и публикует событие `GroupCreated`.

**Альтернативные сценарии:**
- 2a. Наименование не уникально → система отклоняет создание с сообщением о дубликате.

**Постусловия:** Group доступна для назначения User и фильтрации в отчётах.

---

### UC-ID-03: Изменить принадлежность User к Group

**Актор:** Admin
**Предусловия:** User существует.

**Основной сценарий:**
1. Admin выбирает User.
2. Admin выбирает новую Group или снимает привязку (`groupId = null`).
3. Система обновляет `groupId` у User.
4. Если `groupId` установлен — система публикует событие `UserAssignedToGroup`.
5. Если `groupId` снят (`null`) — система публикует событие `UserRemovedFromGroup`.

**Альтернативные сценарии:**
- 2a. Выбранная Group помечена удалённой → система отклоняет операцию.

**Постусловия:** принадлежность User к Group изменена или снята.

---

### UC-ID-04: Деактивировать User

**Актор:** Admin
**Предусловия:** User существует и имеет `isActive = true`.

**Основной сценарий:**
1. Admin выбирает User из User List.
2. Admin инициирует деактивацию.
3. Система информирует Admin, что исторические данные будут сохранены.
4. Система устанавливает `isActive = false` и публикует событие `UserDeactivated`.

**Альтернативные сценарии:**
- 2a. Admin пытается удалить (Soft-delete) User, к которому привязаны Ticket → система отклоняет Soft-delete и предлагает деактивацию.

**Постусловия:** User теряет доступ к системе; исторические Ticket и данные в отчётах сохраняются в неизменном виде.

---

### UC-ID-05: Просмотр User List

**Актор:** Admin, Manager
**Предусловия:** актор аутентифицирован.

**Основной сценарий:**
1. Актор открывает User List.
2. Актор опционально применяет фильтры по Group, функциональной Role или статусу активности (`isActive`).
3. Система возвращает отфильтрованный список User.

**Постусловия:** актор видит актуальный список пользователей.

---

### UC-ID-06: Удалить User (Soft-delete)

**Актор:** Admin
**Предусловия:** User существует и не помечен удалённым.

**Основной сценарий:**
1. Admin инициирует удаление User.
2. Система проверяет наличие привязанных Ticket (запрос к TimesheetContext через Persistence).
3. Если Ticket нет — система помечает User удалённым: устанавливает `deletedAt` = текущее время. Данные физически не удаляются.
4. Система публикует событие `UserDeleted`.
5. Soft-deleted User исчезает из User List и теряет доступ к системе.

**Альтернативные сценарии:**
- 2a. К User привязаны Ticket → система отклоняет Soft-delete и предлагает деактивацию (`isActive = false`) для сохранения исторических данных.

---

### UC-ID-07: Удалить Group (Soft-delete)

**Актор:** Admin
**Предусловия:** Group существует и не помечена удалённой.

**Основной сценарий:**
1. Admin инициирует удаление Group.
2. Система проверяет отсутствие активных User в данной Group.
3. Система помечает Group удалённой: устанавливает `deletedAt` = текущее время. Данные физически не удаляются.
4. Система публикует событие `GroupDeleted`.
5. Soft-deleted Group исчезает из Group List.

**Альтернативные сценарии:**
- 2a. В Group состоят активные User → система отклоняет удаление с явным сообщением.

---

### UC-ID-08: Обновить User

**Актор:** Admin
**Предусловия:** User существует и не помечен удалённым.

**Основной сценарий:**
1. Admin выбирает User из User List.
2. Admin изменяет одно или несколько из следующих полей: `name`, `systemRole`, `roleId`.
3. Система проверяет формат UUID для `roleId` (если передан).
4. Система сохраняет изменения и публикует событие `UserUpdated`.

**Альтернативные сценарии:**
- 2a. Admin пытается изменить `email` → система отклоняет операцию (email является логином и неизменяем).
- 2b. `roleId` передан в некорректном формате → система отклоняет операцию с указанием причины.

**Постусловия:** атрибуты User обновлены.

---

### UC-ID-09: Обновить Group

**Актор:** Admin
**Предусловия:** Group существует и не помечена удалённой.

**Основной сценарий:**
1. Admin выбирает Group из Group List.
2. Admin изменяет одно или несколько из следующих полей: `name`, `description`.
3. Система проверяет уникальность `name` (если изменяется).
4. Система сохраняет изменения и публикует событие `GroupUpdated`.

**Альтернативные сценарии:**
- 3a. Новое `name` не уникально → система отклоняет операцию с сообщением о дубликате.

**Постусловия:** атрибуты Group обновлены.

**Дополнительно:** явный `null` для `description` очищает значение поля.

---

### UC-ID-10: Войти в систему (Login)

**Актор:** Любой пользователь (не аутентифицированный)
**Предусловия:** User существует, имеет `isActive = true` и не помечен удалённым.

**Основной сценарий:**
1. Пользователь вводит email и пароль.
2. Система находит User по email.
3. Система проверяет пароль через `PasswordHasherInterface`.
4. Система создаёт сессию и возвращает идентификатор сессии.

**Альтернативные сценарии:**
- 2a. User с указанным email не найден → система возвращает ошибку аутентификации (без уточнения причины).
- 3a. Пароль неверен → система возвращает ошибку аутентификации (без уточнения причины).
- 2b. User имеет `isActive = false` или помечен удалённым → система отклоняет вход.

**Постусловия:** пользователь аутентифицирован, сессия создана.

---

### UC-ID-11: Выйти из системы (Logout)

**Актор:** Аутентифицированный пользователь
**Предусловия:** пользователь аутентифицирован (сессия активна).

**Основной сценарий:**
1. Пользователь инициирует выход.
2. Система инвалидирует текущую сессию.

**Постусловия:** сессия уничтожена, пользователь не аутентифицирован.

---

### UC-ID-12: Сменить пароль

**Актор:** Аутентифицированный пользователь
**Предусловия:** пользователь аутентифицирован.

**Основной сценарий:**
1. Пользователь вводит текущий пароль и новый пароль.
2. Система проверяет текущий пароль через `PasswordHasherInterface`.
3. Система хэширует новый пароль и сохраняет.

**Альтернативные сценарии:**
- 2a. Текущий пароль введён неверно → система отклоняет операцию.

**Постусловия:** пароль пользователя изменён.

---

### UC-ID-13: Сбросить пароль пользователя

**Актор:** Admin
**Предусловия:** Admin аутентифицирован; User существует.

**Основной сценарий:**
1. Admin выбирает User.
2. Admin задаёт новый пароль для User.
3. Система хэширует новый пароль и сохраняет.

**Постусловия:** пароль User изменён; пользователь должен использовать новый пароль при следующем входе.

---

### UC-ID-14: Получить User по ID

**Актор:** Admin, Manager
**Предусловия:** актор аутентифицирован.

**Основной сценарий:**
1. Актор запрашивает User по `id`.
2. Система возвращает данные User.

**Альтернативные сценарии:**
- 1a. User не найден или помечен удалённым → система возвращает ошибку 404.

---

### UC-ID-15: Получить Group по ID

**Актор:** Admin, Manager
**Предусловия:** актор аутентифицирован.

**Основной сценарий:**
1. Актор запрашивает Group по `id`.
2. Система возвращает данные Group.

**Альтернативные сценарии:**
- 1a. Group не найдена или помечена удалённой → система возвращает ошибку 404.

## 4. Бизнес-правила и инварианты

| # | Инвариант |
|---|-----------|
| ИН-13 | Employee может добавлять Ticket только за себя. (Контроль на стороне TimesheetContext, но IdentityContext обеспечивает корректность идентификации актора.) |
| ИН-16 | User не может быть удалён физически. Удаление выполняется через Soft-delete (`deletedAt`). Если к User привязаны Ticket — Soft-delete недоступен; допускается только деактивация (`isActive = false`). |
| ИН-17 | Email пользователя должен быть уникальным в системе. |

**Дополнительные бизнес-правила:**

| # | Правило |
|---|---------|
| БП-01 | Наименование Group должно быть уникальным. |
| БП-02 | Group не может быть помечена удалённой (Soft-delete), если в ней состоят активные User. Физического удаления записи Group из базы данных не происходит. |
| БП-03 | Email User является логином и не может быть изменён после создания. |
| БП-04 | `groupId` User изменяется только через UC-ID-03 (ChangeUserGroup), не через UC-ID-08 (UpdateUser). |
| БП-05 | `roleId` хранится как UUID без валидации существования в WorkCatalog; валидация будет добавлена после реализации WorkCatalog. |

**Правила безопасности:**
- Пароли не хранятся в открытом виде. Применяется надёжное хэширование с солью.
- Admin задаёт начальный пароль при создании User; пользователь может сменить пароль самостоятельно через UC-ID-12.
- `isActive = false` — способ ограничить доступ User при наличии привязанных Ticket (когда Soft-delete недоступен).
- Soft-delete (`deletedAt`) — способ полного удаления User из системы при отсутствии привязанных Ticket.
- Системная роль User определяет всю матрицу доступа в системе.
- Система использует сессионную аутентификацию (statefull). Сессии хранятся на сервере; клиент идентифицируется по идентификатору сессии.

## 5. API-интерфейсы

Все операции (кроме Login) требуют аутентификации. Все идентификаторы — UUID. Все операции с коллекциями поддерживают пагинацию.

### Аутентификация

| Метод | Эндпоинт | Описание | Права |
|-------|----------|---------|-------|
| POST | `/auth/login` | Войти в систему (создать сессию) | Без аутентификации |
| POST | `/auth/logout` | Выйти из системы (инвалидировать сессию) | Аутентифицированный пользователь |

### User

| Метод | Эндпоинт | Описание | Права |
|-------|----------|---------|-------|
| POST | `/identity/users` | Создать User | Admin |
| GET | `/identity/users` | Получить User List | Admin, Manager |
| GET | `/identity/users/{id}` | Получить User по ID | Admin, Manager |
| PUT | `/identity/users/{id}` | Обновить User (`name`, `systemRole`, `roleId`) | Admin |
| POST | `/identity/users/{id}/deactivate` | Деактивировать User | Admin |
| PUT | `/identity/users/{id}/group` | Изменить принадлежность User к Group | Admin |
| DELETE | `/identity/users/{id}` | Удалить User (Soft-delete) | Admin |
| POST | `/identity/users/{id}/change-password` | Сменить пароль (текущий + новый) | Аутентифицированный пользователь (только свой) |
| POST | `/identity/users/{id}/reset-password` | Сбросить пароль пользователя | Admin |

### Group

| Метод | Эндпоинт | Описание | Права |
|-------|----------|---------|-------|
| POST | `/identity/groups` | Создать Group | Admin |
| GET | `/identity/groups` | Получить Group List | Admin, Manager |
| GET | `/identity/groups/{id}` | Получить Group по ID | Admin, Manager |
| PUT | `/identity/groups/{id}` | Обновить Group (`name`, `description`) | Admin |
| DELETE | `/identity/groups/{id}` | Удалить Group (Soft-delete) | Admin |

**Требования к ошибкам:**
- Попытка создать User с уже существующим email → ошибка с явным указанием поля.
- Попытка выполнить Soft-delete User с привязанными Ticket → ошибка с предложением деактивации.
- Попытка выполнить Soft-delete Group с активными User → ошибка с явным указанием причины.
- Попытка выполнить операцию без необходимых прав → ошибка авторизации.
- Попытка изменить `email` User → ошибка с явным указанием причины.
- Ошибка аутентификации (неверный email или пароль) → единое сообщение без уточнения причины.

## 6. Read Models

| Read Model | Описание | Фильтрация |
|------------|---------|------------|
| User List | Список активных (не удалённых) пользователей с атрибутами | По `groupId`, по `roleId`, по `isActive` |
| Group List | Список активных (не удалённых) организационных групп | Без обязательных фильтров |

**Требование к ответам:**
- User List возвращает `groupName` (наименование Group, если назначена).
- User List возвращает `roleId` и `roleName = null` до реализации WorkCatalog. После реализации WorkCatalog — `roleName` заполняется через JOIN или отдельный запрос к Role через Persistence.

## 7. Публикуемые события

| Событие | Триггер | Содержимое |
|---------|---------|------------|
| `UserCreated` | Создание User | `id`, `name`, `email`, `systemRole` |
| `UserUpdated` | Обновление атрибутов User | `userId`, `name`, `systemRole`, `roleId` |
| `UserDeactivated` | Деактивация User | `userId` |
| `UserDeleted` | Soft-delete User | `userId` |
| `GroupCreated` | Создание Group | `id`, `name` |
| `GroupUpdated` | Обновление атрибутов Group | `groupId`, `name`, `description` |
| `GroupDeleted` | Soft-delete Group | `groupId` |
| `UserAssignedToGroup` | Назначение User в Group | `userId`, `groupId` |
| `UserRemovedFromGroup` | Снятие привязки User к Group | `userId` |

## 8. Зависимости от других доменов

### Входящие зависимости (этот домен зависит от...)

| Домен-поставщик | Что используется | Характер зависимости |
|-----------------|-----------------|---------------------|
| **Work Catalog** | Role (опциональная ссылка `roleId` у User) | Downstream: Identity использует Role из WorkCatalog для профиля пользователя |

### Исходящие зависимости (другие домены зависят от нас)

| Домен-потребитель | Что использует | Характер зависимости |
|-------------------|---------------|---------------------|
| **Timesheet** | User (Employee — обязательный атрибут Ticket: `employeeId`) | Upstream: Timesheet идентифицирует исполнителя по User из Identity |
| **Reporting** | User, Group (фильтрация и группировка в Report) | Upstream: Reporting использует User и Group как измерения |

**Проверка при удалении User:** домен запрашивает TimesheetContext для проверки наличия Ticket с данным `employeeId` (через Persistence).

**Проверка при удалении Role:** WorkCatalogContext запрашивает IdentityContext для проверки, есть ли пользователи с данной `roleId`. Identity предоставляет метод `countActiveUsersByRoleId(string $roleId): int` в `UserRepositoryInterface`, реализованный в `DoctrineUserRepository` (запрос через Persistence).

## 9. Нефункциональные требования

| # | Требование |
|---|-----------|
| НФТ-П-01 | Время отклика API для операций чтения (User List, Group List) не должно превышать 1 секунды. |
| НФТ-П-02 | Время отклика для операций записи не должно превышать 2 секунд. |
| НФТ-П-05 | Список-запросы поддерживают пагинацию и не загружают в память более 1 000 записей за один запрос. |
| НФТ-Б-01 | Все операции (кроме Login) выполняются только от имени аутентифицированного пользователя. |
| НФТ-Б-02 | Разграничение прав реализовано на уровне каждой операции согласно матрице доступа. |
| НФТ-Б-03 | Employee не должен иметь возможности получить данные Ticket, принадлежащих другим сотрудникам (контроль совместно с TimesheetContext). |
| НФТ-Б-04 | Пароли пользователей не хранятся в открытом виде. Применяется надёжное хэширование с солью. |
| НФТ-Б-05 | Все входные данные проходят валидацию и санитизацию до передачи в доменный слой. |
| НФТ-Б-06 | Административные операции (создание/обновление/деактивация/удаление User, создание/обновление/удаление Group) логируются с указанием пользователя, действия, времени и результата. |
| НФТ-Н-01 | Атомарность операций: операция применяется полностью или откатывается. |
| НФТ-Н-02 | Инварианты доменной модели соблюдаются при любых обстоятельствах. |
| НФТ-Р-01 | Публичная граница (API/контракт) чётко определена. Внутренняя модель недоступна другим контекстам напрямую. |
| НФТ-У-01 | Сообщения об ошибках валидации содержат явное указание на поле и причину ошибки. |
| НФТ-У-02 | API-ответы содержат достаточно информации для UI без дополнительных запросов. |
| НФТ-У-03 | Пустые результаты фильтрации возвращаются как пустая коллекция, а не ошибка. |
| НФТ-У-04 | При деактивации User система явно информирует, что исторические данные будут сохранены. |

## 1. Цель домена

Домен **Timesheet** — ядро системы. Он отвечает за фиксацию фактических трудозатрат сотрудников (Ticket) и управление правилами импорта данных из внешних систем (Import Policy). Это downstream-контекст: он потребляет данные из трёх других доменов (Project Management, Work Catalog, Identity) и является источником данных для Reporting.

**Ключевые обязанности:**
- Создание и редактирование Manual Ticket сотрудниками.
- Импорт Ticket из внешних систем по правилам Import Policy.
- Хранение снимка тарифной ставки (`rateSnapshot`) на момент создания Ticket.
- Разграничение доступа к Ticket по ролям (Employee видит только свои Ticket).
- Управление конфигурацией Import Policy администратором.
- Предоставление Ticket List с фильтрацией для использования в Reporting.

**Чем домен не занимается:**
- Не управляет иерархией Client/Project/CR/Task (это ProjectManagementContext).
- Не управляет Rate, Role, Work (это WorkCatalogContext).
- Не управляет пользователями и группами (это IdentityContext).
- Не формирует отчёты и не генерирует файлы (это ReportingContext).

## 2. Сущности и Value Objects

### 2.1 Ticket (Aggregate Root)

Основная сущность системы. Запись о времени, затраченном Employee на конкретную Task.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| employeeId | UUID | обязательно | Ссылка на User (в роли Employee) из IdentityContext |
| taskId | UUID | обязательно | Ссылка на Task из ProjectManagementContext |
| workId | UUID | обязательно | Ссылка на Work из WorkCatalogContext |
| date | date | обязательно | Дата, за которую зафиксированы трудозатраты |
| hours | decimal | обязательно | Количество часов (строго > 0) |
| comment | string | опционально | Комментарий к тикету |
| rateSnapshot | decimal | обязательно | Снимок значения Rate на момент создания (неизменен после создания) |
| type | enum | обязательно | Тип Ticket: `Manual`, `Imported` |
| importSource | string | условно | Идентификатор источника (заполняется только для Imported Ticket) |
| isEditable | boolean | обязательно | Разрешено ли ручное редактирование данного Ticket |

**Допустимые значения `type`:** `Manual`, `Imported`.

**Ограничения:**
- `hours` должно быть строго положительным числом (> 0).
- `rateSnapshot` фиксируется один раз при создании и не пересчитывается никогда.
- Для Imported Ticket `isEditable = false` по умолчанию; значение переопределяется флагом `allowEdit` в Import Policy.
- Manual Ticket создаётся с `isEditable = true`.

---

### 2.2 Import Policy (Aggregate Root)

Набор правил трансформации данных внешней системы в Ticket. Реализует паттерн Anti-Corruption Layer на границе с внешней системой.

| Атрибут | Тип | Обязательность | Описание |
|---------|-----|:--------------:|---------|
| id | UUID | обязательно | Уникальный идентификатор |
| name | string | обязательно | Наименование политики |
| sourceSystem | string | обязательно | Идентификатор внешней системы-источника |
| mappingRules | JSON | обязательно | Правила трансформации полей внешней системы во внутренние атрибуты Ticket. Структура описана ниже. |
| allowEdit | boolean | обязательно | Разрешает ли политика ручное редактирование Imported Ticket |
| isActive | boolean | обязательно | Признак активности политики |

**Ограничения:**
- Для одного `sourceSystem` может быть активна (`isActive = true`) только одна Import Policy одновременно.
- Изменение Import Policy не пересчитывает ранее импортированные Ticket.

**Структура `mappingRules`:**

`mappingRules` — JSON-объект с обязательными ключами:

| Ключ | Тип | Описание |
|------|-----|---------|
| `employeeMapping.sourceField` | string | Поле внешней записи, содержащее идентификатор сотрудника |
| `employeeMapping.matchBy` | enum | Способ сопоставления: `email` или `externalId` |
| `taskMapping.sourceField` | string | Поле внешней записи, содержащее идентификатор задачи |
| `taskMapping.matchBy` | enum | Способ сопоставления: `name` или `externalId` |
| `workMapping.sourceField` | string | Поле внешней записи, содержащее идентификатор вида работ |
| `workMapping.matchBy` | enum | Способ сопоставления: `name` или `externalId` |
| `dateField` | string | Поле внешней записи, содержащее дату |
| `hoursField` | string | Поле внешней записи, содержащее количество часов |
| `commentField` | string \| null | Поле внешней записи, содержащее комментарий (null — не маппится) |
| `externalIdField` | string | Поле внешней записи, используемое как уникальный внешний идентификатор для дедупликации |

Пример:
```json
{
  "employeeMapping": { "sourceField": "user_email", "matchBy": "email" },
  "taskMapping":     { "sourceField": "task_code",  "matchBy": "externalId" },
  "workMapping":     { "sourceField": "work_type",  "matchBy": "name" },
  "dateField":       "worked_date",
  "hoursField":      "duration_hours",
  "commentField":    "notes",
  "externalIdField": "entry_id"
}
```

> **Примечание по реализации:** На первом этапе `mappingRules` сохраняется как произвольный JSON без строгой валидации структуры (`ExternalDataFetcherInterface` реализован как `NullExternalDataFetcher`). Валидация структуры и реализация конкретных интеграций добавляются при подключении реальных внешних систем.

---

### 2.3 Import Log Entry (Value Object)

Запись о результате обработки одной записи в ходе импорта. Не является самостоятельным агрегатом.

| Атрибут | Тип | Описание |
|---------|-----|---------|
| externalId | string | Внешний идентификатор записи |
| status | enum | Результат: `imported`, `duplicate`, `error` |
| errorReason | string | Причина ошибки (для статуса `error`) |

## 3. Use Cases

### UC-TS-01: Добавить Manual Ticket

**Актор:** Employee, Admin (за любого Employee)
**Предусловия:** актор аутентифицирован. Существуют Task и Work.
**Триггер:** Employee фиксирует трудозатраты.

**Основной сценарий:**
1. Employee открывает форму добавления Ticket.
2. Employee выбирает Task из Task List (ProjectManagementContext), Work из Work List (WorkCatalogContext), указывает дату, количество часов, опциональный комментарий.
3. Система проверяет:
   - `hours > 0`;
   - Employee добавляет Ticket только за себя (если актор — Employee, а не Admin);
   - Task существует в системе.
4. Система запрашивает актуальное значение Rate из WorkCatalogContext и фиксирует его как `rateSnapshot`.
5. Система создаёт Manual Ticket (`type = Manual`, `isEditable = true`) и публикует событие `TicketsAdded`.
6. Ticket отображается в Ticket List актора.

**Альтернативные сценарии:**
- 3a. `hours ≤ 0` → система отклоняет создание с сообщением об ошибке валидации.
- 3b. Employee пытается добавить Ticket за другого сотрудника → система отклоняет операцию.
- 3c. Task не существует → система отклоняет создание.
- 4a. Для данной комбинации Employee/Work нет актуальной Rate → система фиксирует `rateSnapshot = 0`. Создание Ticket не блокируется.

**Постусловия:** трудозатраты зафиксированы и доступны для формирования Report.

---

### UC-TS-02: Редактировать Manual Ticket

**Актор:** Employee (автор), Admin
**Предусловия:** Ticket существует, `type = Manual`.

**Основной сценарий:**
1. Актор выбирает Ticket из своего Ticket List.
2. Актор изменяет допустимые поля: дата (`date`), часы (`hours`), вид работ (`workId`), комментарий (`comment`).
3. Система проверяет права: Employee может редактировать только собственный Ticket.
4. Система обновляет Ticket. `rateSnapshot` не пересчитывается.

**Альтернативные сценарии:**
- 3a. Employee пытается редактировать Ticket другого сотрудника → система отклоняет операцию.
- 1a. Ticket имеет `type = Imported` и `isEditable = false` → система отклоняет редактирование.
- 2a. Новое значение `hours ≤ 0` → система отклоняет изменение.

**Постусловия:** Manual Ticket обновлён с сохранением исходного `rateSnapshot`.

---

### UC-TS-03: Просмотр Ticket List

**Актор:** Employee, Manager, Admin
**Предусловия:** актор аутентифицирован.

**Основной сценарий:**
1. Актор открывает Ticket List.
2. Актор применяет фильтры согласно своим правам:
   - Employee видит только свои Ticket; доступны фильтры по Project, Task, Work, периоду.
   - Manager и Admin видят Ticket всех сотрудников; доступны фильтры по Employee, Project, CR, Task, Work, периоду.
3. Система возвращает отфильтрованный список Ticket с пагинацией.

**Постусловия:** актор видит записи о трудозатратах в соответствии со своими правами.

---

### UC-TS-04: Настроить Import Policy

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin задаёт наименование, `sourceSystem` (идентификатор внешней системы), `mappingRules` (правила трансформации полей), `allowEdit`.
2. Admin активирует политику (`isActive = true`).
3. Система проверяет: для данного `sourceSystem` нет другой активной Import Policy.
4. Система сохраняет Import Policy.

**Альтернативные сценарии:**
- 3a. Для данного `sourceSystem` уже существует активная Import Policy → система отклоняет активацию новой и сообщает о конфликте.

**Постусловия:** система готова к импорту Ticket из указанной внешней системы.

---

### UC-TS-05: Запустить импорт Ticket

**Актор:** Admin
**Предусловия:** существует активная Import Policy для внешней системы.

**Основной сценарий:**
1. Admin выбирает Import Policy и указывает временной диапазон для импорта (`dateFrom`, `dateTo`).
2. Система через Anti-Corruption Layer (Import Policy) получает данные из внешней системы.
3. Система трансформирует записи по `mappingRules`, сопоставляет их с внутренними сущностями (Employee, Task, Work).
4. Система создаёт Imported Ticket для каждой успешно трансформированной записи.
   - Дубликаты определяются по паре (`importSource` + внешний идентификатор записи) — дублирующие записи не создаются.
   - `isEditable` для каждого Imported Ticket устанавливается согласно `allowEdit` Import Policy.
5. Записи, которые не удалось сопоставить, логируются (Import Log Entry); импорт остальных записей продолжается без прерывания.
6. Система публикует событие `TicketsImported` с итоговой сводкой: количество импортированных, количество дубликатов, количество ошибок.

**Постусловия:** данные из внешней системы доступны в Ticket List. Несопоставленные записи доступны в логе импорта.

---

### UC-TS-06: Просмотр и управление Import Policy

**Актор:** Admin
**Предусловия:** Admin аутентифицирован.

**Основной сценарий:**
1. Admin открывает список Import Policy.
2. Admin просматривает, создаёт, редактирует Import Policy.
3. При изменении статуса активности система проверяет инвариант: одна активная политика на один `sourceSystem`.

**Постусловия:** Import Policy актуальна; ранее импортированные Ticket не пересчитываются.

## 4. Бизнес-правила и инварианты

### Инварианты иерархии

| # | Инвариант |
|---|-----------|
| ИН-01 | Ticket всегда привязан к Task. Нельзя создать Ticket без существующей Task. |

### Инварианты тарификации

| # | Инвариант |
|---|-----------|
| ИН-08 | Rate фиксируется в момент создания Ticket (`rateSnapshot`) и не пересчитывается ретроспективно ни при редактировании Ticket, ни при изменении Rate. |

### Инварианты доступа к данным

| # | Инвариант |
|---|-----------|
| ИН-13 | Employee может добавлять Ticket только за себя. Добавление Ticket за другого сотрудника доступно только Admin. |
| ИН-14 | Employee может редактировать только собственные Manual Ticket. Admin может редактировать любой Manual Ticket. |
| ИН-15 | Imported Ticket нельзя редактировать вручную, если Import Policy не установила `allowEdit = true`. |

### Инварианты импорта

| # | Инвариант |
|---|-----------|
| ИН-18 | Для одного `sourceSystem` может быть активна только одна Import Policy одновременно. |
| ИН-19 | Изменение Import Policy не пересчитывает ранее импортированные Ticket. |
| ИН-20 | Дубликаты при импорте определяются по паре (`importSource` + внешний идентификатор записи) и не создаются повторно. |

**Дополнительные правила валидации:**
- `hours` в Ticket должно быть строго положительным числом (> 0).
- `date` в Ticket должна быть корректной датой.
- `rateSnapshot` не может быть изменён после создания Ticket при любых условиях.

## 5. API-интерфейсы

Все операции требуют аутентификации. Все идентификаторы — UUID. Все операции с коллекциями поддерживают пагинацию.

### Ticket

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать Manual Ticket | `employeeId`, `taskId`, `workId`, `date`, `hours` (> 0), `comment` (опционально) | Созданный Ticket с `id` и `rateSnapshot` | Employee (за себя), Admin (за любого) |
| Получить Ticket List | Фильтры: `employeeId`, `projectId`, `crId`, `taskId`, `workId`, `dateFrom`, `dateTo` (опционально) | Список Ticket с пагинацией | Employee (только свои), Manager, Admin |
| Обновить Manual Ticket | `ticketId`, `date`, `hours`, `workId`, `comment` (допустимые поля) | Обновлённый Ticket | Employee (свой), Admin |

**Ограничения Обновить Manual Ticket:**
- `rateSnapshot` не изменяется.
- Отклоняет, если `type = Imported` и `isEditable = false`.
- Employee может обновлять только собственный Ticket.

### Import Policy

| Операция | Входные данные | Выходные данные | Права |
|----------|---------------|----------------|-------|
| Создать Import Policy | `name`, `sourceSystem`, `mappingRules`, `allowEdit` | Созданная Import Policy с `id` | Admin |
| Получить Import Policy List | Без обязательных фильтров | Список всех Import Policy | Admin |
| Обновить Import Policy | `id`, допустимые поля: `mappingRules`, `allowEdit`, `isActive` | Обновлённая Import Policy | Admin |
| Запустить импорт | `importPolicyId`, `dateFrom`, `dateTo` | Сводка: `imported`, `duplicates`, `errors` | Admin |

**Требования к операции импорта:**
- Возвращает сводку в ответе независимо от наличия ошибок в отдельных записях.
- Несопоставленные записи не прерывают импорт остальных.
- Повторный запуск с теми же данными идемпотентен (дубликаты не создаются).

## 6. Read Models

| Read Model | Описание | Фильтрация |
|------------|---------|------------|
| Ticket List | Список Ticket с атрибутами | По `employeeId`, `projectId`, `crId`, `taskId`, `workId`, периоду (dateFrom/dateTo) |
| Import Policy List | Список Import Policy | Без обязательных фильтров |

**Права доступа к Ticket List:**
- Employee видит только Ticket со своим `employeeId`.
- Employee не может получить чужой Ticket даже при прямом обращении по идентификатору.
- Manager и Admin видят Ticket всех сотрудников.

**Требование к ответам:** Ticket List должен возвращать наименования связанных сущностей (Task, Work, имя Employee) — а не только их идентификаторы — для построения UI без дополнительных запросов.

## 8. Зависимости от других доменов

### Входящие зависимости (этот домен зависит от...)

| Домен-поставщик | Что используется | Характер зависимости |
|-----------------|-----------------|---------------------|
| **Project Management** | Task (обязательная ссылка `taskId` в Ticket) | Downstream: Timesheet проверяет существование Task и читает её атрибуты |
| **Work Catalog** | Rate (для фиксации `rateSnapshot`), Work (обязательный атрибут `workId` в Ticket) | Downstream: Timesheet запрашивает актуальную Rate при создании Ticket |
| **Identity** | User (Employee — обязательный атрибут `employeeId` в Ticket) | Downstream: Timesheet идентифицирует исполнителя через Identity |

### Исходящие зависимости (другие домены зависят от нас)

| Домен-потребитель | Что использует | Характер зависимости |
|-------------------|---------------|---------------------|
| **Reporting** | Ticket (все Report строятся на основе Ticket) | Upstream: Reporting запрашивает Ticket List с фильтрами |

**Anti-Corruption Layer:** Import Policy реализует паттерн Anti-Corruption Layer для изоляции ядра Timesheet от особенностей внешних систем. Добавление нового источника данных не должно требовать изменения ядра контекста — достаточно создать новую Import Policy.

## 9. Нефункциональные требования

| # | Требование |
|---|-----------|
| НФТ-П-01 | Время отклика API для операций чтения (Ticket List) не должно превышать 1 секунды при нормальной нагрузке. |
| НФТ-П-02 | Время отклика для операций записи (создание/обновление Ticket) не должно превышать 2 секунд. |
| НФТ-П-05 | Ticket List поддерживает пагинацию и не загружает в память более 1 000 записей за один запрос. |
| НФТ-Б-01 | Все операции выполняются только от имени аутентифицированного пользователя. |
| НФТ-Б-02 | Разграничение прав реализовано на уровне каждой операции согласно матрице доступа. |
| НФТ-Б-03 | Employee не должен иметь возможности получить данные Ticket, принадлежащих другим сотрудникам, даже при прямом обращении по `id`. |
| НФТ-Б-05 | Все входные данные проходят валидацию и санитизацию до передачи в доменный слой. |
| НФТ-Б-06 | Административные операции (создание/редактирование Import Policy, запуск импорта) логируются. |
| НФТ-Н-01 | Атомарность операций: операция применяется полностью или откатывается без частичных изменений. |

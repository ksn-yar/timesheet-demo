# Bounded Context: Identity

## Назначение и границы контекста

**Identity** — вспомогательный (supporting) контекст, отвечающий за управление пользователями системы и их организационную структуру. Он является единственным источником истины о том, кто имеет доступ к системе и какой набор прав ему соответствует.

**Что входит в контекст:**
- Создание и ведение учётных записей пользователей (User)
- Создание и ведение организационных групп (Group)
- Назначение пользователям ролей (Role из WorkCatalogContext) и групп
- Разграничение прав доступа (Admin, Employee, Manager)
- Предоставление read-моделей для других контекстов

**Что не входит в контекст:**
- Определение самих функциональных ролей (Role) — они хранятся в WorkCatalogContext
- Учёт трудозатрат — это зона ответственности TimesheetContext
- Формирование отчётов — это зона ответственности ReportingContext
- Аутентификация (если реализована через внешний провайдер — выносится за границу контекста)

**Роль в карте контекстов:** Identity является upstream-поставщиком для TimesheetContext (Employee — обязательный атрибут Ticket) и для ReportingContext (группировка отчётов по Employee и Group). Отношение — Customer-Supplier.

**Важные семантические разграничения:**
- **Admin** — не отдельный агрегат, а контекстная роль User с расширенными правами на управление конфигурацией.
- **Employee** — контекстная роль User в TimesheetContext, означающая, что данный User вносит трудозатраты через Ticket. Сам термин "Employee" принадлежит TimesheetContext.

## Доменные модели

### Агрегаты

#### User (Пользователь)
Физическое лицо, имеющее доступ к системе. Обладает одной или несколькими ролями и может входить в Group.

| Атрибут    | Тип      | Описание                                                          |
|------------|----------|-------------------------------------------------------------------|
| id         | UUID     | Уникальный идентификатор пользователя                             |
| name       | string   | Полное имя пользователя                                           |
| email      | string   | Email — уникальный логин для входа в систему                      |
| groupId    | UUID     | Ссылка на Group, к которой принадлежит пользователь (опционально) |
| roleId     | UUID     | Ссылка на функциональную Role (из WorkCatalogContext)             |
| systemRole | enum     | Системная роль: Admin, Manager, Employee                          |
| isActive   | boolean  | Признак активности учётной записи                                 |

**Инварианты:**
- Email должен быть уникальным в системе.
- User создаётся с `isActive = true` по умолчанию.
- User с системной ролью Admin может управлять справочниками и конфигурацией.
- Employee может добавлять Ticket только за себя, если не обладает правами Admin.
- User не может быть удалён (только деактивирован), если к нему привязаны Ticket.

---

#### Group (Группа)
Организационная единица, объединяющая User. Используется для разграничения доступа и группировки данных в отчётах.

| Атрибут     | Тип    | Описание                                |
|-------------|--------|-----------------------------------------|
| id          | UUID   | Уникальный идентификатор группы         |
| name        | string | Наименование группы                     |
| description | string | Описание группы (опционально)           |

**Инварианты:**
- Наименование Group должно быть уникальным.
- Group не может быть удалена, если в ней есть активные User.

---

### Read Models

| Read Model     | Описание                                                                                                        |
|----------------|-----------------------------------------------------------------------------------------------------------------|
| **User List**  | Список User с возможностью фильтрации по Group, функциональной Role и isActive. Доступен Admin и Manager.       |
| **Group List** | Список Group. Используется при назначении пользователя в группу и при фильтрации в Reporting. Доступен Admin и Manager. |

## Пользовательские потоки (Use Cases)

### UC-ID-01: Создать пользователя
**Актор:** Admin
**Предусловия:** пользователь аутентифицирован и обладает правами Admin.
**Сценарий:**
1. Admin вводит имя, email, системную роль и опционально выбирает Group и функциональную Role (из Work Catalog).
2. Система проверяет уникальность email.
3. Система создаёт User и публикует событие `UserCreated`.
4. User появляется в User List.

**Результат:** новый User может войти в систему и выполнять действия в соответствии со своей системной ролью.

---

### UC-ID-02: Создать группу
**Актор:** Admin
**Предусловия:** пользователь аутентифицирован и обладает правами Admin.
**Сценарий:**
1. Admin вводит наименование и описание Group.
2. Система проверяет уникальность наименования.
3. Система создаёт Group и публикует событие `GroupCreated`.

**Результат:** новая Group доступна для назначения User и для фильтрации в отчётах.

---

### UC-ID-03: Назначить пользователя в группу
**Актор:** Admin
**Предусловия:** существуют User и Group.
**Сценарий:**
1. Admin выбирает User из User List.
2. Admin выбирает Group из списка групп.
3. Система обновляет принадлежность User к Group.
4. Система публикует событие `UserAssignedToGroup`.

**Результат:** User входит в Group, его Ticket учитываются при групповой фильтрации в ReportingContext.

---

### UC-ID-04: Просмотр User List
**Актор:** Admin, Manager
**Сценарий:**
1. Актор открывает список пользователей.
2. Актор опционально применяет фильтры: по Group, по функциональной Role, по статусу активности.
3. Система возвращает отфильтрованный User List.

**Результат:** актор видит актуальный список пользователей с нужными параметрами.

---

### UC-ID-05: Деактивировать пользователя
**Актор:** Admin
**Предусловия:** User существует и имеет статус активного.
**Сценарий:**
1. Admin выбирает User из User List.
2. Admin инициирует деактивацию.
3. Система устанавливает `isActive = false`.
4. Система публикует событие `UserDeactivated`.

**Результат:** User теряет доступ к системе. Исторические данные (Ticket, отчёты) сохраняются.

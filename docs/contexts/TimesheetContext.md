# Bounded Context: Timesheet

## Назначение и границы контекста

**Timesheet** — ядро (core domain) системы. Именно здесь концентрируется основная бизнес-ценность: фиксация фактически затраченного времени сотрудников в привязке к задачам проекта. Все остальные контексты либо поставляют конфигурационные данные для этого контекста, либо потребляют его данные для аналитики.

**Что входит в контекст:**
- Ручное добавление записей о трудозатратах (Manual Ticket)
- Автоматический импорт Ticket из внешних систем по правилам (Imported Ticket)
- Управление политиками импорта (Import Policy)
- Предоставление read-моделей для просмотра и фильтрации записей

**Что не входит в контекст:**
- Создание Task, Project, CR, Client — это зона ответственности ProjectContext
- Определение Rate, Role, Work — это зона ответственности WorkCatalogContext
- Управление учётными записями User — это зона ответственности IdentityContext
- Формирование сводных отчётов и выгрузок — это зона ответственности ReportingContext

**Роль в карте контекстов:** Timesheet является downstream-потребителем данных из ProjectContext (Task), IdentityContext (Employee/User) и WorkCatalogContext (Work, Rate). По отношению к ReportingContext — upstream-поставщик: все Report строятся на основе Ticket.

**Интеграция с внешними системами:** Imported Ticket поступают через Anti-Corruption Layer (Import Policy), который транслирует структуры данных внешней системы в доменные объекты TimesheetContext, не допуская загрязнения внутренней модели.

## Доменные модели

### Агрегаты

#### Ticket (Тикет)
Основная сущность системы. Запись о времени, затраченном Employee на конкретную Task. Существует в двух вариациях: добавленный вручную (Manual Ticket) и импортированный (Imported Ticket).

| Атрибут      | Тип      | Описание                                                         |
|--------------|----------|------------------------------------------------------------------|
| id           | UUID     | Уникальный идентификатор тикета                                  |
| employeeId   | UUID     | Ссылка на User (в роли Employee) из IdentityContext              |
| taskId       | UUID     | Ссылка на Task из ProjectContext                                  |
| workId       | UUID     | Ссылка на Work из WorkCatalogContext                             |
| date         | date     | Дата, за которую зафиксированы трудозатраты                      |
| hours        | decimal  | Количество затраченных часов                                     |
| comment      | string   | Комментарий к тикету (опционально)                               |
| rateSnapshot | decimal  | Снимок Rate на момент создания Ticket (не изменяется)            |
| type         | enum     | Тип тикета: Manual, Imported                                     |
| importSource | string   | Идентификатор источника импорта (заполняется только для Imported Ticket) |
| isEditable   | boolean  | Признак возможности ручного редактирования (для Imported Ticket определяется Import Policy) |

**Инварианты:**
- Ticket всегда привязан к Task; Task всегда привязана к Project или CR.
- Количество часов должно быть положительным числом.
- Rate фиксируется на момент создания Ticket (`rateSnapshot`) и не пересчитывается ретроспективно ни при редактировании Ticket, ни при изменении Rate.
- Employee может добавлять Ticket только за себя (если не Admin).
- Manual Ticket создаётся с `isEditable = true`.
- Imported Ticket нельзя редактировать вручную без явного разрешения Import Policy (`isEditable = false` по умолчанию для импортированных).

---

#### Import Policy (Политика импорта)
Набор правил, по которым данные из внешней системы трансформируются в Ticket. Живёт на границе с внешней системой и реализует паттерн Anti-Corruption Layer.

| Атрибут      | Тип     | Описание                                                          |
|--------------|---------|-------------------------------------------------------------------|
| id           | UUID    | Уникальный идентификатор политики                                 |
| name         | string  | Наименование политики                                             |
| sourceSystem | string  | Идентификатор внешней системы-источника                           |
| mappingRules | JSON    | Правила трансформации полей внешней системы в атрибуты Ticket     |
| allowEdit    | boolean | Разрешает ли политика ручное редактирование импортированных Ticket |
| isActive     | boolean | Признак активности политики                                       |

**Инварианты:**
- Для одной внешней системы может существовать несколько Import Policy, но активной единовременно может быть только одна.
- Изменение Import Policy не пересчитывает ранее импортированные Ticket.

## Пользовательские потоки (Use Cases)

### UC-TS-01: Добавить Ticket вручную (Add Tickets)
**Актор:** Employee
**Предусловия:** пользователь аутентифицирован в роли Employee. Существуют Task и Work.
**Сценарий:**
1. Employee открывает форму добавления Ticket.
2. Employee выбирает Task (из Task List ProjectContext), Work (из Work List WorkCatalogContext), указывает дату, количество часов и опциональный комментарий.
3. Система проверяет:
   - Employee добавляет Ticket только за себя (если не Admin).
   - Количество часов > 0.
   - Task существует и активна.
4. Система фиксирует текущую Rate (snapshot).
5. Система создаёт Manual Ticket и публикует событие `TicketsAdded`.
6. Ticket появляется в Ticket List.

**Результат:** трудозатраты зафиксированы и доступны для просмотра и последующей отчётности.

---

### UC-TS-02: Импортировать Ticket по политике (Import Tickets)
**Актор:** Admin или System (автоматически по расписанию)
**Предусловия:** настроена хотя бы одна активная Import Policy для внешней системы.
**Сценарий:**
1. Admin (или планировщик) инициирует команду `ImportTickets`, указывая Import Policy и временной диапазон.
2. Система обращается к Anti-Corruption Layer (Import Policy), который:
   a. Получает данные из внешней системы.
   b. Трансформирует их в структуры Ticket согласно mappingRules.
   c. Сопоставляет Employee, Task, Work с внутренними идентификаторами.
3. Система создаёт Imported Ticket для каждой успешно трансформированной записи.
4. Система публикует событие `TicketsImported` с указанием количества импортированных записей и источника.
5. Imported Ticket появляются в Ticket List.

**Результат:** данные из внешней системы доступны в Timesheet без ручного ввода.

**Обработка ошибок:**
- Записи, которые не удалось сопоставить, логируются как ошибки импорта и не создают Ticket.
- Дубликаты определяются по связке (importSource + внешний идентификатор записи) и не создаются повторно.

---

### UC-TS-03: Просмотр Ticket List
**Актор:** Employee, Manager, Admin
**Сценарий:**
1. Актор открывает Ticket List.
2. Актор применяет фильтры:
   - Employee: только свои Ticket (если роль Employee); любой Employee (если роль Admin/Manager).
   - Project, CR, Task — фильтрация по структуре ProjectContext.
   - Work — фильтрация по классификатору WorkCatalogContext.
   - Период: дата от/до.
3. Система возвращает отфильтрованный список Ticket.

**Результат:** актор видит записи о трудозатратах в соответствии со своими правами и заданными фильтрами.

---

### UC-TS-04: Редактировать Manual Ticket
**Актор:** Employee (автор), Admin
**Предусловия:** Ticket существует, его тип — Manual.
**Сценарий:**
1. Актор выбирает Ticket из Ticket List.
2. Актор изменяет допустимые поля (дата, часы, Work, комментарий).
3. Система проверяет права: Employee может редактировать только собственный Ticket.
4. Система обновляет Ticket. Rate snapshot не пересчитывается.

**Результат:** Manual Ticket обновлён.

---

### UC-TS-05: Настроить Import Policy
**Актор:** Admin
**Предусловия:** пользователь аутентифицирован и обладает правами Admin.
**Сценарий:**
1. Admin задаёт наименование политики, идентификатор внешней системы и правила маппинга полей.
2. Admin указывает, разрешено ли ручное редактирование Imported Ticket (`allowEdit`).
3. Admin активирует политику (`isActive = true`).
4. Система проверяет, что для данного `sourceSystem` нет другой активной политики.
5. Система сохраняет Import Policy.

**Результат:** система готова к импорту Ticket из указанной внешней системы согласно заданным правилам.

---

### UC-TS-06: Запустить импорт Ticket
**Актор:** Admin
**Предусловия:** существует активная Import Policy для внешней системы.
**Сценарий:**
1. Admin выбирает Import Policy и указывает временной диапазон для импорта.
2. Система через Anti-Corruption Layer (Import Policy) получает данные из внешней системы.
3. Система трансформирует записи по `mappingRules`, сопоставляет их с внутренними сущностями (Employee, Task, Work).
4. Система создаёт Imported Ticket для каждой успешно трансформированной записи. Дубликаты (по паре `importSource` + внешний идентификатор) не создаются.
5. Записи, которые не удалось сопоставить, логируются; импорт остальных записей продолжается.
6. Система публикует событие `TicketsImported` с количеством импортированных записей и источника.

**Результат:** данные из внешней системы доступны в Ticket List без ручного ввода.

# Вопросы и неточности к ТЗ домена Reporting

**Дата обновления:** 2026-03-22
**Основание:** docs/technical-specification-parts/reporting.md (v1.0)

## Проблема 1: ReportExport -- Value Object или Entity?

**Статус:** РЕШЕНО В ПЛАНЕ

**Раздел ТЗ:** Раздел 2.2 "Report Export (Value Object)", Раздел 5 "API-интерфейсы", Раздел 6 "Read Models"

**Описание:** ТЗ описывает Report Export как Value Object, однако одновременно требует:
- Хранение списка выгрузок (Exported Reports List) с пагинацией (раздел 5, раздел 6)
- Фильтрацию по `format` и `generatedAt` (раздел 6)
- Доступ к файлу по ссылке (раздел 5)

Value Object по определению не имеет идентичности и жизненного цикла. Но для реализации Exported Reports List с пагинацией, фильтрацией и хранением нужен собственный идентификатор и отдельная таблица в базе данных.

**Решение:** В плане ReportExport остаётся Value Object в доменном слое, но получает `ReportExportId` (UUID) для идентификации. В Persistence-слое моделируется как отдельная Doctrine Entity с собственным `id`.

## Проблема 2: Отсутствие Use Case для удаления Report

**Статус:** РЕШЕНО В ТЗ

**Раздел ТЗ:** Раздел 3 "Use Cases", Раздел 4.1 "Известные ограничения MVP"

**Описание:** ТЗ не определяет операцию удаления Report. Report неизменяем (ИН-22), но ТЗ не запрещает его удаление.

**Решение:** ТЗ обновлено -- раздел 4.1 "Известные ограничения MVP" явно фиксирует: удаление Report не реализуется на этапе MVP. При необходимости в будущем следует реализовать как soft-delete по аналогии с другими доменами системы.

---

## Проблема 3: Отсутствие Use Case для удаления Report Export (файла выгрузки)

**Статус:** РЕШЕНО В ТЗ

**Раздел ТЗ:** Раздел 3 "Use Cases", Раздел 4.1 "Известные ограничения MVP"

**Описание:** ТЗ не определяет операцию удаления файлов выгрузки. Генерируемые файлы (CSV, XLSX, PDF) занимают дисковое пространство. Без механизма очистки файловое хранилище будет неограниченно расти.

**Решение:** ТЗ обновлено -- раздел 4.1 "Известные ограничения MVP" явно фиксирует: механизм автоматической очистки не реализуется на этапе MVP. Перспективное решение -- консольная команда `reporting:cleanup-exports` с параметром TTL (в днях), запускаемая по cron.

## Проблема 4: Неясен формат и структура поля `data` в Report

**Статус:** РЕШЕНО В ПЛАНЕ

**Раздел ТЗ:** Раздел 2.1 "Report", Раздел 3 "UC-RP-01"

**Описание:** ТЗ указывает, что `data` -- это JSON с агрегированными данными (snapshot Ticket на момент формирования). Однако не определена конкретная структура этого JSON.

**Решение:** В плане определено: `data` -- плоский массив записей, каждая содержит значения измерений (ID + наименование) и три агрегированные метрики: `totalHours`, `totalCost`, `ticketCount`. Промежуточные итоги не включаются. Реализуется через `ReportAggregationService`.

## Проблема 5: Неясен механизм хранения и доступа к файлам экспорта

**Статус:** РЕШЕНО В ПЛАНЕ

**Раздел ТЗ:** Раздел 2.2 "Report Export", Раздел 5 "API-интерфейсы"

**Описание:** ТЗ указывает, что Report Export содержит `fileRef` -- "ссылка на сгенерированный файл (для скачивания)". Не определено, где и как хранятся файлы.

**Решение:** В плане определено: файлы хранятся в локальной файловой системе (`var/exports/`), `fileRef` = относительный путь. Доступ через API-эндпоинт `GET /api/reporting/exports/{id}/download` с проверкой авторизации.

---

## Проблема 6: Отсутствие API-эндпоинта для скачивания файла выгрузки

**Статус:** РЕШЕНО В ТЗ

**Раздел ТЗ:** Раздел 5 "API-интерфейсы"

**Описание:** ТЗ ранее не определяло конкретный эндпоинт для скачивания файла, хотя UC-RP-02 шаг 6 упоминает "Актор скачивает файл по ссылке".

**Решение:** ТЗ обновлено -- раздел 5 теперь содержит: "Файл доступен через `GET /api/reporting/exports/{exportId}/download`". В плане реализуется как `DownloadExportController`, который возвращает `BinaryFileResponse`.

## Проблема 7: Операция экспорта и производительность при больших объёмах

**Статус:** РЕШЕНО В ТЗ

**Раздел ТЗ:** Раздел 5 "API-интерфейсы", Раздел 9 "НФТ-П-04"

**Описание:** НФТ-П-04 требует генерацию файла до 50 000 строк не более чем за 60 секунд. Стандартный HTTP-запрос имеет ограниченный timeout.

**Решение:** ТЗ обновлено -- раздел 5 теперь явно указывает: "На этапе MVP генерация файла выполняется синхронно (клиент ожидает ответа). Асинхронная генерация через Symfony Messenger (job queue) — перспективное направление при недостаточной производительности синхронного режима." В плане: `set_time_limit(120)` для контроллера экспорта, ответ HTTP 201 с `exportId`.

## Проблема 8: Недостаточно определён `createdBy` -- откуда берётся автор Report

**Статус:** РЕШЕНО В ПЛАНЕ

**Раздел ТЗ:** Раздел 2.1 "Report", Раздел 3 "UC-RP-01"

**Описание:** ТЗ указывает, что `createdBy` -- "Ссылка на User, создавшего отчёт (из IdentityContext)". Однако UC-RP-01 не описывает, как определяется автор.

**Решение:** В плане определено: `createdBy` извлекается автоматически из токена аутентификации (Security Token) в `CreateReportInputTransformer` и передаётся в `CreateReportInputDto`. Имя автора (`createdByName`) получается через JOIN с таблицей `users` в Persistence-слое.

## Проблема 9: Отсутствие Get Report Export по ID

**Статус:** РЕШЕНО В ПЛАНЕ

**Раздел ТЗ:** Раздел 5 "API-интерфейсы"

**Описание:** В разделе API определена операция "Получить Exported Reports List", но нет операции получения одного Report Export по ID. Без этого невозможно реализовать эндпоинт скачивания.

**Решение:** В плане добавлен метод `findById(ReportExportId)` в `ReportExportRepositoryInterface`. Используется в `DownloadExportController`.

## Проблема 10: Формирование Report -- `rateSnapshot * hours` упомянуто, но не формализовано

**Статус:** РЕШЕНО В ПЛАНЕ

**Раздел ТЗ:** Раздел 3 "UC-RP-01", шаг 4

**Описание:** UC-RP-01 шаг 4 упоминает: "суммирует `hours`, `rateSnapshot * hours` и т.д." -- формулировка "и т.д." размыта.

**Решение:** В плане определены три метрики: `totalHours` (сумма `hours`), `totalCost` (сумма `hours * rateSnapshot`), `ticketCount` (количество Ticket в группе). Реализуется в `ReportAggregationService`.

## Проблема 11: Отсутствие фильтра по `createdBy` в Exported Reports List

**Статус:** РЕШЕНО В ТЗ

**Раздел ТЗ:** Раздел 2.2 "Report Export (Value Object)", Раздел 5 "API-интерфейсы", Раздел 6 "Read Models"

**Описание:** Exported Reports List поддерживает фильтрацию по `format` и `generatedAt`, но не по `createdBy` (кто инициировал экспорт). В ТЗ не указано, кто создал выгрузку. У Report Export нет поля `createdBy`.

**Решение:** ТЗ обновлено -- раздел 2.2 содержит примечание: "Report Export не содержит поля `createdBy` (автор выгрузки). Идентификация инициатора экспорта не является требованием MVP. При необходимости в будущем следует добавить поле `createdBy` в Report Export и соответствующий фильтр в Exported Reports List." Вопрос закрыт осознанным решением.

## Проблема 12: Неясно, как передаётся `createdBy` в CreateReportUseCase

**Статус:** РЕШЕНО В ПЛАНЕ

**Раздел ТЗ:** Раздел 3 "UC-RP-01", Раздел 5 "API-интерфейсы"

**Описание:** Таблица API (раздел 5) указывает входные данные для "Создать Report" без `createdBy`, хотя Report содержит `createdBy` как обязательный атрибут.

**Решение:** `createdBy` извлекается из контекста аутентификации (Security Token) в `CreateReportInputTransformer` и передаётся в `CreateReportInputDto`. UseCase получает UUID автора через InputDto.

## Проблема 13: ТЗ не определяет ответ на создание Report

**Статус:** РЕШЕНО В ТЗ

**Раздел ТЗ:** Раздел 5 "API-интерфейсы"

**Описание:** Ранее таблица API (раздел 5) не определяла конкретный формат ответа на создание Report.

**Решение:** ТЗ обновлено -- раздел 5 теперь указывает: "HTTP 201 с `id` сформированного Report. Полные данные (`data`) доступны через `GET /api/reporting/reports/{id}`." Это полностью соответствует паттерну Command без Presenter, используемому в проекте. Контроллер генерирует `ReportId` заранее в `InputTransformer`, передаёт в InputDto, после `execute()` возвращает HTTP 201 с `id`.

## Проблема 15: ТЗ описывает `name` в инвариантах неявно

**Статус:** РЕШЕНО В ТЗ

**Раздел ТЗ:** Раздел 4 "Бизнес-правила и инварианты"

**Описание:** Ранее правило о непустом `name` не было выделено как отдельный инвариант с номером и не имело ограничения длины.

**Решение:** ТЗ обновлено -- добавлен инвариант ИН-24: "`name` Report не может быть пустым. Максимальная длина — 255 символов." В плане реализации `name` валидируется через `#[NotBlank]`, `#[Length(max: 255)]` в Request DTO и проверку в фабричном методе `Report::create()`.

## Проблема 17: Лишний ExportReportsOutputPortInterface в плане реализации

**Статус:** ИСПРАВЛЕНО В ПЛАНЕ

**Раздел плана:** Раздел 11, Шаг 3.2 "OutputPort-интерфейсы"

**Описание:** В шаге 3.2 плана (этап 3, Application Layer) перечислен `ExportReportsOutputPortInterface`. Однако `ExportReportsUseCase` -- это Command Use Case с `execute(): void` (без OutputPort/Presenter), что явно указано в разделе 5 плана ("Паттерн Command: оба Command Use Case имеют `execute(): void`"). В дереве файлов (раздел 2) `ExportReportsOutputPortInterface` не был указан -- расхождение между деревом файлов и шагами реализации.

**Решение:** `ExportReportsOutputPortInterface` удалён из шага 3.2 плана (версия 1.1). OutputPort-интерфейсы определяются только для Query Use Cases: `GetReportOutputPortInterface`, `ListReportsOutputPortInterface`, `ListExportedReportsOutputPortInterface`.

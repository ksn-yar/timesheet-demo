# Вопросы и неточности к ТЗ домена Work Catalog

**Дата:** 2026-03-22
**Основание:** docs/technical-specification-parts/work-catalog.md (v1.1)

## Проблема 1: Отсутствие событий для операций Update и Delete

**Статус:** ЗАКРЫТО

**Раздел ТЗ:** Раздел 7 "Публикуемые события"

**Описание:** ТЗ определяет только три доменных события: `WorkCreated`, `RoleCreated`, `RateCreated`. При этом система поддерживает операции обновления (UC-WC-04: Изменить Rate) и удаления (UC-WC-05, UC-WC-06, UC-WC-07: Soft-delete Work/Role/Rate). Для этих операций события не определены.

**Почему это важно:**
- НФТ-Б-06 требует логирования административных операций. Без событий для Update и Delete аудит-логирование через Event Listener невозможно для этих операций.
- В домене ProjectManagement аналогичная проблема была решена добавлением 8 событий Updated/Deleted (см. `docs/plan/project-management-issues.md`, проблема 10).

**Рекомендация:** Добавить события:
- `WorkDeleted` (поля: `workId`)
- `RoleDeleted` (поля: `roleId`)
- `RateUpdated` (поля: `rateId`)
- `RateDeleted` (поля: `rateId`)

## Проблема 2: Отсутствие операций Update для Work и Role

**Статус:** ЗАКРЫТО

**Раздел ТЗ:** Раздел 3 "Use Cases", Раздел 5 "API-интерфейсы"

**Описание:** ТЗ определяет операции создания и удаления (soft-delete) для Work и Role, но не определяет операцию обновления. При этом обе сущности имеют изменяемые атрибуты (`name`, `description`), и аналогичные сущности в домене ProjectManagement (Client, Project, CR, Task) поддерживают обновление.

**Вопрос:** Является ли отсутствие Update для Work и Role осознанным решением (справочники не редактируются, только создаются/удаляются), или это пропуск?

**Рекомендация:** Если это пропуск -- добавить Use Cases и API-эндпоинты:
- UC-WC-09: Обновить Work (PUT `/api/work-catalog/works/{id}`)
- UC-WC-10: Обновить Role (PUT `/api/work-catalog/roles/{id}`)

Если осознанное решение -- зафиксировать это в ТЗ явно.

## Проблема 3: Неоднозначность проверки уникальности name при наличии soft-deleted записей

**Статус:** ЗАКРЫТО

**Раздел ТЗ:** Раздел 2.1 "Work", Раздел 2.2 "Role", Раздел 4 "Бизнес-правила"

**Описание:** ТЗ требует уникальности `name` для Work и Role. Однако не уточняется, распространяется ли ограничение уникальности на soft-deleted записи.

**Сценарий:**
1. Admin создаёт Work с именем "Development"
2. Admin удаляет (soft-delete) эту Work
3. Admin пытается создать новую Work с именем "Development"

Должна ли система разрешить создание?

**Варианты:**
- **A. Уникальность среди всех записей (включая удалённые):** проще в реализации (UNIQUE constraint на уровне БД), но удалённые записи блокируют создание одноимённых.
- **B. Уникальность только среди активных записей:** пользователь может переиспользовать имя. Требует partial unique index (`WHERE deleted_at IS NULL`) или программной проверки.

**Рекомендация:** Вариант B (уникальность среди активных записей) более user-friendly и логичен для soft-delete системы. Реализуется через partial unique index в PostgreSQL:
```sql
CREATE UNIQUE INDEX uq_works_name_active ON works (name) WHERE deleted_at IS NULL;
CREATE UNIQUE INDEX uq_roles_name_active ON roles (name) WHERE deleted_at IS NULL;
```

## Проблема 4: Отсутствие Read Model для Role List -- несогласованность прав доступа

**Статус:** ЗАКРЫТО

**Раздел ТЗ:** Раздел 5 "API-интерфейсы", Раздел 6 "Read Models"

**Описание:** В Разделе 5 "API-интерфейсы" право просмотра Role List указано только для Admin. Однако в общем ТЗ (`docs/technical-specification.md`, Раздел 2.2 "Матрица прав доступа") просмотр справочников доступен всем ролям (Admin, Manager, Employee).

**Вопрос:** Role List доступен только Admin или всем ролям?

**Контекст:** Work List доступен всем ролям (Admin, Manager, Employee) -- это согласовано между разделами 5 и 6 ТЗ Work Catalog и общим ТЗ. Для Role List есть расхождение.

**Рекомендация:** Согласовать с общим ТЗ. Если Role -- справочник, используемый при выборе (например, при фильтрации User List), логично предоставить доступ Manager и Employee для чтения.

## Проблема 5: Тип поля amount -- decimal vs string

**Статус:** ЗАКРЫТО

**Раздел ТЗ:** Раздел 2.3 "Rate"

**Описание:** ТЗ определяет тип `amount` как `decimal`. В контексте PHP и Doctrine это порождает вопрос о представлении:
- Doctrine хранит `decimal` как `string` в PHP (для точности)
- В JSON API десериализация может дать `float` (потеря точности для больших чисел)

**Рекомендация:** Использовать `string` для передачи `amount` через API (JSON) и хранения в PHP-коде (Value Object `Money`). Doctrine column type `decimal(12,2)`. Валидация формата -- на уровне Request DTO.

## Проблема 6: Формат валюты currency -- нет ограничения на допустимые значения

**Статус:** ЗАКРЫТО

**Раздел ТЗ:** Раздел 2.3 "Rate", Раздел 4 "Бизнес-правила"

**Описание:** ТЗ описывает `currency` как `string` с примерами (USD, EUR, RUB) и требованием "непустая строка". Однако не определён фиксированный перечень допустимых валют и не указан стандарт (ISO 4217).

**Вопрос:** Должна ли система валидировать `currency` по ISO 4217, или принимать любую непустую строку длиной до 3 символов?

**Рекомендация:** На первом этапе ограничить `currency` непустой строкой длиной 3 символа (совместимо с ISO 4217, но без жёсткой привязки к справочнику). При необходимости в будущем можно добавить Enum или справочник валют.

## Проблема 7: Отсутствие операции "Получить Rate по ID" (Get Rate)

**Статус:** ЗАКРЫТО

**Раздел ТЗ:** Раздел 5 "API-интерфейсы"

**Описание:** ТЗ определяет List, Create, Update и Delete для Rate, но не определяет операцию получения одной Rate по ID. Аналогично, для Work и Role нет операции Get by ID.

**Вопрос:** Нужны ли эндпоинты GET `/api/work-catalog/rates/{id}`, GET `/api/work-catalog/works/{id}`, GET `/api/work-catalog/roles/{id}`?

**Рекомендация:** Для MVP можно обойтись без Get by ID -- фронтенд получает данные через List. Однако для Update Rate контроллеру может потребоваться предзагрузка данных. Рекомендуется добавить Get by ID хотя бы для Rate, если планируется форма редактирования на фронтенде.

## Проблема 8: Условие проверки effectiveFrom при обновлении Rate -- точное сравнение дат

**Статус:** ЗАКРЫТО

**Раздел ТЗ:** Раздел 3 "UC-WC-04", Раздел 4 "ИН-09"

**Описание:** ТЗ запрещает изменять `effectiveFrom` у Rate, применённой к Ticket. Однако не уточняется: запрещено ли отправлять то же самое значение `effectiveFrom` в запросе на обновление?

**Сценарий:**
1. Rate с `effectiveFrom = 2026-01-01` применена к Ticket
2. Admin отправляет PUT с `effectiveFrom = 2026-01-01` (значение не изменилось)

Должна ли система отклонить запрос?

**Рекомендация:** Если новое значение `effectiveFrom` совпадает с текущим -- считать это допустимым (значение не изменилось, инвариант не нарушен). Бросать `RateEffectiveFromImmutableException` только при фактическом изменении значения.

## Проблема 9: Cascading soft-delete для Rate при удалении Role

**Статус:** ЗАКРЫТО

**Раздел ТЗ:** Раздел 2.2 "Role", Раздел 3 "UC-WC-06"

**Описание:** ТЗ запрещает soft-delete Role, если к ней привязаны активные Rate. Но не описывает сценарий, в котором Admin хочет удалить Role вместе со всеми привязанными Rate.

**Вопрос:** Должна ли система предоставлять возможность каскадного soft-delete (удалить Role и все связанные Rate одной операцией)?

**Рекомендация:** На первом этапе не реализовывать каскадный soft-delete. Admin должен сначала удалить все связанные Rate, затем удалить Role. Это проще, безопаснее и явнее.

## Проблема 10: Rate без привязки к Role и Work

**Статус:** ЗАКРЫТО

**Раздел ТЗ:** Раздел 2.3 "Rate"

**Описание:** ТЗ определяет `roleId` и `workId` как опциональные поля Rate. Это означает, что Rate может существовать без привязки ни к Role, ни к Work. Такая Rate -- "базовая ставка по умолчанию"?

**Вопрос:** Какова бизнес-семантика Rate без привязки? Как TimesheetContext выбирает применимую Rate при создании Ticket, если существуют Rate с разной степенью специфичности (по Role, по Work, по обоим, без привязки)?

**Примечание:** Этот вопрос выходит за рамки домена Work Catalog и касается логики TimesheetContext. Однако ответ на него может повлиять на валидацию при создании Rate.

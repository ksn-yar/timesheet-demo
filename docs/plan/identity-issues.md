**Дата:** 2026-03-22
**Основание:** docs/technical-specification-parts/identity.md (v1.1)

## Проблема 1: Отсутствие механизма установки пароля при создании User

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 2.1 "User", Раздел 3 "UC-ID-01", Раздел 4 "Правила безопасности"

**Описание:** ТЗ указывает, что «пароль хранится в виде хэша с солью, никогда не в открытом виде» (раздел 2.1), и что аутентификация пользователей -- одна из ключевых обязанностей домена (раздел 1). Однако UC-ID-01 (Создать User) не включает пароль во входные данные и не описывает механизм его установки.

**Варианты решения:**
1. Admin задаёт пароль при создании User (пароль включается в `CreateUser` API).
2. Система генерирует временный пароль и возвращает его Admin (или отправляет по email).
3. При создании User отправляется ссылка на установку пароля (invite flow).

**Рекомендация:** Вариант 1 -- наиболее простой для MVP. Пароль передаётся в `CreateUserRequestDto`, хэшируется через `PasswordHasherInterface`, в ответе API не возвращается. В будущем можно добавить invite flow.

**Решение:** Применён вариант 3: invite flow — при создании User Admin задаёт пароль, система хэширует его через `PasswordHasherInterface`. В v1.2 ТЗ добавлен атрибут `passwordHash` в модель User и шаг хэширования в UC-ID-01.

## Проблема 2: Отсутствие Use Case для аутентификации (Login)

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 1 "Цель домена", все API-операции "требуют аутентификации"

**Описание:** ТЗ указывает, что домен Identity отвечает за «аутентификацию пользователей при входе в систему» (раздел 1). Все API-операции требуют аутентификации (раздел 5). Однако в ТЗ отсутствует Use Case для входа в систему (Login), а также не определены:
- Механизм аутентификации (JWT, Session, API Key)
- API-эндпоинт для входа/выхода
- Формат токена и время жизни
- Механизм обновления токена (refresh)

**Рекомендация:** Определить механизм аутентификации (рекомендуется JWT для stateless API). Добавить Use Cases: `LoginUseCase`, `LogoutUseCase`, `RefreshTokenUseCase`. Добавить API-эндпоинты: `POST /auth/login`, `POST /auth/logout`, `POST /auth/refresh`.

**Решение:** Выбрана statefull система с сессиями, аутентификация по логину и паролю (продукт работает только внутри корпоративной VPN). Добавлены UC-ID-10 (Login), UC-ID-11 (Logout), эндпоинты `POST /auth/login` и `POST /auth/logout`. RefreshToken не требуется при сессионной модели.

## Проблема 3: Отсутствие Use Case для обновления User (Update)

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 3 "Use Cases", Раздел 5 "API-интерфейсы"

**Описание:** В ТЗ определены Use Cases для создания, деактивации, назначения в Group и soft-delete User, но нет Use Case для обновления атрибутов User (имя, системная роль, функциональная Role). Также нет соответствующего API-эндпоинта в разделе 5.

Без Update-операции невозможно:
- Исправить опечатку в имени пользователя
- Изменить системную роль (повышение/понижение)
- Назначить или сменить функциональную Role (roleId)

**Рекомендация:** Добавить UC-ID-09 "Обновить User" и API-эндпоинт `PUT /identity/users/{id}`. Изменяемые поля: `name`, `systemRole`, `roleId`. Поле `email` -- неизменяемо (является логином). `groupId` изменяется через отдельные UC-ID-03 / UC-ID-07.

**Решение:** Добавлен UC-ID-08 "Обновить User" (с учётом перенумерации), эндпоинт `PUT /identity/users/{id}`. Изменяемые поля: `name`, `systemRole`, `roleId`. Email неизменяем. Добавлено событие `UserUpdated`.

## Проблема 4: Отсутствие Use Case для обновления Group (Update)

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 3 "Use Cases", Раздел 5 "API-интерфейсы"

**Описание:** В ТЗ определены Use Cases для создания и soft-delete Group, но нет Use Case для обновления атрибутов Group (наименование, описание).

**Рекомендация:** Добавить UC-ID-10 "Обновить Group" и API-эндпоинт `PUT /identity/groups/{id}`. Изменяемые поля: `name` (с проверкой уникальности), `description`. PUT-семантика: переданные поля обновляются; не переданные остаются; явный `null` для `description` очищает значение.

**Решение:** Добавлен UC-ID-09 "Обновить Group" (с учётом перенумерации), эндпоинт `PUT /identity/groups/{id}`. Проверка уникальности `name`. Явный `null` для `description` очищает значение. Добавлено событие `GroupUpdated`.

## Проблема 5: Дублирование UC-ID-03 и UC-ID-07

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 3, UC-ID-03 "Назначить User в Group", UC-ID-07 "Изменить принадлежность User к Group"

**Описание:** UC-ID-03 и UC-ID-07 выполняют по сути одну и ту же операцию -- изменение `groupId` у User. UC-ID-03 описывает назначение User в Group, а UC-ID-07 описывает изменение или снятие привязки. Разница:
- UC-ID-03: назначает в Group (groupId обязателен), публикует `UserAssignedToGroup`
- UC-ID-07: назначает новую Group **или** снимает привязку (groupId опционален), **не публикует** событие

Вопросы:
1. Нужно ли отдельное событие для UC-ID-07 (например, `UserGroupChanged`)?
2. Можно ли объединить UC-ID-03 и UC-ID-07 в один Use Case с опциональным `groupId`?

**Рекомендация:** Объединить в один Use Case `ChangeUserGroupUseCase` с опциональным `groupId`. Если `groupId` передан -- назначить; если `null` -- снять. Один API-эндпоинт `PUT /identity/users/{id}/group`. Событие `UserAssignedToGroup` при назначении, отдельное событие `UserRemovedFromGroup` при снятии.

**Решение:** UC-ID-03 и UC-ID-07 объединены в один UC-ID-03 "Изменить принадлежность User к Group" с опциональным `groupId`. Эндпоинт `PUT /identity/users/{id}/group`. При назначении публикуется `UserAssignedToGroup`, при снятии — `UserRemovedFromGroup`.

## Проблема 6: Нумерация Use Cases нарушена

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 3

**Описание:** UC-ID-07 (Изменить принадлежность User к Group) расположен после UC-ID-08 (Удалить Group). Нумерация нарушена: UC-ID-08 идёт перед UC-ID-07 в тексте ТЗ. Это косметическая проблема, не влияющая на реализацию.

**Решение:** Нумерация исправлена. Use Cases перенумерованы в v1.2 ТЗ в логическом порядке: UC-ID-01..15. Старые UC-ID-07 и UC-ID-08 объединены в UC-ID-03 (см. Проблема 5).

## Проблема 7: Отсутствие события при soft-delete Group

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 7 "Публикуемые события"

**Описание:** В разделе 7 перечислены 4 события: `UserCreated`, `GroupCreated`, `UserAssignedToGroup`, `UserDeactivated`. Отсутствует событие для soft-delete Group (UC-ID-08). Также отсутствует событие для soft-delete User (UC-ID-06).

По аналогии с доменом ProjectManagement, где все операции (create, update, delete) покрыты доменными событиями, необходимо добавить:
- `UserDeleted` -- триггер: soft-delete User (UC-ID-06)
- `GroupDeleted` -- триггер: soft-delete Group (UC-ID-08)

Без этих событий аудит-логирование (НФТ-Б-06) не сможет зафиксировать операции удаления.

**Рекомендация:** Добавить `UserDeleted` (поля: `userId`) и `GroupDeleted` (поля: `groupId`).

**Решение:** Добавлены события `UserDeleted` (поля: `userId`) и `GroupDeleted` (поля: `groupId`) в раздел 7. Соответствующие шаги публикации добавлены в UC-ID-06 и UC-ID-07.

## Проблема 8: Отсутствие Use Case для смены пароля

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 2.1 "User", Раздел 4 "Правила безопасности"

**Описание:** ТЗ требует хранение паролей в хэшированном виде, но не определяет механизм смены пароля. Сотрудник не может самостоятельно изменить свой пароль. Admin не может сбросить пароль пользователя.

**Рекомендация:** Добавить два Use Cases:
- `ChangePasswordUseCase` -- пользователь меняет свой пароль (текущий + новый)
- `ResetPasswordUseCase` -- Admin сбрасывает пароль пользователя (генерация временного пароля)

**Решение:** Добавлены UC-ID-12 "Сменить пароль" (пользователь вводит текущий + новый пароль) и UC-ID-13 "Сбросить пароль пользователя" (Admin задаёт новый пароль). Соответствующие эндпоинты добавлены в раздел 5.

## Проблема 9: Поле roleId -- неясность при отсутствии домена WorkCatalog

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 2.1 "User", Раздел 8 "Зависимости от других доменов"

**Описание:** User содержит опциональную ссылку `roleId` на функциональную Role из WorkCatalogContext. На момент реализации домена Identity домен WorkCatalog может быть ещё не реализован. Вопросы:
1. Нужно ли валидировать существование Role при создании/обновлении User?
2. Что делать, если WorkCatalog ещё не реализован?

**Рекомендация:** На данном этапе хранить `roleId` как строку (UUID) без валидации существования в WorkCatalog. Добавить валидацию формата UUID. Валидация существования Role будет добавлена после реализации WorkCatalog через порт (ACL).

**Решение:** В v1.2 ТЗ зафиксировано: `roleId` хранится как UUID без валидации существования в WorkCatalog. Валидируется только формат UUID. Добавлено бизнес-правило БП-05. Будущая интеграция через ACL описана в разделе 8.

## Проблема 10: User List -- требование к отображению roleName без реализации WorkCatalog

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 6 "Read Models"

**Описание:** Раздел 6 требует, чтобы User List возвращал «наименования связанных Group и Role (а не только идентификаторы)». Однако Role принадлежит WorkCatalogContext, который может быть ещё не реализован.

**Рекомендация:** На данном этапе User List возвращает `roleId` как идентификатор и `roleName = null`. После реализации WorkCatalog -- добавить JOIN или отдельный запрос к Role через Persistence для получения `roleName`.

**Решение:** Раздел 6 обновлён: User List возвращает `roleId` и `roleName = null` до реализации WorkCatalog. После реализации WorkCatalog — `roleName` заполняется через JOIN или запрос через Persistence.

## Проблема 11: Проверка при удалении Role из WorkCatalog

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 8 "Зависимости от других доменов"

**Описание:** ТЗ указывает: «WorkCatalogContext запрашивает IdentityContext для проверки, есть ли пользователи с данной `roleId`». Это означает, что Identity должен предоставить метод/порт для проверки `hasUsersWithRoleId(roleId): bool`.

**Рекомендация:** Добавить метод `countActiveUsersByRoleId(string $roleId): int` в `UserRepositoryInterface`. Реализовать его в `UserRepository`. Предоставить API-эндпоинт или использовать прямой запрос через Persistence (аналогично `hasTicketsForTask` в ProjectManagement).

**Решение:** Раздел 8 обновлён: Identity предоставляет метод `countActiveUsersByRoleId(string $roleId): int` в `UserRepositoryInterface`, реализованный в `UserRepository` через Persistence (без дополнительного API-эндпоинта).

## Проблема 12: Отсутствие операции "Получить User по ID" (Get User)

**Статус:** ЗАКРЫТ

**Раздел ТЗ:** Раздел 5 "API-интерфейсы"

**Описание:** В ТЗ определён только User List, но нет API-эндпоинта для получения одного User по ID (`GET /identity/users/{id}`). Аналогично для Group -- нет `GET /identity/groups/{id}`.

Это может потребоваться для:
- Просмотра профиля пользователя
- Получения актуальных данных User после обновления
- Подписчикам событий для запроса полных данных сущности

**Рекомендация:** Добавить API-эндпоинты `GET /identity/users/{id}` и `GET /identity/groups/{id}`. Добавить Use Cases: `GetUserUseCase`, `GetGroupUseCase`.

**Решение:** Добавлены UC-ID-14 "Получить User по ID" и UC-ID-15 "Получить Group по ID". Эндпоинты `GET /identity/users/{id}` и `GET /identity/groups/{id}` добавлены в раздел 5 с правами Admin, Manager.

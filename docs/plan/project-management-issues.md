## Проблема 1: Отсутствие Use Case для удаления CR

**Статус:** РЕШЕНО (ТЗ v1.1)

**Раздел ТЗ:** Раздел 3 "Use Cases", UC-PM-12

**Решение:** В ТЗ v1.1 добавлен UC-PM-12 "Удалить CR (Soft-delete)" и UC-PM-14 "Получить CR List". CR удаляется через soft-delete (`deletedAt`). CR List добавлен как отдельный эндпоинт.

## Проблема 3: Неясность проверки Ticket при удалении Task

**Статус:** РЕШЕНО (ТЗ v1.1)

**Раздел ТЗ:** Раздел 2.4 "Task", Раздел 3 "UC-PM-13", Раздел 4 "ИН-07"

**Цитата (v1.1):** "Task не может быть удалена, если к ней привязаны Ticket. Проверка выполняется через Persistence (прямой запрос к базе данных)."

**Решение:** В ТЗ v1.1 явно указано, что проверка выполняется через **Persistence** -- прямой запрос к базе данных, без межсервисных вызовов. Реализуется как метод `hasTicketsForTask()` в `TaskRepositoryInterface` / `DoctrineTaskRepository`.

## Проблема 4: Удаление Client -- только активные Projects или все?

**Статус:** РЕШЕНО (ТЗ v1.1)

**Раздел ТЗ:** Раздел 2.1 "Client", Раздел 3 "UC-PM-10", Раздел 4 "ИН-05"

**Решение:** В ТЗ v1.1 удаление Client реализовано как **Soft-delete**: запись не удаляется физически, поле `deletedAt` устанавливается в текущее время. Все исторические данные (Project, Task, CR, Ticket) сохраняются. Инвариант ИН-05 сохранён: Client не может быть помечен удалённым при наличии активных Project. Проблема "осиротевших" данных снята -- данные остаются на месте.

**Раздел ТЗ:** Раздел 9, НФТ-Б-06, Раздел 9.1

**Решение:** В ТЗ v1.1 добавлен раздел 9.1 "Механизм аудит-логирования". Определён механизм:

## Проблема 8: Отсутствие `description` в событии `ClientCreated`

**Статус:** РЕШЕНО / ЗАКРЫТО

**Раздел ТЗ:** Раздел 7 "Публикуемые события"

**Решение:** События содержат только те поля, которые указаны в ТЗ -- это намеренное решение. Минимальный контракт событий позволяет снизить связность между контекстами. Подписчик при необходимости запрашивает полные данные сущности через API.

## Проблема 9: Неоднозначность подсчёта CR при удалении Project (UC-PM-11)

**Статус:** РЕШЕНО (ТЗ v1.2, план v1.2)

**Раздел ТЗ:** Раздел 2.2 "Project", Раздел 2.3 "CR", Раздел 3 "UC-PM-12", Раздел 4 "ИН-05, ИН-06, ИН-08"

**Решение в ТЗ:** В ТЗ v1.2 все инварианты и ограничения уточнены: везде явно указано условие «активный (не удалённый, `deletedAt IS NULL`)»:
- ИН-05: Client не может быть помечен удалённым, если к нему привязан хотя бы один **активный** (не удалённый, `deletedAt IS NULL`) Project.
- ИН-06: Project не может быть помечен удалённым, если к нему привязана хотя бы одна **активная** Task или хотя бы один **активный** CR.
- ИН-08: CR не может быть помечен удалённым, если к нему привязана хотя бы одна **активная** Task.
- Ограничение Project (раздел 2.2) и ограничение CR (раздел 2.3) также уточнены.
- UC-PM-12 (удаление CR): шаг 2 теперь явно содержит «активных (не удалённых) Task».

**Изменения в плане:** Методы репозиториев переименованы для явного указания на подсчёт активных записей: `countActiveTasksByProjectId()`, `countActiveChangeRequestsByProjectId()`, `countActiveTasksByChangeRequestId()`. В описании UC Soft-delete для Project и Client добавлены уточнения: проверяются только активные записи (`deletedAt IS NULL`).

## Проблема 10: Отсутствие событий для операций обновления и soft-delete

**Статус:** РЕШЕНО (ТЗ v1.2, план v1.2)

**Раздел ТЗ:** Раздел 7 "Публикуемые события"

**Решение в ТЗ:** В ТЗ v1.2 в раздел 7 добавлены 8 новых доменных событий с минимальным форматом (только id сущности, по аналогии с уже существующими событиями создания):
- `ClientUpdated` — поля: `clientId`
- `ClientDeleted` — поля: `clientId`
- `ProjectUpdated` — поля: `projectId`
- `ProjectDeleted` — поля: `projectId`
- `ChangeRequestUpdated` — поля: `changeRequestId`
- `ChangeRequestDeleted` — поля: `changeRequestId`
- `TaskUpdated` — поля: `taskId`
- `TaskDeleted` — поля: `taskId`

Все операции (create, update, delete) теперь покрыты доменными событиями, что обеспечивает работу аудит-логирования через Event Listener согласно разделу 9.1.

**Изменения в плане:** Добавлены 8 файлов событий в структуру (`Domain/Event/`). В раздел 6.1 добавлены все 12 событий с полями и триггерами. В описания всех Update и Delete UC добавлен шаг публикации соответствующего события. В описания Create UC добавлен шаг публикации Created-события. `AuditLogEventListener` обновлён для обработки всех 12 событий. Тесты дополнены проверкой публикации событий.

## Проблема 11: API Update -- семантика частичного обновления (PATCH vs PUT)

**Статус:** РЕШЕНО (ТЗ v1.2, план v1.2)

**Раздел ТЗ:** Раздел 5 "API-интерфейсы"

**Решение в ТЗ:** В ТЗ v1.2 в начале раздела 5 добавлены правила:
- HTTP-метод для всех Update-операций — **PUT**.
- Переданные поля обновляются; не переданные поля остаются без изменений.
- Явная передача `null` для опционального поля (`description`, `estimate`) очищает его значение.
- Пустое тело запроса (ни одно поле не передано) — запрос принимается без изменений, ответ HTTP 200/204.

Во всех строках таблиц API обозначение Update-операций дополнено указанием метода «(PUT)», а для опциональных полей добавлено пояснение «`null` — очистить».

**Изменения в плане:** В описания всех Update UC добавлена пометка «(PUT-семантика)» и шаг с правилами: переданные поля обновляются; не переданные остаются без изменений; явный `null` для `description`/`estimate` очищает поле; пустое тело -- 200/204 без изменений. Таблица HTTP-эндпоинтов уже использовала метод PUT.

## Проблема 12: Несогласованность предусловий Update UC для Project и Task

**Статус:** РЕШЕНО (ТЗ v1.3, план v1.3)

**Раздел ТЗ:** Раздел 3, UC-PM-06, UC-PM-07, UC-PM-08, UC-PM-09; Раздел 4, ИН-09

**Описание:** UC-PM-06 (Обновить Client) и UC-PM-08 (Обновить CR) содержали предусловие «не помечен удалённым», однако UC-PM-07 (Обновить Project) и UC-PM-09 (Обновить Task) такого предусловия не содержали. При этом все четыре сущности поддерживают soft-delete (`deletedAt`).

**Решение в ТЗ v1.3:**
- UC-PM-06: уточнено предусловие до «`deletedAt IS NULL`»; добавлен альтернативный сценарий 0a — «Client помечен удалённым → ошибка "Сущность удалена и не может быть изменена"».
- UC-PM-07: добавлено предусловие «не помечен удалённым (`deletedAt IS NULL`)»; добавлен альтернативный сценарий 0a — «Project помечен удалённым → ошибка "Сущность удалена и не может быть изменена"».
- UC-PM-08: уточнено предусловие до «`deletedAt IS NULL`»; добавлен альтернативный сценарий 0a — «CR помечен удалённым → ошибка "Сущность удалена и не может быть изменена"».
- UC-PM-09: добавлено предусловие «не помечена удалённой (`deletedAt IS NULL`)»; добавлен альтернативный сценарий 0a — «Task помечена удалённой → ошибка "Сущность удалена и не может быть изменена"».
- Раздел 4 (инварианты): добавлен ИН-09 — «Нельзя изменять (Update) сущность, помеченную удалённой (`deletedAt IS NOT NULL`)».

**Изменения в плане v1.3:**
- Добавлено доменное исключение `EntityDeletedException` в структуру файлов (`Domain/Exception/EntityDeletedException.php`), таблицу исключений (раздел 7) и шаг 1.3 порядка реализации. Исключение -- единое для всех сущностей, сообщение: «Сущность удалена и не может быть изменена».
- Во всех четырёх Update Use Cases (UpdateClient, UpdateProject, UpdateChangeRequest, UpdateTask) шаг 2 уточнён: при `deletedAt IS NOT NULL` выбрасывается `EntityDeletedException` с явной ссылкой на ИН-09.
- Тесты Update UC обновлены: проверка выброса `EntityDeletedException` при попытке обновить удалённую сущность.

## Проблема 13: Plan v1.1 -- отсутствие soft-delete для Project и Task

**Статус:** РЕШЕНО (план v1.2)

**Раздел ТЗ:** Раздел 2.2 "Project", Раздел 2.4 "Task", Раздел 3 UC-PM-11, UC-PM-13

**Описание:** ТЗ явно определяет soft-delete для всех 4 сущностей (Client, Project, CR, Task): поле `deletedAt`, физическое удаление не происходит. Однако план v1.1 реализовывал Project и Task через `remove()` (физическое удаление), а Domain Entity Project и Task не имели атрибута `deletedAt` и методов `softDelete()`/`isDeleted()`. Persistence Entity Project и Task не имели колонки `deleted_at`.

**Решение в плане:** В план v1.2 внесены исправления:
- Domain Entity Project и Task: добавлены `deletedAt`, `softDelete()`, `isDeleted()`
- Persistence Entity Project и Task: добавлена колонка `deleted_at` с индексом
- DeleteProjectUseCase и DeleteTaskUseCase: заменён `remove()` на `softDelete()` + `save()`
- Все репозитории: `findAll` фильтрует по `deleted_at IS NULL`
- Тесты обновлены для проверки soft-delete поведения

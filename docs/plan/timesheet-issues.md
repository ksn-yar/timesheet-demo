# Вопросы и неточности к ТЗ домена Timesheet

**Дата:** 2026-03-22
**Основание:** docs/technical-specification-parts/timesheet.md (v1.0)

---

## Проблема 1: Отсутствие поля externalId в сущности Ticket

**Статус:** ЗАКРЫТО (решено в плане v1.1)

**Раздел ТЗ:** Раздел 2.1 "Ticket", Раздел 2.3 "Import Log Entry", Раздел 3 "UC-TS-05"

**Описание:** ТЗ описывает механизм дедупликации при импорте: "дубликаты определяются по паре (`importSource` + внешний идентификатор записи)". Однако в атрибутах сущности Ticket (раздел 2.1) отсутствует поле для хранения внешнего идентификатора записи (`externalId`). Поле `importSource` хранит идентификатор *источника* (внешней системы), но не идентификатор *конкретной записи* в этой системе.

**Почему это важно:**
- Без `externalId` невозможно реализовать проверку дубликатов при импорте (инвариант ИН-20).
- Невозможно обеспечить идемпотентность импорта (НФТ-Н-05).

**Решение:** В плане реализации v1.1 добавлено поле `externalId: ?string` (условно обязательное -- заполняется только для Imported Ticket) в доменную сущность Ticket и колонка `external_id` в Doctrine Entity. Создан composite unique index на `(import_source, external_id)` WHERE `import_source IS NOT NULL`.

## Проблема 2: Неопределённое поведение при отсутствии Rate

**Статус:** ЗАКРЫТО (решено в ТЗ и плане v1.1)

**Раздел ТЗ:** Раздел 3 "UC-TS-01", альтернативный сценарий 4a

**Описание:** В ранней версии ТЗ поведение при отсутствии актуальной Rate было неопределённым. В актуальной версии ТЗ однозначно указано: "Для данной комбинации Employee/Work нет актуальной Rate -- система фиксирует `rateSnapshot = 0`. Создание Ticket не блокируется."

**Решение:** ТЗ обновлено, неопределённости нет. `RateProviderInterface::getCurrentRate()` возвращает `'0'` при отсутствии Rate.

---

## Проблема 3: Алгоритм определения актуальной Rate не специфицирован

**Статус:** ЗАКРЫТО (решено в плане v1.1)

**Раздел ТЗ:** Раздел 2.1 "Ticket", Раздел 3 "UC-TS-01", Раздел 8 "Зависимости"

**Описание:** ТЗ указывает, что система "запрашивает актуальное значение Rate из WorkCatalogContext", но не описывает алгоритм выбора Rate.

**Решение:** Алгоритм определения Rate делегируется в `RateProviderInterface` (Application Port). Реализация `DoctrineRateProvider` использует приоритетную цепочку: Work+Role > Work > Role > базовая ставка, с учётом `effectiveFrom <= date`. Timesheet-домен не знает о деталях алгоритма.

---

## Проблема 4: Отсутствие операции удаления Ticket

**Статус:** ЗАКРЫТО (решено в плане v1.1 -- отложено)

**Раздел ТЗ:** Раздел 3 "Use Cases", Раздел 5 "API-интерфейсы"

**Описание:** ТЗ определяет операции создания и редактирования Manual Ticket, но не определяет операцию удаления.

**Решение:** Удаление Ticket не реализуется в первой версии. С точки зрения аудита и целостности данных запрет на удаление оправдан. Если потребуется в будущем -- будет добавлено отдельным UC.

## Проблема 5: Фильтрация Ticket List по projectId и crId -- межконтекстная зависимость

**Статус:** ЗАКРЫТО (решено в плане v1.1)

**Раздел ТЗ:** Раздел 3 "UC-TS-03", Раздел 5 "API-интерфейсы", Раздел 6 "Read Models"

**Описание:** Ticket List поддерживает фильтрацию по `projectId` и `crId`, однако Ticket не содержит этих полей напрямую. Связь идёт через `taskId` -> Task -> Project/CR (данные из ProjectManagementContext).

**Решение:** Принят вариант A (JOIN через Persistence) -- прямые SQL-запросы через таблицы другого контекста. Архитектурный компромисс для монолитного приложения с единой БД. Реализуется через специализированные методы в Doctrine Repository.

**Раздел ТЗ:** Раздел 3 "Use Cases"

**Описание:** В техническом задании (docs/technical-specification-parts/timesheet.md) и в контекстном описании Use Cases нумеруются по-разному.

**Решение:** Нумерация из ТЗ (docs/technical-specification-parts/timesheet.md) принята как каноническая.

## Проблема 7: Отсутствие событий для операций Update

**Статус:** ЗАКРЫТО (решено в плане v1.1)

**Раздел ТЗ:** Раздел 7 "Публикуемые события"

**Описание:** ТЗ определяет только два доменных события: `TicketsAdded` и `TicketsImported`. При этом система поддерживает операции обновления Ticket (UC-TS-02) и обновления Import Policy (UC-TS-06). Для этих операций события не определены.

**Почему это важно:**
- НФТ-Б-06 требует логирования административных операций. Без событий для Update аудит-логирование через Event Listener невозможно для операций обновления.

**Решение:** В плане v1.1 добавлены события: `TicketUpdated`, `ImportPolicyCreated`, `ImportPolicyUpdated`.

## Проблема 8: Можно ли при редактировании Manual Ticket изменить taskId?

**Статус:** ЗАКРЫТО (решено в плане v1.1)

**Раздел ТЗ:** Раздел 3 "UC-TS-02", Раздел 5 "API-интерфейсы"

**Описание:** В описании UC-TS-02 перечислены допустимые для изменения поля: `date`, `hours`, `workId`, `comment`. Поле `taskId` отсутствует в этом списке.

**Решение:** Принято как осознанное ограничение ТЗ -- `taskId` нельзя менять при редактировании. Это зафиксировано в плане реализации. Если потребуется исправление ошибочной привязки, Admin может обратиться к инструментам прямого доступа к БД (административная операция вне scope домена).

---

## Проблема 9: Структура mappingRules не специфицирована

**Статус:** ЗАКРЫТО (решено в ТЗ)

**Раздел ТЗ:** Раздел 2.2 "Import Policy"

**Описание:** В ранней версии ТЗ поле `mappingRules` было определено как JSON без спецификации структуры. В актуальной версии ТЗ (раздел 2.2) структура полностью описана: обязательные ключи `employeeMapping`, `taskMapping`, `workMapping`, `dateField`, `hoursField`, `commentField`, `externalIdField` с указанием типов и допустимых значений `matchBy`.

**Решение:** Неопределённость устранена в ТЗ. На первом этапе `mappingRules` сохраняется как произвольный JSON без строгой валидации структуры (`ExternalDataFetcherInterface` реализован как `NullExternalDataFetcher`). Валидация структуры добавляется при подключении реальных внешних систем (см. примечание в ТЗ, раздел 2.2).

## Проблема 10: Неоднозначность: Manager может ли редактировать Ticket?

**Статус:** ЗАКРЫТО (решено в плане v1.1)

**Раздел ТЗ:** Раздел 3 "UC-TS-02", Раздел 5 "API-интерфейсы"

**Описание:** В ТЗ домена Timesheet акторами для "Обновить Manual Ticket" указаны: "Employee (автор), Admin". Manager не упоминается.

**Решение:** Принято как осознанное: Manager наблюдает, но не редактирует. При необходимости Manager обращается к Admin для исправления. Соответствует матрице прав в ТЗ.

## Проблема 11: Отсутствие операции "Получить Ticket по ID"

**Статус:** ЗАКРЫТО (решено в плане v1.1)

**Раздел ТЗ:** Раздел 5 "API-интерфейсы"

**Описание:** ТЗ определяет Create, Update и List для Ticket, но не определяет операцию получения одного Ticket по ID (`GET /api/timesheet/tickets/{id}`).

**Решение:** В плане v1.1 добавлены `GetTicketUseCase`, `GetTicketController`, `GetTicketInputDto`, `GetTicketInputTransformer` и эндпоинт `GET /api/timesheet/tickets/{id}` с проверкой прав (Employee -- только свой; Manager, Admin -- любой).

## Проблема 12: Именование событий -- множественное число TicketsAdded

**Статус:** ЗАКРЫТО (принято как есть)

**Раздел ТЗ:** Раздел 7 "Публикуемые события"

**Описание:** Событие названо `TicketsAdded` (множественное число), но в UC-TS-01 описывается создание одного Ticket.

**Решение:** Именование `TicketsAdded` сохранено из ТЗ как есть. Если в будущем потребуется batch-создание, именование будет уже подходящим. Новые события (`TicketUpdated`, `ImportPolicyCreated`, `ImportPolicyUpdated`) именуются в единственном числе, так как они однозначно относятся к одной сущности.

## Проблема 13: Путь контроллеров не соответствует проектному соглашению

**Статус:** ЗАКРЫТО (решено в плане v1.1)

**Описание:** В исходном плане v1.0 контроллеры размещались в `Infrastructure/Controller/`, тогда как по проектному соглашению путь должен быть `Infrastructure/Http/Controller/`.

**Решение:** В плане v1.1 путь исправлен на `Infrastructure/Http/Controller/`, что соответствует соглашению из `project_architecture.md`.

## Проблема 14: ImportLogEntry использует строковый статус вместо типизированного Enum

**Статус:** ЗАКРЫТО (решено в плане v1.1)

**Описание:** В исходном плане v1.0 `ImportLogEntry` принимал `string $status` с ограничением на значения `imported`, `duplicate`, `error`. Это нетипобезопасно и не соответствует паттерну проекта, где статусы моделируются через Enum.

**Решение:** В плане v1.1 добавлен `ImportLogEntryStatus` enum (`Imported`, `Duplicate`, `Error`). `ImportLogEntry` теперь принимает `ImportLogEntryStatus $status` вместо строки.

## Проблема 15: Аудит-логирование покрывает не все операции

**Статус:** ЗАКРЫТО (решено в плане v1.1)

**Описание:** В исходном плане v1.0 аудит-лог фиксировал только два типа действий: `create` и `import`. Операции обновления (`update`) не логировались, что нарушало НФТ-Б-06 (логирование административных операций).

**Решение:** В плане v1.1 аудит-лог расширен: тип действия включает `create`, `update`, `import`. `AuditLogEventListener` подписан на все 5 доменных событий.

---

## Проблема 16: Отсутствие Resolver Port-интерфейсов для импорта

**Статус:** ЗАКРЫТО (решено в плане v1.2)

**Раздел ТЗ:** Раздел 2.2 "Import Policy" (mappingRules), Раздел 3 "UC-TS-05"

**Описание:** В плане v1.1 `RunImportUseCase` описывал шаг 4b "Сопоставление employeeId, taskId, workId с внутренними идентификаторами" через `TaskExistenceCheckerInterface` и `WorkExistenceCheckerInterface`. Однако ExistenceChecker проверяет только наличие сущности по UUID, а при импорте сопоставление выполняется по внешним идентификаторам (email, externalId, name), как определено в `mappingRules.matchBy`.

**Почему это важно:**
- `TaskExistenceCheckerInterface::taskExists(string $taskId): bool` принимает UUID, но при импорте входящая запись содержит внешний идентификатор (name или externalId), а не UUID.
- Без специализированных Resolver-ов невозможно трансформировать внешние идентификаторы во внутренние UUID.

**Решение:** В плане v1.2 добавлены Port-интерфейсы `EmployeeResolverInterface`, `TaskResolverInterface`, `WorkResolverInterface` с методом `resolve(string $value, string $matchBy): ?string`. Реализации `DoctrineEmployeeResolver`, `DoctrineTaskResolver`, `DoctrineWorkResolver` выполняют поиск по заданному полю и возвращают UUID.

## Проблема 17: Отсутствие externalId в TicketResponseDto

**Статус:** ЗАКРЫТО (решено в плане v1.2)

**Раздел ТЗ:** Раздел 2.1 "Ticket", Раздел 5 "API-интерфейсы"

**Описание:** В плане v1.1 `TicketResponseDto` не содержал поля `externalId`, хотя для Imported Ticket это поле хранится в сущности. Без него невозможно идентифицировать Imported Ticket в контексте исходной внешней системы.

**Решение:** В плане v1.2 добавлено поле `externalId` в `TicketResponseDto`.

## Проблема 18: Метод isEmployee() отсутствует в CurrentUserProviderInterface

**Статус:** ЗАКРЫТО (решено в плане v1.2)

**Раздел ТЗ:** Раздел 3 "UC-TS-01, UC-TS-02, UC-TS-03", Раздел 5 "API-интерфейсы"

**Описание:** В плане v1.1 `CurrentUserProviderInterface` определял методы `getCurrentUserId(): string`, `getCurrentUserRole(): string`, `isAdmin(): bool`. Для проверки прав в Use Cases нужно различать Employee, Manager и Admin, но методы `isEmployee()` и `isManager()` отсутствовали, что вынуждало сравнивать строковые значения ролей.

**Решение:** В плане v1.2 добавлены методы `isEmployee(): bool` и `isManager(): bool` в `CurrentUserProviderInterface` для единообразия с `isAdmin()`.

## Проблема 19: UpdateImportPolicy не позволяет изменить name

**Статус:** ЗАКРЫТО (осознанное ограничение ТЗ)

**Раздел ТЗ:** Раздел 5 "API-интерфейсы"

**Описание:** В ТЗ операция "Обновить Import Policy" допускает изменение только `mappingRules`, `allowEdit`, `isActive`. Поле `name` не включено в список изменяемых полей, хотя это может быть неудобно для администратора (например, при опечатке в названии).

**Решение:** Принято как осознанное ограничение ТЗ. Если потребуется изменение `name`, это будет добавлено как отдельное обновление ТЗ.

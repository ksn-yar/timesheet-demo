## 1. Назначение и цели системы

**corpo-timesheet** — локальная корпоративная система учёта рабочего времени. Её назначение состоит в том, чтобы обеспечить прозрачную и структурированную фиксацию фактических трудозатрат сотрудников в разрезе клиентов, проектов и задач.

### Бизнес-цели

| # | Цель | Ценность |
|---|------|----------|
| БЦ-1 | Обеспечить достоверный учёт рабочего времени сотрудников в привязке к конкретным задачам | Основа для расчёта стоимости работ и контроля трудозатрат |
| БЦ-2 | Предоставить руководителям инструмент для анализа и выгрузки отчётов о трудозатратах | Управленческая аналитика, обоснование счетов клиентам |
| БЦ-3 | Поддержать иерархическую структуру клиент — проект — задача | Структурирование работ и корректная тарификация |
| БЦ-4 | Обеспечить возможность автоматического импорта данных из внешних систем | Снижение ручного ввода и ошибок, интеграция с существующими инструментами |
| БЦ-5 | Контролировать доступ к данным в соответствии с ролями пользователей | Конфиденциальность и разграничение ответственности |

### Что система не делает

- Не является системой управления задачами (task tracker) — задачи создаются как справочные объекты для привязки трудозатрат, а не как инструмент планирования.
- Не выставляет счета клиентам — она предоставляет данные, на основе которых это можно сделать.
- Не управляет расписанием и загрузкой сотрудников.

## 2. Целевая аудитория и роли пользователей

Система обслуживает три категории пользователей. Роль определяет как набор доступных действий, так и видимость данных.

### Admin (Администратор)

Управляет конфигурацией всей системы. Является единственной ролью, способной создавать и редактировать справочники и структурные объекты.

**Ключевые права:**
- Создание и ведение клиентов, проектов, Change Request и задач
- Создание и ведение справочников: ставки (Rate), функциональные роли (Role), виды работ (Work)
- Создание пользователей и организационных групп
- Запуск и настройка импорта данных из внешних систем
- Просмотр тикетов любого сотрудника
- Формирование и выгрузка отчётов

### Employee (Сотрудник)

Вносит фактические трудозатраты в систему. Работает только со своими данными.

**Ключевые права:**
- Добавление тикетов вручную за себя
- Просмотр и редактирование своих тикетов (только Manual Ticket)
- Просмотр справочников (Work List, Task List) для выбора при внесении данных

### Manager (Менеджер)

Контролирует ход работ и анализирует трудозатраты команды. Не вносит данные — работает с результатами.

**Ключевые права:**
- Просмотр тикетов по любому сотруднику, проекту, периоду
- Формирование отчётов по заданным параметрам
- Выгрузка отчётов в файлы (CSV, XLSX, PDF)
- Просмотр списков пользователей и групп

### Сводная матрица прав

| Действие | Admin | Manager | Employee |
|----------|:-----:|:-------:|:--------:|
| Управление клиентами / проектами / CR / задачами | + | - | - |
| Управление справочниками (Rate, Role, Work) | + | - | - |
| Управление пользователями и группами | + | - | - |
| Настройка и запуск импорта тикетов | + | - | - |
| Добавление тикетов за себя | + | - | + |
| Добавление тикетов за других | + | - | - |
| Просмотр своих тикетов | + | - | + |
| Просмотр тикетов любого сотрудника | + | + | - |
| Формирование и просмотр отчётов | + | + | - |
| Выгрузка отчётов в файл | + | + | - |

## 3. Бизнес-домены и их функциональность

Система разделена на пять связанных бизнес-доменов (Bounded Context). Каждый домен несёт ответственность за чётко очерченную область данных и правил.

```
┌─────────────────────────────────────────────────────────────────┐
│                        CORPO-TIMESHEET                          │
│                                                                 │
│  [Project Management]  ──────────────────────────────────────┐  │
│  Клиенты, проекты, CR, задачи                                │  │
│                                                              ▼  │
│  [Work Catalog]  ────────────►  [Timesheet]  ────► [Reporting]  │
│  Ставки, роли, виды работ      Тикеты (ядро)       Отчёты       │
│                                      ▲                          │
│  [Identity]  ───────────────────────┘                          │
│  Пользователи и группы                                          │
└─────────────────────────────────────────────────────────────────┘
```

### 3.1 Project Management — управление проектной структурой

**Назначение:** Хранит и предоставляет иерархическую структуру объектов, в рамках которых ведётся учёт трудозатрат. Является структурообразующим доменом.

**Иерархия объектов:**

```
Client (Клиент)
  └── Project (Проект)
        ├── Task (Задача)
        └── CR (Change Request)
              └── Task (Задача)
```

**Функциональность:**

| Функция | Описание |
|---------|----------|
| Ведение клиентов | Создание и хранение записей о клиентах — организациях или лицах, для которых выполняются работы |
| Ведение проектов | Создание проектов в рамках клиента, управление их статусом (Active / Closed) |
| Ведение CR | Создание Change Request — расширений скоупа существующего проекта |
| Ведение задач | Создание задач внутри проекта или CR. Задача — конечная точка иерархии, к которой привязывается тикет |
| Read-модели для других доменов | Предоставление Client List, Project List, Task List для выбора при внесении тикетов и построении отчётов |

**Роль в системе:** upstream-поставщик для Timesheet (Task — обязательная ссылка для любого тикета) и для Reporting (группировка отчётов по Project/CR/Task).

---

### 3.2 Work Catalog — справочник работ и тарификации

**Назначение:** Хранит классификаторы и тарифные ставки. Данные изменяются редко (только Admin) и потребляются остальными доменами в режиме только чтения.

**Функциональность:**

| Функция | Описание |
|---------|----------|
| Ведение ставок (Rate) | Тарифная ставка в единицу времени с привязкой к функциональной роли или виду работ, с датой вступления в силу |
| Ведение функциональных ролей (Role) | Специализация исполнителя (например, Developer, QA, PM). Влияет на тарификацию |
| Ведение видов работ (Work) | Классификатор деятельности (например, Development, Consulting, Testing). Используется при внесении тикетов и группировке в отчётах |
| Work List | Предоставление полного списка доступных видов работ для выбора в других доменах |

**Роль в системе:** upstream-поставщик для Timesheet (Rate фиксируется в момент создания тикета) и для Reporting (Work используется как измерение группировки).

---

### 3.3 Identity — управление пользователями и группами

**Назначение:** Единственный источник истины о том, кто имеет доступ к системе и с какими правами. Управляет учётными записями и организационной структурой.

**Функциональность:**

| Функция | Описание |
|---------|----------|
| Ведение пользователей (User) | Создание учётных записей с указанием имени, email, системной роли и функциональной роли |
| Ведение групп (Group) | Создание организационных групп для разграничения доступа и группировки данных в отчётах |
| Назначение в группу | Отнесение пользователя к группе |
| Деактивация пользователя | Отзыв доступа к системе без удаления исторических данных |
| User List | Предоставление списка пользователей с фильтрацией по группе, роли и статусу активности |

**Роль в системе:** upstream-поставщик для Timesheet (Employee — обязательный атрибут тикета) и для Reporting (группировка по Employee и Group).

---

### 3.4 Timesheet — учёт трудозатрат (ядро системы)

**Назначение:** Основной бизнес-домен. Здесь концентрируется ключевая ценность системы — фиксация фактического времени сотрудников в привязке к задачам проектов. Все остальные домены либо поставляют данные в этот домен, либо потребляют его результаты.

**Функциональность:**

| Функция | Описание |
|---------|----------|
| Ручное добавление тикетов (Manual Ticket) | Employee вносит трудозатраты через форму: выбирает задачу, вид работ, указывает дату, часы и комментарий |
| Редактирование Manual Ticket | Employee может исправить собственный тикет (дата, часы, вид работ, комментарий). Admin может редактировать любой Manual Ticket |
| Импорт тикетов из внешних систем (Imported Ticket) | Автоматическая загрузка данных по правилам Import Policy с трансформацией в формат тикета |
| Настройка политик импорта (Import Policy) | Admin задаёт правила маппинга полей из внешней системы, источник и разрешение на ручное редактирование импортированных тикетов |
| Просмотр Ticket List | Просмотр записей о трудозатратах с фильтрацией по сотруднику, проекту, CR, задаче, виду работ и периоду |

**Два типа тикетов:**

| Тип | Источник | Редактирование |
|-----|----------|----------------|
| Manual Ticket | Ручной ввод сотрудника | Разрешено автором и Admin |
| Imported Ticket | Автоматический импорт из внешней системы | Только если Import Policy явно разрешает (allowEdit = true) |

**Роль в системе:** downstream-потребитель Project Management, Work Catalog и Identity. Upstream-поставщик для Reporting.

---

### 3.5 Reporting — аналитика и выгрузки

**Назначение:** Аналитический домен. Формирует агрегированные представления данных о трудозатратах и предоставляет их руководителям и администраторам в виде отчётов и экспортируемых файлов.

**Функциональность:**

| Функция | Описание |
|---------|----------|
| Формирование отчёта (Report) | Создание снимка агрегированных данных по заданному периоду, фильтрам и измерениям группировки |
| Просмотр Report List | Просмотр ранее сформированных отчётов с мета-информацией (период, автор, дата создания) |
| Выгрузка отчётов (Report Export) | Экспорт одного или нескольких отчётов в файл формата CSV, XLSX или PDF |
| Просмотр Exported Reports List | Доступ к ранее сгенерированным файлам выгрузок |

**Параметры группировки отчётов:** Employee, Group, Project, CR, Task, Work.

**Ключевое бизнес-решение:** Report — это неизменяемый снимок данных на момент формирования. Если данные в тикетах изменились после создания отчёта, для получения актуальной картины необходимо сформировать новый Report.

**Роль в системе:** конечный downstream-потребитель всех остальных доменов.

## 4. Ключевые бизнес-правила и инварианты

Инварианты — правила, которые система должна соблюдать при любых обстоятельствах. Нарушение инварианта недопустимо.

### 4.1 Инварианты иерархии объектов

| # | Правило |
|---|---------|
| ИН-01 | Ticket всегда привязан к Task. |
| ИН-02 | Task всегда принадлежит либо Project, либо CR — не может существовать без родителя. |
| ИН-03 | CR всегда принадлежит ровно одному Project. CR не может быть перенесён в другой Project после создания. |
| ИН-04 | Project всегда принадлежит ровно одному Client. |
| ИН-05 | Client не может быть удалён, если к нему привязан хотя бы один активный Project. |
| ИН-06 | Project не может быть удалён, если к нему привязаны Task или CR. |
| ИН-07 | Task не может быть удалена, если к ней привязаны Ticket. |

### 4.2 Инварианты тарификации

| # | Правило |
|---|---------|
| ИН-08 | Rate фиксируется в момент создания Ticket и не пересчитывается ретроспективно. |
| ИН-09 | Дата вступления в силу (effectiveFrom) у Rate не может быть изменена после того, как ставка была применена хотя бы к одному Ticket. |
| ИН-10 | Сумма Rate должна быть положительным числом. |
| ИН-11 | Наименование Role должно быть уникальным. Role не может быть удалена, если к ней привязаны Rate или пользователи. |
| ИН-12 | Наименование Work должно быть уникальным. Work не может быть удалена, если она использована в существующих Ticket. |

### 4.3 Инварианты доступа к данным

| # | Правило |
|---|---------|
| ИН-13 | Employee может добавлять Ticket только за себя. Добавление тикетов за другого сотрудника доступно только Admin. |
| ИН-14 | Employee может редактировать только собственные Manual Ticket. |
| ИН-15 | Imported Ticket нельзя редактировать вручную, если Import Policy не установила allowEdit = true. |
| ИН-16 | User не может быть удалён физически, если к нему привязаны Ticket. Допускается только деактивация (isActive = false). |
| ИН-17 | Email пользователя должен быть уникальным в системе. |

### 4.4 Инварианты импорта

| # | Правило |
|---|---------|
| ИН-18 | Для одной внешней системы может быть активна только одна Import Policy одновременно. |
| ИН-19 | Изменение Import Policy не пересчитывает ранее импортированные Ticket. |
| ИН-20 | Дубликаты при импорте определяются по паре (importSource + внешний идентификатор записи) и не создаются повторно. |

### 4.5 Инварианты отчётности

| # | Правило |
|---|---------|
| ИН-21 | Данные Report фиксируются как снимок на момент формирования и не обновляются автоматически. |
| ИН-22 | Report не может быть изменён после создания. |
| ИН-23 | PeriodFrom отчёта не может быть позже PeriodTo. |

## 5. User Stories по доменам

### 5.1 Project Management

---

**US-PM-01: Создать клиента**

```
Как Admin,
я хочу создать запись о клиенте,
чтобы иметь возможность привязывать к нему проекты и отслеживать трудозатраты в его разрезе.

Acceptance Criteria:
- Дано: Admin аутентифицирован в системе
  Когда: Admin вводит наименование клиента и нажимает "Создать"
  Тогда: клиент создан и появляется в Client List
- Дано: Admin вводит пустое наименование
  Когда: Admin нажимает "Создать"
  Тогда: система отклоняет запрос с сообщением об ошибке валидации

Definition of Done:
- [ ] Код проверен и слит
- [ ] Acceptance Criteria пройдены
- [ ] Client List обновляется корректно
```

---

**US-PM-02: Создать проект**

```
Как Admin,
я хочу создать проект в рамках существующего клиента,
чтобы структурировать работы и обеспечить корректную группировку трудозатрат.

Acceptance Criteria:
- Дано: существует хотя бы один Client
  Когда: Admin выбирает Client и вводит наименование и статус проекта
  Тогда: Project создан и появляется в Project List данного Client
- Дано: Admin пытается создать Project без выбора Client
  Тогда: система не позволяет завершить создание

Definition of Done:
- [ ] Код проверен и слит
- [ ] Acceptance Criteria пройдены
```

---

**US-PM-03: Создать Change Request**

```
Как Admin,
я хочу создать CR в рамках существующего проекта,
чтобы учитывать трудозатраты по расширениям или изменениям скоупа отдельно от основного проекта.

Acceptance Criteria:
- Дано: существует хотя бы один Project
  Когда: Admin выбирает Project и создаёт CR с наименованием
  Тогда: CR создан и доступен для привязки Task и Ticket
- Дано: CR создан
  Когда: Admin пытается перенести CR в другой Project
  Тогда: система отклоняет операцию (CR неизменно принадлежит исходному Project)

Definition of Done:
- [ ] Код проверен и слит
- [ ] Acceptance Criteria пройдены
```

---

**US-PM-04: Создать задачу**

```
Как Admin,
я хочу создать задачу внутри проекта или CR,
чтобы сотрудники могли указывать конкретную задачу при внесении трудозатрат.

Acceptance Criteria:
- Дано: существует Project или CR
  Когда: Admin создаёт Task с наименованием и опциональным эстимейтом
  Тогда: Task появляется в Task List и доступна для привязки Ticket
- Дано: Task привязана к Ticket
  Когда: Admin пытается удалить Task
  Тогда: система отклоняет удаление

Definition of Done:
- [ ] Код проверен и слит
- [ ] Acceptance Criteria пройдены
```

---

**US-PM-05: Просмотр списков объектов**

```
Как Admin, Manager или Employee,
я хочу просматривать списки клиентов, проектов и задач с возможностью фильтрации,
чтобы быстро находить нужный объект при навигации или привязке тикетов.

Acceptance Criteria:
- Дано: актор открывает Client List
  Тогда: отображаются все клиенты с возможностью поиска по наименованию
- Дано: актор открывает Project List
  Тогда: доступна фильтрация по Client и по статусу (Active / Closed)
- Дано: актор открывает Task List
  Тогда: доступна фильтрация по Project и/или CR

Definition of Done:
- [ ] Код проверен и слит
- [ ] Acceptance Criteria пройдены
```

---

### 5.2 Work Catalog

---

**US-WC-01: Создать вид работ**

```
Как Admin,
я хочу создать классификатор вида работ,
чтобы сотрудники могли указывать тип деятельности при внесении тикетов,
а менеджеры — группировать отчёты по видам работ.

Acceptance Criteria:
- Дано: Admin вводит уникальное наименование вида работ
  Тогда: Work создан и появляется в Work List
- Дано: Admin вводит наименование, которое уже существует
  Тогда: система отклоняет создание с сообщением о дубликате
- Дано: Work используется в существующих Ticket
  Когда: Admin пытается удалить Work
  Тогда: система отклоняет удаление

Definition of Done:
- [ ] Код проверен и слит
- [ ] Acceptance Criteria пройдены
```

---

**US-WC-02: Создать функциональную роль**

```
Как Admin,
я хочу создать функциональную роль исполнителя,
чтобы использовать её при тарификации и назначении пользователям.

Acceptance Criteria:
- Дано: Admin вводит уникальное наименование Role
  Тогда: Role создана и доступна для привязки Rate и назначения пользователям
- Дано: наименование Role не уникально
```

## 6. Глоссарий

Полный единый глоссарий терминов системы ведётся в отдельном документе:

`<project-dir>/docs/UbiquitousLanguage.md`

Все термины в коде, документации и коммуникациях используются строго в соответствии с этим глоссарием, без синонимов и произвольных замен.

### Краткая справка по ключевым терминам

| Термин | Определение |
|--------|-------------|
| **Client** | Организация или лицо, для которого выполняются работы. Верхний уровень иерархии. |
| **Project** | Совокупность работ для Client в рамках договора. Принадлежит одному Client. |
| **CR (Change Request)** | Запрос на изменение скоупа Project. Всегда привязан к Project, не является самостоятельным проектом. |
| **Task** | Единица работы внутри Project или CR. Конечная точка иерархии для привязки Ticket. |
| **Rate** | Тарифная ставка в единицу времени. Фиксируется в Ticket на момент его создания. |
| **Role** | Функциональная роль исполнителя (Developer, QA, PM и т.д.). Влияет на тарификацию. |
| **Work** | Классификатор вида деятельности (Development, Consulting и т.д.). Используется в Ticket и отчётах. |
| **User** | Физическое лицо с доступом к системе. |
| **Group** | Организационная единица, объединяющая User. |
| **Admin** | Системная роль User с правами на управление конфигурацией. Не отдельный агрегат. |
| **Employee** | Контекстная роль User в TimesheetContext — вносит трудозатраты через Ticket. |
| **Manager** | Системная роль User — контролирует и анализирует работы, формирует отчёты. |
| **Ticket** | Запись о затраченном времени Employee на конкретную Task. Основная сущность системы. |
| **Manual Ticket** | Ticket, добавленный вручную через форму. |
| **Imported Ticket** | Ticket, созданный автоматически по правилам Import Policy из внешней системы. |
| **Import Policy** | Набор правил трансформации данных внешней системы в Ticket (Anti-Corruption Layer). |
| **Report** | Агрегированный неизменяемый снимок данных о трудозатратах за период. |
| **Report Export** | Файл (CSV, XLSX, PDF), сгенерированный из Report. Артефакт, не агрегат. |

### Запрещённые синонимы

| Запрещено | Правильный термин |
|-----------|-------------------|
| TimeEntry | Ticket |
| ChangeRequest | CR |
| Worker / Staff | Employee |
| HourlyRate | Rate |
| JobType | Work |
| Log | Ticket |
